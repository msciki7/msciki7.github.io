# 접근제어

&ensp;접근제어 = **허가된 사람만 시스템 자원에 접근하게 만드는 것**<br/>
&ensp;쉽게 말하면<br/>
* 로그인 안 하면 DB 못 들어감
* 권한 없으면 테이블 못 봄

&ensp;이 모든 게 접근제어<br/>

&ensp;분야별 접근제어<br/>

1. 정보시스템 접근제어
* 정보 보안 정책에 따라 프로그램, 프로세서, 시스템 등을 허가된 주체(사용자)만이 정보 시스템 자원에 접근할 수 있도록 제한하는 것
* 사용자 → DB, 서버 접근 제한
2. 통신망 접근제어
* 통신 장비가 전송 매체에 접근하는 것을 제어하는 것
* 단말 기기에서 애플리케이션이 단말의 기능 및 자원에 접근하는 것을 허락 또는 거절하는 것
* 네트워크 접근 제어
* 예: Wi-Fi 접속 제한
3. DB 접근제어
* DBMS 관리 시스템에 의해 관리
* 인증과정을 거쳐 로그인 후 SQL을 통해서만 해당 정보에 정상적으로 접근 가능
* DMZ를 거쳐 조직의 가장 내부에 위치
* DBMS 자체가 강력한 보안기능 제공
* ->DB 접근 권한을 가진 사용자가 권한을 남용하여 정보를 유출/변조하는 것이 가장 큰 위협

&ensp;DB 접근제어의 실제 의미<br/>
&ensp;데이터베이스 접근제어: 사용자가 DBMS에 로그인하거나 SQL을 수행하려고 할 때 미리 정의된 보안규칙에 따라 권한 여부를 판단하여 통제하는 솔루션 -> SQL 통제 및 로깅이 필요한 SQL에 대해 SQL수행과 관련된 정보를 저장하는 기능 보유<br/>
* 로그인 + SQL 실행을 규칙으로 통제

&ensp;기능 2가지 핵심<br/>
* SQL 통제
* SQL 로그 저장

&ensp;단순 허용/차단이 아니라 “누가 뭐 했는지 기록”까지 포함<br/>

&ensp;DB 보안 구조<br/>
<p align="center"><img src="/assets/img/database/9주차/9-1.png" width="600"></p>

&ensp;흐름: `사용자 → 인증 → SQL → DB`<br/>

&ensp;그 사이에
* 로그인 통제
* SQL 통제
* 감시 / 감사

&ensp;즉 DB 보안은 “단일 기능”이 아니라 **여러 단계로 구성된 시스템**<br/>

# 접근제어 구성 요소

&ensp;3가지 요소<br/>
```txt
주체 (Subject)
객체 (Object)
권한 (Permission)
```

<p align="center"><img src="/assets/img/database/9주차/9-4.png" width="600"></p>

&ensp;1. 주체 (User, Process 등)<br/>
&ensp;객체에 접근할 수 있는 대상<br/>
* 모든 사용자, 시스템, 응용 프로그램의 프로세스 등

&ensp;주체 등급 분류<br/>
<p align="center"><img src="/assets/img/database/9주차/9-2.png" width="600"></p>

&ensp;2. 객체 (Object)<br/>
* 주체가 접근 및 사용하고자 하는 대상
* 데이터(데이터베이스), 서버, 컴퓨터, 파일, 응용 프로그램 등

&ensp;예<br/>
* DB
* 파일
* 서버
* 프로그램

&ensp;3. 접근 권한 (Permission)<br/>
* 특정 주체가 특정 객체를 접근하는 방법을 지정

<p align="center"><img src="/assets/img/database/9주차/9-3.png" width="600"></p>

| 권한 | 의미 |
| -- | -- |
| R  | 읽기 |
| W  | 수정 |
| X  | 실행 |
| D  | 삭제 |
| C  | 생성 |


# 접근제어 절차

&ensp;전체 흐름: `식별 → 인증 → 인가`<br/>

&ensp;1. 식별<br/>
&ensp;식별이란 시스템이 주체의 신원을 확인하기 위해 고유한 식별자를 입력받는 과정<br/>
&ensp;2. 인증 (Authentication)<br/>
&ensp;인증이란 주체가 자신이 주장하는 신원이 맞는지를 검증하는 과정<br/>
* 인증 = 신원 확인
&ensp;3. 인가 (Authorization)<br/>
&ensp;인증된 주체가 특정 객체에 대해 수행할 수 있는 행위를 결정하고 권한을 부여하는 과정<br/>
* 인가 = 권한 부여

# 접근제어 규칙

&ensp;잘못된 접근제어 규칙은 정보유츌/ 변조 를 가능하게 함 -> 정확한 접근제어 규칙 설계 필요<br/>

&ensp;접근제어 설계 요소<br/>
1. 정보 식별
* DBMS 내 정보 종류에 따라 법규가 다르므로 접근제어 대상 정보를 먼저 식별
  -  예를 들어 정보통신망법은 주민등록번호·카드번호·계좌번호 암호화를, 개인정보보호법은 여권번호·운전면허번호·외국인등록번호 암호화를 요구
  - 법적 규제 외에도 조직의 보안정책에 따라 추가 정보를 정의해야 한다.
* 법적으로 규제를 받고 있는 대상 정보 이외에 조직의 성격에 따라 분류하여 특별히 관리 필요
2. 사용자 식별
* 관리 대상 정보에 접근할 수 있는 사용자를 IP 및 MAC 주소로 파악
* P·MAC은 변경될 수 있으므로 계정(ID/PW), OTP, SMS 등의 추가 인증을 통해 식별한다.
3. 접근 시간
* 민감한 정보는 업무 시간에만 접속 가능하도록 설정하고, 장시간 자리를 비운 뒤 재접속 시 동일인 여부를 확인하거나 세션을 차단·재접속하도록 설정한다.
4. 접근 방법
* 사용자가 DB 접속에 사용하는 단말기, 접속 툴, 접속 프로토콜을 지정하고, 사용 가능한 SQL 종류를 제한한다.

# 접근제어 규칙 종류 및 설정

&ensp;접근제어 규칙 = 명칭부 + 조건부 + 제어부<br/>
<p align="center"><img src="/assets/img/database/9주차/9-6.png" width="600"></p>

&ensp;1. 명칭부 (Name Part)<br/>
&ensp;정의<br/>
* 접근제어 규칙의 이름을 정의하는 부분
* 규칙의 내용을 간단하고 명확하게 표현해야 함

&ensp;특징<br/>
* 누가, 어떤 DB에 대해 만든 규칙인지 드러나야 함
* 개인 단위 관리 시 → ID / IP 포함 가능

&ensp;예시<br/>
* USER1 DBS 접근 규칙

&ensp;2. 조건부 (Condition Part)<br/>
&ensp;정의<br/>
* 어떤 상황에서 이 규칙이 적용될지를 결정하는 조건
* 여러 요소(Factor)를 조합해서 구성

<p align="center"><img src="/assets/img/database/9주차/9-7.png" width="600"></p>

&ensp;조건부 구성 요소 (3가지로 나뉨)<br/>
&ensp;(1) 사용자 속성<br/>
* ID
* IP

&ensp;(2) 수단 속성<br/>
* 접속 툴 (예: TOAD)
* 단말기명

&ensp;(3) 정보 속성<br/>
* DB명
* DB 계정
* 테이블 / 컬럼

&ensp;조건부는 “누가 + 어떻게 + 무엇에 접근할 때”를 정의하는 부분<br/>

&ensp;3. 제어부 (Control Part)<br/>
&ensp;정의<br/>
* 조건부에서 설정한 조건으로 사용자가 접속하는 경우 어떻게 제어할지 정의

&ensp;제어부의 4가지 핵심 규칙<br/>
&ensp;1. 로그인 통제 규칙<br/>
&ensp;정의<br/>
* DBMS 로그인 자체를 통제하는 규칙

&ensp;특징<br/>
* 단순 ID/비밀번호가 아니라
* 여러 요소를 함께 고려 (Multi-Factor)

&ensp;사용 요소<br/>
* IP
* 접속 툴
* 단말기
* 프로토콜
* 시간

&ensp;2. SQL 수행 통제 규칙<br/>
&ensp;정의<br/>
* SQL 실행 권한을 검사해서 실행 여부를 결정하는 규칙

&ensp;판단 기준<br/>
* SQL 종류 (SELECT, INSERT, DROP 등)
* 접근 대상 (테이블, 컬럼)

&ensp;3. 로깅 통제 규칙<br/>
&ensp;정의<br/>
* 어떤 SQL을 기록할지 결정하는 규칙

&ensp;핵심: 모든 SQL을 기록하면 안됨<br/>
* 저장 공간 낭비
* 분석 시간 증가
* 보안적으로 의미 없는 데이터 증가

&ensp;보안적으로 의미 있는 SQL만 저장<br/>

&ensp;4. 경보 통제 규칙<br/>
* DB 접근제어 과정에서 보안 정책이 위반하는 사건이 발생할 때 보안 관리자에게 통지하여 즉각적인 대응을 할 수 있도록 하는 규칙
* 보안 위반 발생 시 관리자에게 알리는 규칙

&ensp;경보 발생 조건<br/>
* 반복 로그인 실패
* 금지된 테이블 접근 시도
* 허용되지 않은 SQL 실행
* 대량 데이터 조회

&ensp;경보 방식<br/>
* 이메일
* SMS
* 관리자 화면

# 데이터베이스 접근제어 구축

&ensp;접근제어 규칙 설계 → 규칙 종류 정의 → 실제 시스템에 적용 (구축)<br/>

&ensp;1. 우회 접근 방지<br/>
&ensp;정의: 접근제어 시스템을 거치지 않고 DB에 직접 접근하는 것을 차단하는 것<br/>

&ensp;접근제어 서버를 안 거치면 모든 규칙이 무의미해진다.<br/>

&ensp;1. 모든 접근 기록(Logging)<br/>
* 언제
* 어디서
* 누가
* 무엇을 했는지

&ensp;이걸 기록해야 **책임추적성(Accountability) 확보** <br/>

&ensp;우회 접근 방지는 접근제어 규칙이 적용되지 않는 경로를 차단하여 보안 통제를 유지하는 것이다.<br/>

&ensp;2. 프록시 게이트웨이 (Proxy Gateway)<br/>
&ensp;정의: DB 접근 시 반드시 특정 서버(프록시)를 거치도록 강제하는 방식<br/>

&ensp;동작 원리<br/>
&ensp;`사용자 → 프록시 서버 → DB`<br/>
&ensp;직접 DB 접근 x<br/>
&ensp;무조건 프록시 거쳐야 함<br/>

&ensp;특징<br/>
* 접근제어 서버 역할 수행
* 모든 트래픽을 통제 가능

&ensp;문제점<br/>
* 사용자가 설정 변경하면 직접 DB 접속 가능

&ensp;3. 우회 차단 방법<br/>
&ensp;① 에이전트 방식<br/>
&ensp;정의: DB 서버에 직접 프로그램(Agent)을 설치해서 접근 통제<br/>

&ensp;특징<br/>
* DB 내부에서 직접 통제
* 우회 접속도 차단 가능

&ensp;주의<br/>
* 서버 성능 영향 고려 필요

&ensp;서버 내부에서 직접 접근을 감시하고 차단<br/>

&ensp;② 서버 보안 방식<br/>
&ensp;정의: 운영체제(OS) 수준에서 접근을 통제하는 방식<br/>

&ensp;동작 방식<br/>
* 특정 포트 접근 제어
* API 호출 시 권한 검사
* DB 리스너 접근 통제

&ensp;특징<br/>
* OS 레벨 보안
* 강력한 통제 가능

&ensp;“인가된 사용자 관리” 중요<br/>
&ensp;운영체제 수준에서 DB 접근을 제어하는 방식이다.<br/>

&ensp;③ 스니핑 방식<br/>
&ensp;정의: 네트워크 패킷을 복사해서 감시하고 이상 행동 시 차단<br/>

&ensp;특징<br/>
* DB 서버에 영향 없음
* 네트워크에서 감시

&ensp;동작<br/>
* 권한 없는 SQL 실행 → 세션 강제 종료

&ensp;프록시 안 거친 접근도 탐지 가능<br/>

&ensp;단점<br/>
* 오작동 시 정상 사용자도 차단 가능
* 사전 테스트 필수

<p align="center"><img src="/assets/img/database/9주차/9-8.png" width="600"></p>

&ensp;④ 기타 방식<br/>
&ensp;예시<br/>
* 방화벽
* DBMS 자체 기능 (로그인 트리거 등)

&ensp;핵심: 시스템 환경에 맞게 다양한 방법을 조합해서 사용<br/>

# 환경 보안

&ensp;1) 접근제어 서버 관리<br/>
&ensp;우회 접근을 차단하더라도 접근제어 서버가 안전하게 관리되지 않으면 접근제어는 무의미하다.<br/>
&ensp;악의적인 공격자가 접근제어 서버에 접근해서 **접근제어 규칙을 변경하거나 로그를 훼손**하면 올바른 접근제어를 수행할 수 없다. 따라서 DB 접근제어와 관련하여 설치되는 **솔루션과 서버는 DBMS와 동일한 수준에서 관리**해야 한다.<br/>

&ensp;이해 포인트<br/>
&ensp;그런데 아무리 DB로 직접 들어가는 길을 막아도, 접근제어 서버 자체가 뚫리면 끝이다.<br/>
&ensp;예를 들어 접근제어 서버에 있는 규칙이 이렇게 되어 있었다고 한다.<br/>
&ensp;`운영 DB의 고객정보 테이블 접근 금지`<br/>
&ensp;그런데 공격자가 접근제어 서버에 들어가서 이 규칙을 바꿔버리면?<br/>
&ensp;`운영 DB의 고객정보 테이블 접근 허용`<br/>
&ensp;이렇게 되면 접근제어 시스템은 존재하지만 실제로는 보안을 못 하는 상태가 된다. 그래서 접근제어 서버는 단순한 보조 서버가 아니라 **DBMS만큼 중요한 보안 대상**으로 관리해야 한다.<br/>

&ensp;2) DB 접근제어 관리자 계정 관리<br/>
&ensp;솔루션에 따라 혼자서 관리하거나 관리 기능이 **세분화되어 여러 명이 관리**할 수 있다. 따라서 수행하는 **관리 범위에 따라 적절한 관리 권한이 부여되도록 보안 정책을 설정**해야 한다.<br/>

&ensp;이해 포인트<br/>
&ensp;관리자라고 해서 모든 권한을 다 주면 안 된다.<br/>
&ensp;예를 들어 DB 접근제어 관리자 역할을 나누면 이렇게 볼 수 있다.<br/>
```txt
정책 관리자: 접근제어 규칙 생성/수정
로그 관리자: 로그 조회 및 보관
감사 관리자: 감사 보고서 확인
시스템 관리자: 서버 설정 및 유지보수
```

&ensp;이때 로그만 봐야 하는 관리자에게 정책 수정 권한까지 주면 위험하다. 왜냐하면 로그 담당자가 악의적으로 정책을 바꾸거나 실수로 중요한 규칙을 삭제할 수도 있기 때문이다.<br/>
&ensp;그래서 이 부분은 최소 권한 원칙과 연결된다.<br/>

>> 필요한 일을 수행하는 데 필요한 만큼만 권한을 부여해야 한다.

&ensp;3) 포트 관리<br/>
&ensp;기능 제공과 관련된 것으로 **필요한 포토만 개방**하고 **불필요한 포트는 모두 차단**되도록 설정해야 한다.<br/>

&ensp;이해 포인트<br/>
&ensp;포트는 서버가 외부와 통신하기 위한 문이라고 보면 된다. 예를 들어 DB 서버가 1521번 포트를 사용하고 관리 서버가 8080번 포트를 사용한다. 그런데 필요 없는 21번 FTP 포트, 23번 Telnet 포트, 알 수 없는 관리 포트까지 열려 있으면 공격자가 들어올 수 있는 문이 많아지는 것이다.<br/>
&ensp;그래서 포트 관리는 단순하다.<br/>
```txt
필요한 포트만 열기
불필요한 포트는 닫기
```

&ensp;4) OS 취약점 관리<br/>
&ensp;접근제어 솔루션이 설치된 OS상에 **취약점이 존재하지 않도록 정기적으로 OS 취약점 점검**을 수행해야 한다. 취약점이 발견된 버전의 경우 **보안 패치를 통해 취약점을 제거**해야 한다.<br/>

&ensp;이해 포인트<br/>
&ensp;접근제어 솔루션은 결국 어떤 서버의 OS 위에서 실행된다. 즉 OS가 취약하면 그 위에 설치된 접근제어 솔루션도 위험해질 수 있다. 예를 들어 접근제어 솔루션 자체는 안전해도 운영체제에 알려진 보안 취약점이 있으면 공격자가 OS를 통해 서버에 침입할 수 있다. 그러면 접근제어 정책이나 로그도 영향을 받을 수 있다. 그래서 OS 취약점 관리는 다음 흐름으로 이해하면 된다.<br/>
```txt
정기 점검
→ 취약점 발견
→ 보안 패치 적용
→ 취약점 제거
```

# 보안 적용 시험

&ensp;1) 보안 적용 시험 개요<br/>
&ensp;보안 적용 시험은 접근제어 솔루션의 기능이 제대로 동작하는지 점검하는 것이다. 개발 DB 또는 테스트 DB가 **별도 구축된 상태에서 진행**하며 시험 결과는 시험 결과서로 관리한다.<br/>

&ensp;이해 포인트<br/>
&ensp;보안 적용 시험은 말 그대로 “우리가 만든 보안 정책이 실제로 잘 동작하나?”를 확인하는 과정.<br/>
&ensp;예를 들어 이런 걸 확인하는 것이다.<br/>
```txt
허용된 사용자는 로그인 가능한가?
금지된 사용자는 로그인 차단되는가?
DROP TABLE 같은 위험 SQL은 차단되는가?
접근 기록이 로그로 남는가?
위반 상황에서 경보가 발생하는가?
```

&ensp;중요한 건 운영 DB에서 바로 시험하면 위험하다는 것이다. 그래서 개발 또는 테스트 DB가 별도 구축된 상태에서 진행한다.<br/>

&ensp;2) 시험 대상 항목<br/>
* 로그인 제어: 사용자가 DBMS에 로그인할 때, 접근제어 정책에 따라 로그인을 허용하거나 차단하는 기능을 시험하는 항목
* SQL 통제: 사용자가 SQL을 실행할 때, 권한에 따라 SQL 수행을 허용하거나 차단하는 기능을 시험하는 항목
* 로깅(감사): DB 접근이나 SQL 수행 결과가 로그로 기록되는지 확인하는 항목
* 경보: 보안 정책 위반 상황이 발생했을 때, 보안 관리자에게 이메일, SMS, 관리 화면 등으로 경보가 전달되는지 확인하는 항목
* SQL 마스킹: 민감한 데이터가 조회될 때 일부 값을 가려서 보여주는 기능을 시험하는 항목
* 모니터링: DB 접근 현황, 사용자 접속 상태, SQL 수행 현황 등을 실시간 또는 주기적으로 확인할 수 있는지 시험하는 항목
* 보안 정책 관리: 접근제어 정책을 생성, 수정, 삭제하고 적용하는 기능이 제대로 동작하는지 확인하는 항목
* 보고서: 로그나 감사 결과를 기반으로 보고서를 생성할 수 있는지 확인하는 항목
* 장애 대응: 장애가 발생했을 때 서비스나 접근제어 기능이 어떻게 동작하는지 확인하는 항목
* 로그 관리: 로그가 정상적으로 저장되고, 보관되고, 검색되고, 삭제 정책에 맞게 관리되는지 확인하는 항목

&ensp;3) 시험 환경 구성<br/>
&ensp;시험 환경은 실제 환경 또는 시험 항목에 따라 다르게 구성할 수 있다.<br/>

&ensp;이해 포인트<br/>
&ensp;즉, 정해진 하나의 환경만 있는 게 아니다. 테스트하려는 항목에 따라 환경을 다르게 구성할 수 있다. 예를 들어 스니핑 방식 차단을 시험하려면 네트워크 트래픽을 복사해서 보는 구성이 필요할 수 있고, 프록시 게이트웨이를 시험하려면 사용자가 프록시 서버를 거쳐 DB에 접속하는 구조가 필요하다.<br/>

&ensp;4) 보안 적용 시험 수행<br/>
&ensp;기능 시험<br/>
&ensp;필요한 기능이 적절히 동작하는지 확인하여 기능 시험서를 작성한다.<br/>

&ensp;그 외의 시험<br/>
&ensp;완전성 및 성능 시험을 위해 패킷 손실, Long SQL 등에 대한 시험을 수행한다.<br/>

&ensp;보안 적용 시험 유의점<br/>
&ensp;기능 시험에서는 조직이 DB 접근제어를 위해 필요하다고 생각하는 모든 기능을 점검해야 한다. 솔루션 시스템 업그레이드 이후 기능 제공 여부를 파악해야 한다. 또한 실제 환경과 유사한 환경을 구축하고 테스트해야 한다.<br/>

&ensp;이해 포인트<br/>
&ensp;시험할 때 대충 “로그인만 되네?” 하고 끝내면 안 된다. 조직에서 필요한 기능이 있다면 전부 확인해야 한다.<br/>
```txt
로그인 통제 필요 → 로그인 시험
SQL 통제 필요 → SQL 차단 시험
마스킹 필요 → 마스킹 시험
경보 필요 → 경보 시험
보고서 필요 → 보고서 시험
```

&ensp;그리고 솔루션을 업그레이드하면 기존 기능이 그대로 유지되는지도 다시 확인해야 한다. 업그레이드 이후 설정이 바뀌거나 기능이 달라질 수 있기 때문이다. 마지막으로, 시험 환경은 실제 운영 환경과 비슷해야 한다. 너무 단순한 테스트 환경에서만 성공하면 실제 운영 환경에서 문제가 생길 수 있다.<br/>

# 접근제어 모델(정책) 유형

&ensp;4가지 주요 접근 통제 정책<br/>
1. 임의적 접근제어(DAC): 접근을 요청하는 사용자의 신분(Identity) 및 접근 규칙에 기반하는 접근제어
2. 강제적 접근제어(MAC): 주체 및 객체의 보안 분류 등급에 기반하는 접근제어
3. 역할 기반 접근제어(RBAC): 주체에 대한 행위나 역할에 기반하는 접근제어
4. 속성 기반 접근제어(ABAC): 동적인 환경과 주체와 객체의 속성(Attribute)에 기반하는 접근제어

&ensp;1) 임의적 접근제어, DAC<br/>
&ensp;접근을 요청하는 사용자의 신분, 즉 Identity 및 접근 규칙에 기반하는 접근제어이다.<br/>
&ensp;또한 DAC에서 Discretionary, 즉 “임의적”이라는 말은 객체 소유자의 판단에 따라 임의적으로 권한을 줄 수 있다는 의미이다. 객체 소유자가 객체에 대한 접근 권한을 설정한다.<br/>

&ensp;DAC는 “누구인지”를 보고 권한을 주는 방식<br/>

&ensp;2) 강제적 접근제어, MAC<br/>
&ensp;주체 및 객체의 보안 분류 등급에 기반하는 접근제어이다.<br/>
&ensp;MAC는 사용자가 마음대로 권한을 주는 방식이 아니라, 보안 등급에 따라 접근 여부가 결정되는 방식이다. DAC는 객체 소유자가 권한을 줄 수 있지만, MAC는 보안 정책이 강제로 적용되기 때문에 사용자가 임의로 권한을 바꾸기 어렵다.<br/>

&ensp;3) 역할 기반 접근제어, RBAC<br/>
&ensp;주체에 대한 행위나 역할에 기반하는 접근제어이다.<br/>

&ensp;RBAC는 “개인이 누구냐”보다 어떤 역할을 맡고 있느냐를 기준으로 권한을 주는 방식이다.<br/>
```txt
관리자 역할 → 사용자 생성, 삭제 가능
일반 사용자 역할 → 조회만 가능
회계 담당자 역할 → 회계 데이터 접근 가능
```

&ensp;사용자가 바뀌어도 같은 역할을 맡으면 같은 권한을 갖는다.<br/>

&ensp;4) 속성 기반 접근제어, ABAC<br/>
&ensp;동적인 환경과 주체와 객체의 속성(Attribute)에 기반하는 접근제어이다.<br/>
&ensp;ABAC는 단순히 사용자 이름이나 역할만 보는 게 아니라, 여러 속성을 종합해서 판단하는 방식<br/>

## 임의적 접근제어(DAC)

&ensp;임의적 접근제어(DAC; Discretionary Access Control)는 접근을 요청하는 사용자의 신분(Identity) 및 접근 규칙에 기반하는 접근제어이다. Discretionary는 객체 소유자의 판단에 따라 임의적으로 권한을 줄 수 있다는 의미이며, 객체 소유자가 객체에 대한 접근 권한을 설정한다. 또한 Identity-based Access Control, 즉 IBAC라고도 한다.<br/>

```txt
DAC = 사용자의 신분 기반 접근제어
DAC = 객체 소유자가 접근 권한을 설정하는 방식
DAC = IBAC라고도 부름
```

&ensp;장점<br/>
1. 필요에 따라 접근제어 가능 → 융통성 있는 시스템
* DAC는 객체 소유자가 상황에 따라 권한을 줄 수 있다.
2. 대체적으로 구현 용이하고 간단한 사용
* DAC는 사용자와 객체의 권한 관계를 비교적 단순하게 표현할 수 있다.
3. 객체별로 세분화된 접근제어 가능
* 객체마다 권한을 다르게 줄 수 있다.

&ensp;단점<br/>
1. 객체 소유자가 임의로 접근을 허용할 수 있어 다른 모델에 비해 보안성이 취약함
* 중요 파일 소유자 → 잘못된 사용자에게 읽기 권한 부여 → 정보 유출 가능
2. 정보에 대한 엄격한 접근제어가 어려움
* MAC처럼 보안 등급에 의해 강제로 통제되는 구조가 아니기 때문에, 사용자나 소유자의 판단에 따라 권한이 바뀔 수 있다.
3. 다른 주체의 신분을 도용한 중대한 결함 발생 가능
* root 권한 탈취 → 시스템을 완벽하게 장악 가능

&ensp;예시<br/>
&ensp;Windows 예시<br/>
&ensp;Windows에서는 사용자 계정별로 권한을 줄 수 있다.<br/>
```txt
Admin 권한
사용자 계정 생성
사용자별 권한 부여
객체 생성
정보 접근 권한 설정
```

&ensp;사용자별로 파일이나 폴더에 대해 읽기, 쓰기, 실행 권한을 다르게 설정할 수 있다.<br/>

&ensp;DAC의 대표적인 모델<br/>
1. 접근제어행렬(Access Control Matrix, ACM)
2. 권한목록(Capability List, 접근가능목록)
3. 접근제어목록(Access Control List, ACL)

&ensp;접근제어행렬, ACM<br/>
&ensp;접근제어행렬은 모든 주체(Subject)와 객체(Object)에 대한 권한 관계를 2차원 배열로 표현하는 모델이다.<br/>
&ensp;주체와 객체를 알고 있으면 권한 확인이 가능하다.<br/>
&ensp;주체-객체 간의 권한을 개념적으로 표현한다.<br/>
&ensp;실제 시스템 구현 시 Capability List 또는 Access Control List로 구현한다.<br/>

<p align="center"><img src="/assets/img/database/9주차/9-9.png" width="600"></p>

&ensp;권한목록, Capability List<br/>
&ensp;권한목록은 주체에 대한 접근 가능한 객체를 리스트 형태, 즉 객체와 권한으로 구현하는 방법이다.<br/>
&ensp;주체 중심 방식이다.<br/>

&ensp;핵심 구조<br/>
&ensp;권한목록은 한 주체가 무엇에 접근할 수 있는지를 중심으로 본다.<br/>
&ensp;`주체 → [(객체, 권한), (객체, 권한), ...]` <br/>

<p align="center"><img src="/assets/img/database/9주차/9-10.png" width="600"></p>

&ensp;주체가 접근할 수 있는 객체가 많아지면 탐색 시간이 증가한다.<br/>

&ensp;접근제어목록, ACL<br/>
&ensp;접근제어목록은 객체에 대한 권한을 가지고 있는 주체를 리스트 형태, 즉 주체와 권한으로 구현하는 방식이다. 객체 중심 방식이다.<br/>
&ensp;주체가 접근할 수 있는 객체가 많아지면 탐색 시간도 증가한다.<br/>
&ensp;토큰은 객체에 대한 권한 정보를 보유한다. 쉽게 말하면 토큰은 “이 사용자가 어떤 객체에 어떤 권한을 갖는지”를 담고 있는 증표처럼 볼 수 있다.<br/>

&ensp;핵심 구조<br/>
&ensp;ACL은 하나의 객체에 누가 접근할 수 있는지를 중심으로 본다.<br/>
&ensp;`객체 → [(주체, 권한), (주체, 권한), ...]` <br/>

<p align="center"><img src="/assets/img/database/9주차/9-11.png" width="600"></p>

&ensp;ACL의 특징<br/>
&ensp;한 객체에 대해 많은 주체가 권한을 부여받았을 경우, 리스트가 길어져 탐색 시간이 증가한다.<br/>
&ensp;즉, 하나의 객체를 너무 많은 사용자가 접근할 수 있다면, 그 객체의 ACL이 길어지고 권한 확인 시간이 늘어날 수 있다.<br/>

&ensp;Capability List와 ACL 차이<br/>

| 구분    | Capability List             | ACL                                           |
| ----- | --------------------------- | --------------------------------------------- |
| 기준    | 주체 중심                       | 객체 중심                                         |
| 형태    | 주체 → 객체와 권한 목록              | 객체 → 주체와 권한 목록                                |
| 질문 방식 | “Bob은 무엇에 접근할 수 있는가?”       | “이 파일에는 누가 접근할 수 있는가?”                        |
| 예시    | Bob = [(OS, RX), (Data, R)] | Accounting Program = [(Bob, RX), (Alice, RX)] |

# DAC와 Trojan Horse 공격 취약성

&ensp;DAC 모델이 Trojan Horse 공격에 취약하다.<br/>
>> 응용프로그램에 내장된 Trojan Horse에 대해 데이터를 보호할 수 없다.

&ensp;취약한 이유<br/>
&ensp;DAC는 사용자의 신분과 권한을 기준으로 접근을 허용한다. 문제는 사용자가 실행한 프로그램이 악성코드를 포함하고 있으면, 그 프로그램이 사용자의 권한을 이용해서 데이터에 접근할 수 있다는 점이다.<br/>

&ensp;예시<br/>
<p align="center"><img src="/assets/img/database/9주차/9-12.png" width="600"></p>

&ensp;주체<br/>
```txt
밥(Bob)
앨리스(Alice)
이브(Eve)
Prog. Troy
```

&ensp;객체<br/>
```txt
File X
File Y
Prog. Troy
```

&ensp;관계 흐름<br/>
```txt
Alice는 File X를 읽을 수 있음
Alice는 Prog. Troy를 실행할 수 있음
Prog. Troy는 File X를 읽고 File Y에 쓸 수 있음
Eve는 File Y를 읽을 수 있음
```

&ensp;공격 흐름<br/>
1. Eve가 악성 프로그램 Prog. Troy를 만든다.
2. Alice가 Prog. Troy를 실행한다.
3. Prog. Troy는 Alice의 권한을 이용해 File X를 읽는다.
4. Prog. Troy는 읽은 내용을 File Y에 쓴다.
5. Eve는 File Y를 읽어 File X의 정보를 얻는다.

&ensp;Alice는 정상 사용자지만, Alice가 실행한 프로그램이 Alice의 권한을 이용해 정보를 빼내는 구조<br/>

&ensp;핵심 위험성<br/>
&ensp;Trojan Horse 악성코드를 통해 모든 시스템 제어가 가능할 수 있다고 설명한다. DAC는 “누가 접근했는가”를 중심으로 보기 때문에, 정상 사용자가 실행한 프로그램 내부의 악성 행위를 완벽하게 막기 어렵다.<br/>
