# 관계형 데이터베이스(RDB) 

&ensp;관계형 데이터베이스는 영어로 Relational Database, 줄여서 RDB라고 한다. 이 말에서 가장 중요한 단어는 관계(Relation)이다.<br/>
&ensp;RDB는 현실 세계의 데이터를 그냥 흩어 놓는 것이 아니라 행과 열로 이루어진 표 형태로 표현하고 그 표들 사이의 논리적인 관계를 이용해서 데이터를 관리하는 방식이다.<br/>

&ensp;누가 제안했는가?<br/>
&ensp;관계형 데이터베이스는 1970년대 IBM의 에드거 F. 커드(E. F. Codd)가 제안한 관계형 모델(Relational Model) 을 바탕으로 만들어졌다. 즉, RDB는 단순히 “표처럼 생긴 저장소”가 아니라, 수학적 관계 모델에 기반한 데이터 모델이다.<br/>

&ensp;관계형 데이터베이스를 사용하는 대표적인 DBMS는 다음과 같다.<br/>
* Oracle
* Microsoft SQL Server
* IBM DB2

&ensp;프리웨어 / 오픈소스<br/>
* MariaDB
* PostgreSQL
* SQLite

<p align="center"><img src="/assets/img/database/3주차/3-1.png" width="600"></p>

&ensp;RDB는 이론으로만 끝나는 것이 아니라 실제 산업 현장과 서비스에서 널리 사용되는 가장 대표적인 데이터베이스 방식이다.<br/>

# RDB의 특징

&ensp;1. 표 형태로 데이터를 저장한다.<br/>
&ensp;RDB의 가장 큰 특징은 데이터를 단순한 표 형태로 저장한다는 점이다. 그래서 사용자가 구조를 직관적으로 이해하기 쉽다.<br/>
&ensp;예를 들어 고객 정보를 저장한다면 아래처럼 볼 수 있다.<br/>
* 열: 고객아이디, 고객이름, 나이, 등급, 직업, 적립금
* 행: 각 고객 한 명의 정보

&ensp;이렇게 표 형태로 저장되기 때문에 데이터가 무엇을 의미하는지 파악하기 쉽고 초보자도 구조도 비교적 빨리 이해할 수 있다.<br/>

&ensp;2. SQL로 데이터를 관리한다.<br/>
&ensp;RDB는 구조화된 질의 언어(SQL)를 사용해서 데이터를 다룬다.<br/>
&ensp;SQL을 이용하면 다음 작업들을 수행할 수 있다.<br/>
* 검색
* 추가
* 갱신
* 삭제

&ensp;즉, 데이터를 보기 좋게 저장할 뿐만 아니라, 정해진 언어로 체계적으로 조작할 수 있다는 점이 중요하다.<br/>

&ensp;3. 데이터 이용과 확장이 비교적 쉽다.<br/>
&ensp;RDB는 저장 구조가 명확해서 데이터를 이용하기 쉽고 응용 프로그램을 크게 바꾸지 않고도 데이터 항목을 확장할 수 있다.<br/>
&ensp;물론 완전히 자유롭게 막 바꾸는 것은 아니지만 적어도 구조가 잘 정리되어 있기 때문에 예측 가능한 방식으로 확장할 수 있다는 장점이 있다.<br/>

&ensp;4. 데이터 공유 환경에서 효과적이다.<br/>
&ensp;RDB는 다양한 보안 기능을 제공하므로 여러 사용자가 함께 데이터를 쓰는 환경에 적합하다.<br/>
&ensp;예를 들어<br/>
* 사용자 A는 시스템 D와 테이블 G에 접근 가능
* 사용자 B는 폴더 H만 접근 가능
* 사용자 C는 여러 곳에 접근 가능

&ensp;이런 식으로 사용자별 권한을 다르게 부여할 수 있다. 즉, 같은 데이터베이스를 여러 사람이 쓰더라도 접근 권한을 세밀하게 통제할 수 있다는 뜻이다.<br/>

&ensp;RDB의 장점과 단점<br/>
&ensp;장점<br/>
1. 이해하기 쉽다
2. 데이터 이용이 쉽다
3. 공유와 보안에 유리하다.

&ensp;단점<br/>
&ensp;구조 변경 시 비용이 많이 든다.<br/>
&ensp;처음 설계한 데이터베이스 구조를 나중에 변경하거나 확장하려면 하면<br/>
* 구조를 다시 최적화해야 하고
* 유지 및 관리 비용이 상대적으로 많이 들 수 있다.

&ensp;즉 RDB는 초기 설계가 매우 중요하다. 처음 구조를 잘못 잡으면 나중에 수정하는 데 부담이 커질 수 있다.<br/>

# RDB 모델링

## 릴레이션(Relation)

&ensp;RDB에서 가장 기본이 되는 개념이 릴레이션(Relation)이다. 하나의 표라고 생각하면 된다.<br/>

<p align="center"><img src="/assets/img/database/3주차/3-2.png" width="600"></p>

&ensp;예를 들어 고객 릴레이션이 있다면 그 안에는 다음과 같은 속성이 있을 수 있다.<br/>
* 고객 아이디
* 고객 이름
* 나이
* 등급
* 직업
* 적립금

&ensp;그리고 각 고객의 실제 정보가 행으로 저장된다.<br/>

&ensp;속성과 튜플<br/>
<p align="center"><img src="/assets/img/database/3주차/3-3.png" width="600"></p>

&ensp;속성(Attribute): 표의 열(column)을 의미한다. (예: 고객이름, 나이, 직업)<br/>
&ensp;튜플(Tuple): 표의 행(row)을 의미한다. (예: apple, 김현준, 20, gold, 학생, 1000)<br/>
* 열 = 속성
* 행 = 튜플

## 릴레이션 스키마와 릴레이션 인스턴스

&ensp;**릴레이션 스키마(Relation Schema)**<br/>
&ensp;릴레이션 스키마는 릴레이션의 논리적 구조를 뜻한다. 쉽게 말하면 "이 표가 어떤 열들로 이루어져 있는가?"를 나타낸다.

&ensp;예를 들면 다음과 같다.<br/>
* 고객(고객아이디, 고객 이름, 나이, 등급, 직업, 적립금)

&ensp;이건 실제 데이터가 아니라 **무엇을 저장할지 정해 놓은 설계도**라고 보면 된다. 이런 스키마는 자주 바뀌지 않는 정적인 특징을 가진다. 그래서 릴레이션 스키마를 릴레이션 내포(Relation Intension)라고도 한다.<br/>

<p align="center"><img src="/assets/img/database/3주차/3-4.png" width="600"></p>

&ensp;**릴레이션 인스턴스(Relation Instance)**<br/>
&ensp;릴레이션 인스턴스는 **특정 시점에 실제로 저장되어 있는 튜플들의 집합** 이다.<br/>
&ensp;예를 들어 오늘 고객 테이블에 4명의 고객 정보가 저장되어 있다면 그 4개의 행 전체가 현재 시점의 릴레이션 인스턴스가 된다.<br/>
* 스키마는 구조
* 인스턴스는 실제 데이터

&ensp;라고 정리하면 된다.<br/>
&ensp;릴레이션 인스턴스는 삽입, 삭제, 수정이 자주 일어나는 동적인 특징을 가지며 **릴레이션 외연(Relaiton Extension)**이라고도 한다.<br/>

<p align="center"><img src="/assets/img/database/3주차/3-5.png" width="600"></p>

&ensp;스키마와 인스턴스의 차이<br/>
&ensp;릴에이션 스키마<br/>
* 논리적 구조
* 릴레이션 이름과 속성 이름들
* 자주 변하지 않음
* 정적

&ensp;릴레이션 인스턴스<br/>
* 실제 저장된 데이터
* 튜플들의 집합
* 자주 바뀜
* 동적

# 데이터베이스 스키마와 데이터베이스 인스턴스

&ensp;데이터베이스 스키마(Database Schema)<br/>
&ensp;데이터베이스 스키마는 데이터베이스 전체 구조를 의미한다. 즉, 데이터베이스를 구성하는 여러 릴레이션 스키마들의 모음이다.<br/>
&ensp;예를 들어<br/>
* 고객 릴레이션 스키마
* 상품 릴레이션 스키마
* 주문 릴레이션 스키마

&ensp;이 세 개를 모아 놓은 것이 데이터베이스 스키마다.<br/>

&ensp;데이터베이스 인스턴스(Database Instance)<br/>
&ensp;데이터베이스 인스턴스는 데이터베이스를 구성하는 릴레이션 인스턴스들의 모음이다. 즉 현재 시점에서 데이터베이스 안에 실제로 들어 있는 전체 데이터 상태라고 보면 된다.<br/>
<p align="center"><img src="/assets/img/database/3주차/3-6.png" width="600"></p>
