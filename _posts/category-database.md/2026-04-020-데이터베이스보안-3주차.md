# 관계형 데이터베이스(RDB) 

&ensp;관계형 데이터베이스는 영어로 Relational Database, 줄여서 RDB라고 한다. 이 말에서 가장 중요한 단어는 관계(Relation)이다.<br/>
&ensp;RDB는 현실 세계의 데이터를 그냥 흩어 놓는 것이 아니라 행과 열로 이루어진 표 형태로 표현하고 그 표들 사이의 논리적인 관계를 이용해서 데이터를 관리하는 방식이다.<br/>

&ensp;누가 제안했는가?<br/>
&ensp;관계형 데이터베이스는 1970년대 IBM의 에드거 F. 커드(E. F. Codd)가 제안한 관계형 모델(Relational Model) 을 바탕으로 만들어졌다. 즉, RDB는 단순히 “표처럼 생긴 저장소”가 아니라, 수학적 관계 모델에 기반한 데이터 모델이다.<br/>

&ensp;관계형 데이터베이스를 사용하는 대표적인 DBMS는 다음과 같다.<br/>
* Oracle
* Microsoft SQL Server
* IBM DB2

&ensp;프리웨어 / 오픈소스<br/>
* MariaDB
* PostgreSQL
* SQLite

<p align="center"><img src="/assets/img/database/3주차/3-1.png" width="600"></p>

&ensp;RDB는 이론으로만 끝나는 것이 아니라 실제 산업 현장과 서비스에서 널리 사용되는 가장 대표적인 데이터베이스 방식이다.<br/>

# RDB의 특징

&ensp;1. 표 형태로 데이터를 저장한다.<br/>
&ensp;RDB의 가장 큰 특징은 데이터를 단순한 표 형태로 저장한다는 점이다. 그래서 사용자가 구조를 직관적으로 이해하기 쉽다.<br/>
&ensp;예를 들어 고객 정보를 저장한다면 아래처럼 볼 수 있다.<br/>
* 열: 고객아이디, 고객이름, 나이, 등급, 직업, 적립금
* 행: 각 고객 한 명의 정보

&ensp;이렇게 표 형태로 저장되기 때문에 데이터가 무엇을 의미하는지 파악하기 쉽고 초보자도 구조도 비교적 빨리 이해할 수 있다.<br/>

&ensp;2. SQL로 데이터를 관리한다.<br/>
&ensp;RDB는 구조화된 질의 언어(SQL)를 사용해서 데이터를 다룬다.<br/>
&ensp;SQL을 이용하면 다음 작업들을 수행할 수 있다.<br/>
* 검색
* 추가
* 갱신
* 삭제

&ensp;즉, 데이터를 보기 좋게 저장할 뿐만 아니라, 정해진 언어로 체계적으로 조작할 수 있다는 점이 중요하다.<br/>

&ensp;3. 데이터 이용과 확장이 비교적 쉽다.<br/>
&ensp;RDB는 저장 구조가 명확해서 데이터를 이용하기 쉽고 응용 프로그램을 크게 바꾸지 않고도 데이터 항목을 확장할 수 있다.<br/>
&ensp;물론 완전히 자유롭게 막 바꾸는 것은 아니지만 적어도 구조가 잘 정리되어 있기 때문에 예측 가능한 방식으로 확장할 수 있다는 장점이 있다.<br/>

&ensp;4. 데이터 공유 환경에서 효과적이다.<br/>
&ensp;RDB는 다양한 보안 기능을 제공하므로 여러 사용자가 함께 데이터를 쓰는 환경에 적합하다.<br/>
&ensp;예를 들어<br/>
* 사용자 A는 시스템 D와 테이블 G에 접근 가능
* 사용자 B는 폴더 H만 접근 가능
* 사용자 C는 여러 곳에 접근 가능

&ensp;이런 식으로 사용자별 권한을 다르게 부여할 수 있다. 즉, 같은 데이터베이스를 여러 사람이 쓰더라도 접근 권한을 세밀하게 통제할 수 있다는 뜻이다.<br/>

&ensp;RDB의 장점과 단점<br/>
&ensp;장점<br/>
1. 이해하기 쉽다
2. 데이터 이용이 쉽다
3. 공유와 보안에 유리하다.

&ensp;단점<br/>
&ensp;구조 변경 시 비용이 많이 든다.<br/>
&ensp;처음 설계한 데이터베이스 구조를 나중에 변경하거나 확장하려면 하면<br/>
* 구조를 다시 최적화해야 하고
* 유지 및 관리 비용이 상대적으로 많이 들 수 있다.

&ensp;즉 RDB는 초기 설계가 매우 중요하다. 처음 구조를 잘못 잡으면 나중에 수정하는 데 부담이 커질 수 있다.<br/>

# RDB 모델링

## 릴레이션(Relation)

&ensp;RDB에서 가장 기본이 되는 개념이 릴레이션(Relation)이다. 하나의 표라고 생각하면 된다.<br/>

<p align="center"><img src="/assets/img/database/3주차/3-2.png" width="600"></p>

&ensp;예를 들어 고객 릴레이션이 있다면 그 안에는 다음과 같은 속성이 있을 수 있다.<br/>
* 고객 아이디
* 고객 이름
* 나이
* 등급
* 직업
* 적립금

&ensp;그리고 각 고객의 실제 정보가 행으로 저장된다.<br/>

&ensp;속성과 튜플<br/>
<p align="center"><img src="/assets/img/database/3주차/3-3.png" width="600"></p>

&ensp;속성(Attribute): 표의 열(column)을 의미한다. (예: 고객이름, 나이, 직업)<br/>
&ensp;튜플(Tuple): 표의 행(row)을 의미한다. (예: apple, 김현준, 20, gold, 학생, 1000)<br/>
* 열 = 속성
* 행 = 튜플

## 릴레이션 스키마와 릴레이션 인스턴스

&ensp;**릴레이션 스키마(Relation Schema)**<br/>
&ensp;릴레이션 스키마는 릴레이션의 논리적 구조를 뜻한다. 쉽게 말하면 "이 표가 어떤 열들로 이루어져 있는가?"를 나타낸다.

&ensp;예를 들면 다음과 같다.<br/>
* 고객(고객아이디, 고객 이름, 나이, 등급, 직업, 적립금)

&ensp;이건 실제 데이터가 아니라 **무엇을 저장할지 정해 놓은 설계도**라고 보면 된다. 이런 스키마는 자주 바뀌지 않는 정적인 특징을 가진다. 그래서 릴레이션 스키마를 릴레이션 내포(Relation Intension)라고도 한다.<br/>

<p align="center"><img src="/assets/img/database/3주차/3-4.png" width="600"></p>

&ensp;**릴레이션 인스턴스(Relation Instance)**<br/>
&ensp;릴레이션 인스턴스는 **특정 시점에 실제로 저장되어 있는 튜플들의 집합** 이다.<br/>
&ensp;예를 들어 오늘 고객 테이블에 4명의 고객 정보가 저장되어 있다면 그 4개의 행 전체가 현재 시점의 릴레이션 인스턴스가 된다.<br/>
* 스키마는 구조
* 인스턴스는 실제 데이터

&ensp;라고 정리하면 된다.<br/>
&ensp;릴레이션 인스턴스는 삽입, 삭제, 수정이 자주 일어나는 동적인 특징을 가지며 **릴레이션 외연(Relaiton Extension)**이라고도 한다.<br/>

<p align="center"><img src="/assets/img/database/3주차/3-5.png" width="600"></p>

&ensp;스키마와 인스턴스의 차이<br/>
&ensp;릴에이션 스키마<br/>
* 논리적 구조
* 릴레이션 이름과 속성 이름들
* 자주 변하지 않음
* 정적

&ensp;릴레이션 인스턴스<br/>
* 실제 저장된 데이터
* 튜플들의 집합
* 자주 바뀜
* 동적

# 데이터베이스 스키마와 데이터베이스 인스턴스

&ensp;데이터베이스 스키마(Database Schema)<br/>
&ensp;데이터베이스 스키마는 데이터베이스 전체 구조를 의미한다. 즉, 데이터베이스를 구성하는 여러 릴레이션 스키마들의 모음이다.<br/>
&ensp;예를 들어<br/>
* 고객 릴레이션 스키마
* 상품 릴레이션 스키마
* 주문 릴레이션 스키마

&ensp;이 세 개를 모아 놓은 것이 데이터베이스 스키마다.<br/>

&ensp;데이터베이스 인스턴스(Database Instance)<br/>
&ensp;데이터베이스 인스턴스는 데이터베이스를 구성하는 릴레이션 인스턴스들의 모음이다. 즉 현재 시점에서 데이터베이스 안에 실제로 들어 있는 전체 데이터 상태라고 보면 된다.<br/>
<p align="center"><img src="/assets/img/database/3주차/3-6.png" width="600"></p>

# 릴레이션의 특성

&ensp;1. 튜플의 유일성<br/>
&ensp;하나의 릴레이션 안에는 완전히 동일한 튜플이 존재할 수 없다. 즉 각 행은 서로 구별 가능해야 한다.<br/>
&ensp;이 유일성을 보장하기 위해 보통 기본키를 둔다.<br/>

&ensp;2. 튜플의 무순서<br/>
&ensp;릴레이션에서 튜플 사이의 순서는 의미가 없다. 첫 번째 행이라고 더 중요한 것도 아니고 마지막 행이라고 덜 중요한 것도 아니다.<br/>

&ensp;3. 속성의 무순서<br/>
&ensp;릴레이션에서 튜플 사이의 순서는 의미가 없다. 첫 번째 행이라고 더 중요한 것도 아니고 마지막 행이라고 덜 중요한 것도 아니다.<br/>
&ensp;즉 행의 순서 자체는 데이터 의미와 무관하다.<br/>

&ensp;4. 속성의 원자성<br/>
&ensp;각 속성에는 원자값 즉 더 이상 나눌 수 없는 하나의 값만 들어가야 한다.<br/>
&ensp;예를 들어 직업 속성에<br/>
* 회사원, 학생

&ensp;처럼 두 값을 한 칸에 넣으면 원자성을 위반한 것이다. 한 속성값에는 하나의 값만 들어가야 한다.<br/>

# 키(Key)의 개념과 종류

&ensp;키란 무엇인가?<br/>
&ensp;키(Key)는 릴레이션에서 튜플을 유일하게 구별하기 위한 속성 또는 속성들의 집합이다. 즉 "이 행이 누구인지 정확히 식별하는 기준"이다.<br/>

&ensp;키의 기본 성질<br/>
&ensp;키는 두 가지 성질을 중심으로 이해해야 한다.<br/>

&ensp;유일성(Uniqueness)<br/>
&ensp;하나의 릴레이션에서 모든 튜플은 서로 다른 키 값을 가져야 한다.<br/>

&ensp;최소성(Minimality)<br/>
&ensp;키는 꼭 필요한 최소한의 속성들로만 구성되어야 한다. 쓸데없는 속성이 더 붙으면 최소성을 만족하지 못한다.<br/>

&ensp;1. 슈퍼키(Super Key)<br/>
&ensp;슈퍼키는 유일성을 만족하는 속성 또는 속성들의 집합이다.<br/>
&ensp;예를 들어 고객 릴레이션에서<br/>
* 고객아이디
* (고객아이디, 고객이름)
* (고객이름, 주소)

&ensp;이 모든 튜플을 유일하게 구별할 수 있다면 슈퍼키가 될 수 있다.<br/>

&ensp;포인트<br/>
&ensp;슈퍼키는 유일하기만 하면 된다. 필요 없는 속성이 더 붙어 있어도 괜찮다.<br/>

<p align="center"><img src="/assets/img/database/3주차/3-7.png" width="600"></p>

&ensp;2. 후보키(Candidate Key)<br/>
&ensp;후보키는 **유일성과 최소성을 모두 만족하는 키**이다.<br/>
&ensp;즉 슈퍼키 중에서<br/>
* 유일하고
* 불필요한 속성이 없는

&ensp;진짜 키 후보 되는 것만 후보키라고 부른다.<br/>

&ensp;예시<br/>
* 고객아이디 → 유일성 O, 최소성 O → 후보키
* (고객아이디, 고객이름) → 유일성 O, 최소성 X → 후보키 아님
* (고객이름, 주소) → 유일성 O, 최소성 O → 후보키

&ensp;즉 **모든 후보키는 슈퍼키이지만 모든 슈퍼키가 후보키는 아니다.**<br/>

<p align="center"><img src="/assets/img/database/3주차/3-8.png" width="600"></p>

&ensp;3. 기본키(Primary Key)<br/>
&ensp;기본키는 후보키 중에서 기본적으로 사용하기 위해 선택한 키이다.<br/>
&ensp;후보키가 여러 개 있을 수 있지만 그중에서 데이터베이스가 대표로 사용하는 키가 기본키이다.<br/>

&ensp;기본키의 역할<br/>
* 튜플 중복 여부 확인
* 각 행을 대표하는 공식 식별자 역할

&ensp;예를 들어<br/>
* 후보키: 고객아이디, (고객이름, 주소)
* 기본키: 고객 아이디

&ensp;처럼 정할 수 있다.<br/>

<p align="center"><img src="/assets/img/database/3주차/3-9.png" width="600"></p>

&ensp;4. 대체키(Alternate Key)<br/>
&ensp;대체키는 **기본키로 선택되지 못한 후보키**이다.<br/>
* 후보키는 맞지만
* 대표로 선택되지 않은 키

&ensp;예를 들어<br/>
* 후보키: 고객아이디, (고객이름, 주소)
* 기본키: 고객아이디

&ensp;라면 (고객이름, 주소)는 데체키가 된다.<br/>

<p align="center"><img src="/assets/img/database/3주차/3-11.png" width="600"></p>

<p align="center"><img src="/assets/img/database/3주차/3-12.png" width="600"></p>

&ensp;5. 외래키(Foreign Key)<br/>
&ensp;왜래키는 다른 릴레이션의 기본키를 참조하는 속성 또는 속성들의 집합이다. 즉 외래키는 릴레이션과 릴레이션 사이의 관계를 표현하기 위해 사용된다.<br/>

&ensp;예시<br/>
* 고객 릴레이션의 기본키: 고객아이디
* 주문 릴레이션의 외래키: 주문고객

&ensp;주문 릴레이션에서 주문고객 값으로 apple, banana, carrot 같은 고객아이디를 저장하면 이 주문이 어떤 고객의 주문인지 알 수 있다.<br/>

&ensp;외래키의 특징<br/>
* 릴레이션 사이의 관계 표현
* 참조되는 기본키와 도메인이 같아야 함
* 한 릴레이션에 여러 개 존재 가능
* 외래키를 기본키로 사용할 수도 있음
* 자기 자신의 릴레이션을 참조할 수도 있음

&ensp;자기 참조 외래키 예시<br/>
&ensp;고객 릴레이션의 추천 고객 속성이 같은 고객 릴레이션의 고객아이디를 참조할 수 있다. 이건 "누가 누구를 추천했는가" 같은 구조를 표현할 때 사용된다.<br/>

# 무결성 제약조건

&ensp;무결성<br/>
&ensp;무결성은 데이터에 결함이 없는 상태, 즉 데이터가 정확하고 유효하게 유지되는 상태를 의미한다. 데이터베이스는 삽입, 삭제, 수정이 계속 일어나지만 그 과정에서도 데이터의 일관성이 깨지지 않아야 한다. 이를 위해 필요한 규칙이 바로 무결성 제약조건이다.<br/>

&ensp;무결성 제약조건의 종류<br/>
&ensp;무결성 제약조건은 크게 세 가지다.<br/>
* 도메인 무결성 제약조건
* 개체 무결성 제약조건
* 참조 무결성 제약조건

&ensp;1. 도메인 무결성 제약조건<br/>
&ensp;도메인 무결성 제약조건은 각 속성값이 정해진 도메인 안의 값만 가져야 한다는 규칙이다.<br/>
&ensp;예를 들어<br/>
* 성별 속성에는 남/여만 허용
* 나이 속성에는 정수만 허용
* 적립금은 0 이상만 허용

&ensp;이런 식으로 속성별 허용 범위를 정한다. SQL에서는 type, null/not null, default, check 등을 사용해서 지정할 수 있다.<br/>

&ensp;예시<br/>
&ensp;고객 릴레이션의 성별 속성에<br/>
* 남
* 여

&ensp;이외의 값이 들어가면 도메인 무결성을 위반한 것이다.<br/>

&ensp;2. 개체 무결성 제약조건<br/>
&ensp;개체 무결성 제약조건은 기본키와 관련된 규칙이다.<br/>
&ensp;기본키는<br/>
* NULL 값을 가져서는 안 되고
* 릴레이션 안에서 유일해야 한다.

&ensp;왜냐하면 기본키는 각 튜플을 식별하는 대표값이기 때문이다. 대표값이 비어 있거나 중복되면 튜플을 구별할 수 없게 된다. 대표값이 비어 있거나 중복되면 튜플을 구별할 수 없게 된다.<br/>

&ensp;3. 참조 무결성 제약조건<br/>
&ensp;참조 무결성 제약조건은 외래키가 참조하는 값이 실제로 존재해야 한다는 규칙이다.<br/>
* 자식 릴레이션의 외래키 값은
* 부모 릴레이션의 기본키 값 중 하나여야 한다.

&ensp;예를 들어 주문 릴레이션의 주문고객이 cherry인데 고객 릴레이션에 cherry라는 고객아이디가 없다면 참조 무결성 위반이다.<br/>

&ensp;참조 무결성의 핵심<br/>
* 부모에 없는 값을 자식이 참조하면 안 됨
* 자식이 참조 중인 부모 키를 함부로 삭제/변경하면 안 됨
* 외래키는 경우에 따라 NULL일 수 있음

#  관게대수(Relational Algebra)

&ensp;관계대수는 릴레이션을 대상으로 원하는 결과를 얻기 위해 사용하는 연산들의 집합이다. 쉽게 말하면 RDB에서 데이터를 논리적으로 다루는 계산 규칙이라고 볼 수 있다.<br/>

<p align="center"><img src="/assets/img/database/3주차/3-15.png" width="600"></p>

&ensp;관계대수의 특징<br/>
* 절차 언어이다.
* 입력도 릴레이션이고 결과도 릴레이션이다.
* 이를 폐쇄 특성(Closure Propety)이라고 한다. 

&ensp;일반 집합 연산자<br/>
* Union(합집합)
* Intersection(교집합)
* Difference(차집합)
* Cartensian Product(카디션 프로덕트)

&ensp;순수 관계 연산자<br/>
* Select(셀렉트)
* Project(프로젝트)
* Join(조인)
* Division(디비전)

# Select 연산자

&ensp;Select 조건을 만족하는 튜플만 선택하면 연산이다. 즉 행을 고르는 연산이다.<br/>
&ensp;그래서 결과 릴레이션은 원래 릴레이션의 수평적 부분집합이 된다.<br/>

&ensp;표현법<br/>
* 수학적 표현: `σ조건식(릴레이션)`
* 데이터 언어적 표현: `릴레이션 where 조건식`

&ensp;예<br/>
* `σ등급='gold'(고객)`
* `고객 where 등급='gold'`

&ensp;예시1<br/>
&ensp;고객 릴레이션에서 등급이 gold인 튜플 검색<br/>
* `σ등급='gold'(고객)`


&ensp;결과<br/>
* apple
* carrot

&ensp;즉 조건을 만족하는 행만 남는다.<br/>

&ensp;예시 2<br/>
&ensp;고객 릴레이션에서 등급이 gold이고 적립금이 2000 이상인 튜플 검색<br/>
&ensp;결과<br/>
* carrot만 남는다. apple은 gold지만 적립금이 1000이기 때문에 제외된다.

<p align="center"><img src="/assets/img/database/3주차/3-17.png" width="600"></p>

&ensp;교환적 특징<br/>
&ensp;Select는 조건의 적용 순서를 바꿔도 결과가 같다.<br/>
* σ조건1(σ조건2(R)) = σ조건2(σ조건1(R))
* = σ조건1∧조건2(R)

<p align="center"><img src="/assets/img/database/3주차/3-18.png" width="600"></p>

&ensp;즉 조건을 한 번에 쓰든 나뉘 쓰든 결과는 같다.<br/>

# Project 연산자

&ensp;Project는 릴레이션에서 원하는 속성(열)만 선택하는 연산이다. 즉 열을 고르는 연산이다.<br/>
&ensp;그래서 결과 릴레이션은 원래 릴레이션의 **수직적 부분집합**이 된다.<br/>

&ensp;표현법<br/>
* 수학적 표현: `π속성리스트(릴레이션)`
* 데이터 언어적 표현: `릴레이션[속성리스트]`

&ensp;예<br/>
* π고객이름, 등급, 적립금(고객)

&ensp;예시1<br>
&ensp;고객 릴레이션에서 고객이름, 등급, 적립금 검색<br/>
&ensp;결과 열<br/>
* 고객이름
* 등급
* 적립금

&ensp;즉 필요한 열만 남기고 나머지는 제거한다.<br/>

<p align="center"><img src="/assets/img/database/3주차/3-19.png" width="600"></p>

&ensp;예시2<br/>
&ensp;고객 릴레이션에서 등급만 검색<br/>
* π등급(고객)

&ensp;원래 값<br/>
* gold
* vip
* gold
* silver

&ensp;Project 결과에서는 중복 튜플이 제거되므로 최종 결과는<br/>
* gold
* vip
* silver

&ensp;가 된다.<br/>

<p align="center"><img src="/assets/img/database/3주차/3-20.png" width="600"></p>

# Division 연산자

&ensp;Division은 릴레이션2의 모든 튜플과 관련이 있는 릴레이션1의 튜플을 찾는 연산이다.<br/>
&ensp;즉 어떤 조건들을 전부 만족하는 대상을 찾고 싶을 때 쓰는 연산이다.<br/>
* `릴레이션1 ÷ 릴레이션2`

&ensp;특징<br/>
* 릴레이션1이 릴레이션2의 모든 속성을 포함하고 있어야 한다.
* 의미상 "모두 만족"이라는 느낌으로 이해하면 편하다.

&ensp;예시<br/>
&ensp;고객 릴레이션을 우수등급 릴레이션으로 나누면 우수등급에 해당하는 조건을 모두 만족하는 고객들이 결과가 된다. 또 주문내역과 제품 릴레이션 예시에서는 "특정 제품 집합을 모두 주문한 고객"을 찾는 식으로 이해할 수 있다.<br/>

# Cartesian Product 연산자

&ensp;Cartesian Product는 두 릴레이션의 모든 튜플 조합을 만드는 연산이다.<br/>
* `R × S`

&ensp;즉 R의 각 행을 S의 모든 행과 하나씩 전부 연결한다.<br/>

&ensp;결과 특성<br/>
* 차수 = R의 차수 + S의 차수
* 카디널리티 = R의 카디널리티 × S의 카디널리티

&ensp;예를 들어<br/>
* R에 3개 행
* S에 3개 행

&ensp;이 있으면 결과는 9개 행이 된다.<br/>

<p align="center"><img src="/assets/img/database/3주차/3-24.png" width="600"></p>

&ensp;성질<br/>
* 교환적
* 결합적

# Union 연산자

&ensp;Union은 두 릴레이션의 **합집합**이다.<br/>
* `R ∪ S`

&ensp;즉 R 또는 S에 속하는 모든 튜플을 결과로 만든다. 단 두 릴레이션은 합병 가능해야 한다. 즉 구조가 같아야 한다.<br/>

&ensp;특징<br/>
* 차수는 동일
* 중복은 제거됨
* 교환적, 결합적 성질이 있음

<p align="center"><img src="/assets/img/database/3주차/3-25.png" width="600"></p>

# Intersection 연산자

&ensp;Intersection은 두 릴레이션의 교집합이다.<br/>
* `R ∩ S`

&ensp;즉 R과 S에 **공통으로 존재하는 튜플만** 결과로 만든다.<br/>

&ensp;특징<br/>
* 차수는 동일
* 결과 카디널리티는 원래 릴레이션보다 같거나 작음
* 교환적, 결합적 성질이 있음

<p align="center"><img src="/assets/img/database/3주차/3-26.png" width="600"></p>

# Difference 연산자

&ensp;Difference는 두 릴레이션의 **차집합**이다.<br/>
* `R - S`

&ensp;즉 R에는 존재하지만 S에는 존재하지 않는 튜플만 결과로 만든다.<br/>

&ensp;핵심포인트<br/>
&ensp;Difference는 방향이 중요하다.<br/>
* `R - S` 와
* `S - R`

&ensp;는 전혀 다른 결과가 나온다. 그리고 다른 연산자와 달리 교환적, 결합적 특징이 없다.<br/>

<p align="center"><img src="/assets/img/database/3주차/3-27.png" width="600"></p>

# Join 연산자

&ensp;Join은 공통 속성 값을 기준으로 두 릴레이션을 결합하는 연산이다.<br/>
* `릴레이션1 ⋈ 릴레이션2`

&ensp;즉 조인 속성 값이 같은 튜플들만 연결해서 새로은 릴레이션을 만든다.<br/>

&ensp;예시<br/>
&ensp;고객 릴레이션<br/>
* 고객아이디, 고객이름, 나이, 등급

&ensp;주문 릴레이션<br/>
* 주문번호, 고객아이디, 주문제품, 수량

&ensp;여기서 공통 속성은 고객아이디이다.<br/>
&ensp;따라서 고객과 주문을 조인하면<br/>
* apple 고객 정보 + apple의 주문 정보
* banana 고객 정보 + banana의 주문 정보
* carrot 고객 정보 + carrot의 주문 정보

&ensp;처럼 연결된다.<br/>

<p align="center"><img src="/assets/img/database/3주차/3-28.png" width="600"></p>

&ensp;`릴레이션.속성이름`으로 쓰는 이유<br/>
&ensp;조인 결과에서는 같은 이름의 속성이 여러 릴레이션에 존재할 수 있다. 예를 들어 고객 릴레이션에도 고객아이디가 있고 주문 릴레이션에도 고객아이디가 있다.<br/>
&ensp;그래서 구분하기 위해<br/>
* 고객.고객아이디
* 주문.고객아이디

&ensp;처럼 표기한다.<br/>

# 요약

&ensp;RDB 한 줄 정리<br/>
&ensp;관계형 데이터베이스는 데이터를 표 형태로 저장하고, 그 표들 사이의 관계를 이용해 데이터를 체계적으로 관리하는 데이터베이스이다.<br/>

&ensp;꼭 구분해야 하는 개념<br/>
&ensp;릴레이션<br/>
* 하나의 표

&ensp;속성<br/>
* 열

&ensp;튜플<br/>
* 행

&ensp;스키마<br/>
* 구조, 설계도

&ensp;인스턴스<br/>
* 실제 저장된 데이터

&ensp;키 정리<br/>
* 슈퍼키: 유일성 만족
* 후보키: 유일성 + 최소성 만족
* 기본키: 후보키 중 대표
* 대체키: 기본키가 아닌 후보키
* 외래키: 다른 릴레이션의 기본키 참조

&ensp;무결성 제약조건 정리<br/>
* 도메인 무결성: 속성값이 허용된 범위 안에 있어야 함
* 개체 무결성: 기본키는 NULL 불가, 유일해야 함
* 참조 무결성: 외래키는 실제 존재하는 기본키를 참조해야 함

&ensp;관계대수 정리<br/>
* Select: 행 선택
* Project: 열 선택
* Division: 모든 조건 만족
* Cartesian Product: 모든 조합
* Union: 합집합
* Intersection: 교집합
* Difference: 차집합
* Join: 공통 속성 기준 결합
