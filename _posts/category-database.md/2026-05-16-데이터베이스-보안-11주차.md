# 암호화 개념

&ensp;1. 데이터 암호화<br/>
&ensp;암호화는 데이터를 아무나 읽을 수 없도록 바꾸는 기술이다.<br/>
&ensp;원래 사람이 읽을 수 있는 데이터를 평문이라고 하고 암호화 과정을 거쳐 의미를 알기 어려운 형태로 바뀐 데이터를 암호문이라고 한다.<br/>

&ensp;암호화의 핵심 목적은 데이터의 기밀성 제공이다.<br/>
* 기밀성: 허가받지 않은 사람이 데이터를 보더라도 내용을 알 수 없게 하는 성질

&ensp;2. 암호화와 복호화<br/>
&ensp;암호화와 복호화는 서로 반대 방향의 과정이다.<br/>

&ensp;**암호화** <br/>
&ensp;암호화는 **암호 키** 를 사용하여 평문을 암호문으로 변환하는 것이다.<br/>
&ensp;`평문 + 암호화 알고리즘 + 키 → 암호문` <br/>

&ensp;예를 들어 내가 “당신을 사랑해요”라는 평문을 가지고 있다고 하자.<br/>
&ensp;이 평문을 암호화 알고리즘에 넣고, 특정한 키를 적용하면 의미를 알 수 없는 암호문이 만들어진다.<br/>
&ensp;암호화 알고리즘만으로는 부족하고 키가 필요하다.<br/>

<p align="center"><img src="/assets/img/database/11주차/11-1.png" width="600"></p>

&ensp;**복호화** <br/>
&ensp;복호화는 암호문을 다시 원래의 평문으로 되돌리는 과정이다.<br/>
&ensp;`암호문 + 복호화 알고리즘 + 키 → 평문` <br/>
&ensp;암호화된 데이터를 원래 내용으로 복원하려면 **복호 키** 가 필요하다.<br/>
&ensp;따라서 키가 제3자에게 알려지면 암호화의 의미가 사라진다.<br/>
&ensp;아무리 암호문으로 바꿔도 공격자가 키를 알고 있으면 다시 평문으로 복구할 수 있기 때문이다.<br/>

<p align="center"><img src="/assets/img/database/11주차/11-2.png" width="600"></p>

&ensp;3. 키의 역할<br/>
&ensp;키는 암호화와 복호화에서 가장 중요한 요소이다.<br/>

&ensp;암호화 알고리즘은 데이터를 바꾸는 규칙이고 키는 그 규칙을 구체적으로 적용하는 값이라고 보면 된다.<br/>
* 암호화 알고리즘 = 자물쇠의 구조
* 키 = 자물쇠를 열고 잠그는 실제 열쇠

&ensp;같은 암호화 알고리즘을 사용하더라도 키가 다르면 결과 암호문이 달라질 수 있다.<br/>
&ensp;그래서 보안에서는 보통 알고리즘 자체를 숨기는 것보다 **키를 안전하게 관리하는 것** 이 더 중요하다.<br/>

&ensp;4. 암호 체계 분류<br/>
&ensp;Cryptology 암호학<br/>
* Cryptography 암호기술
* Cryptanalysis 암호분석

<p align="center"><img src="/assets/img/database/11주차/11-3.png" width="600"></p>

&ensp;암호학 Cryptology<br/>
&ensp;암호학은 암호와 관련된 전체 학문 영역이다. 암호를 만드는 기술뿐 아니라 암호를 깨거나 분석하는 기술까지 포함한다.<br/>

&ensp;암호기술 Cryptography<br/>
&ensp;암호기술은 데이터를 안전하게 보호하기 위해 암호 알고리즘과 프로토콜을 설계하고 사용하는 분야이다.<br/>

```tree
Cryptography 암호기술
├── Symmetric Ciphers 대칭 암호
├── Asymmetric Ciphers 비대칭 암호
└── Protocols 프로토콜
```

&ensp;암호분석 Cryptanalysis<br/>
&ensp;암호분석은 암호문을 분석해서 원래 평문이나 키를 알아내려는 분야이다. 암호기술이 "어떻게 안전하게 만들 것인가?"라면 암호분석은 "이 암호를 어떻게 깨뜨릴 수 있는가?"에 가깝다.<br/>

&ensp;`암호기술은 정보를 보호하기 위해 암호 알고리즘을 설계하고 사용하는 기술이고, 암호분석은 암호문을 해독하거나 암호 체계의 약점을 찾아내는 분석 기술이다.`<br/>

&ensp;5. 대칭 암호와 비대칭 암호<br/>

&ensp;**대칭 암호 Symmetric Cipher** <br/>
&ensp;대칭 암호는 암호화와 복호화에 **같은 키** 또는 매우 밀접하게 관련된 키를 사용하는 방식이다.<br/>
&ensp;`암호화 키 = 복호화 키` <br/>

&ensp;장점은 속도가 빠르다는 것이다. 하지만 단점은 키를 안전하게 공유해야 한다는 점이다.<br/>

&ensp;예를 들어 A와 B가 같은 키를 가지고 있어야 통신할 수 있는데, 이 키를 전달하는 과정에서 누군가 훔쳐보면 보안이 깨진다.<br/>

&ensp;**비대칭 암호 Asymmetric Cipher** <br/>
&ensp;비대칭 암호는 암호화와 복호화에 서로 다른 키를 사용하는 방식이다.<br/>
&ensp;보통 다음 두 가지 키를 사용한다.<br/>
* 공개키: 다른 사람에게 공개 가능
* 개인키: 본인만 가지고 있어야 함

&ensp;비대칭 암호는 키 분배 문제를 해결하는 데 유리하지만, 대칭 암호보다 상대적으로 느리다.<br/>

&ensp;6. 블록 암호와 스트림 암호<br/>
&ensp;대칭 암호는 다시 블록 암호와 스트림 암호로 나뉜다.<br/>

```txt
Symmetric Ciphers 대칭 암호
├── Block Ciphers 블록 암호
└── Stream Ciphers 스트림 암호
```

&ensp;**블록 암호 Block Cipher** <br/>
&ensp;블록 암호는 데이터를 일정한 크기의 블록 단위로 나누어 암호화하는 방식이다.<br/>
&ensp;예를 들어 데이터를 64비트, 128비트 같은 고정된 크기 단위로 잘라서 각각 암호화한다.<br/>
&ensp;`평문 → [블록1] [블록2] [블록3] → 암호화` <br/>

&ensp;**스트림 암호 Stream Cipher** <br/>
&ensp;스트림 암호는 데이터를 비트 단위 또는 바이트 단위로 연속적으로 암호화하는 방식이다.<br/>
&ensp;`평문 → 1비트/1바이트씩 순서대로 암호화` <br/>
&ensp;블록 암호가 데이터를 묶어서 처리한다면, 스트림 암호는 흐르는 데이터처럼 하나씩 처리한다.<br/>

&ensp;7. 암호화의 역사<br/>
&ensp;고대 암호: 고대에도 중요한 정보를 숨기기 위해 암호가 사용되었다. 대표적인 예가 고대 로마의 줄리어스 시저가 사용한 시저 암호이다.<br/>

&ensp;8. 시저 암호 Caesar Cipher<br/>
&ensp;시저 암호는 평문에 사용되는 알파벳을 일정한 문자 수만큼 이동시켜 다른 문자로 치환하는 암호화 기법이다.<br/>

&ensp;예시<br/>
<p align="center"><img src="/assets/img/database/11주차/11-4.png" width="600"></p>

&ensp;시저 암호의 약점<br/>
&ensp;시저 암호는 구조가 단순해서 깨기 쉽다. 알파벳은 총 26개이므로 가능한 이동 값은 많아야 26개이다. 즉 공격자가 모든 경우를 다 시도해 보면 된다.<br/>
&ensp;이렇게 가능한 모든 키를 하나씩 대입해보는 공격을 **전사 공격** 이라고 한다.<br/>

&ensp;9. 단일 치환 암호<br/>
&ensp;시저 암호는 단일 치환 암호의 한 예시이다.<br/>

&ensp;단일 치환 암호의 정의<br/>
&ensp;단일 치환 암호는 평문을 구성하는 알파벳을 다른 알파벳으로 변환하는 암호화 기법이다. 문자 하나가 항상 정해진 다른 문자 하나로 바꾼다.<br/>

* a → Q
* b → M
* c → Z
* ...

&ensp;이런 식으로 매핑이 정해져 있으면, 평문에 a가 나올 때마다 항상 Q로 바뀐다.<br/>
<p align="center"><img src="/assets/img/database/11주차/11-5.png" width="600"></p>

&ensp;시저 암호와 단일 치환 암호의 관계<br/>
&ensp;시저 암호도 결국 알파벳 하나를 다른 알파벳 하나로 바꾸는 방식이다. 다만 시저 암호는 단순히 일정한 칸 수만큼 이동하는 방식이고 일반적인 단일 치환 암호는 알파벳 간 대응 관계가 더 복잡할 수 있다.<br/>
* 시저 암호: 일정 칸 이동
* 단일 치환 암호: 알파벳을 다른 알파벳으로 일대일 치환

&ensp;단일 치환 암호의 약점<br/>
&ensp;단일 치환 암호는 시저 암호보다 복잡해 보이지만 여전히 약점이 있다.<br/>
&ensp;대표적인 약점은 빈도 분석이다. 사람이 사용하는 언어에는 자주 등장하는 문자가 있다.
예를 들어 영어에서는 e, t, a 같은 문자가 자주 등장한다. 만약 암호문에서 어떤 문자가 유독 자주 등장한다면, 그 문자가 평문의 e일 가능성을 의심할 수 있다. 이런 식으로 문자 등장 빈도를 분석해서 암호를 해독하는 방법이 빈도 분석이다.<br/>

&ensp;10. 전사 공격과 빈도 분석<br/>

&ensp;**전사 공격** <br/>
&ensp;전사 공격은 가능한 모든 키를 하나씩 시도해보는 공격이다. 시저 암호처럼 키의 개수가 적은 경우 전사 공격에 매우 취약하다.<br/>
* 시저 암호의 키 후보: 26개 → 모든 경우를 시도하면 해독 가능

&ensp;**빈도 분석** <br/>
&ensp;빈도 분석은 암호문에 등장하는 문자의 빈도를 조사해서 평문을 추정하는 방식이다. 단일 치환 암호에서는 같은 평문 문자가 항상 같은 암호문 문자로 바뀌기 때문에, 언어의 문자 빈도 특징이 암호문에도 남는다. 따라서 빈도 분석으로 해독이 가능하다.<br/>

&ensp;11. 다중 치환 암호<br/>
&ensp;단일 치환 암호의 약점인 빈도 분석을 극복하기 위해 나온 것이 다중 치환 암호이다.<br/>

&ensp;다중 치환 암호는 평문에 등장하는 문자와 암호문에 등장하는 문자의 빈도를 다르게 만드는 암호 알고리즘이다.<br/>
&ensp;예를 들어 단일 치환 암호에서는 다음과 같았다.<br/>
* 평문 a → 항상 암호문 X

&ensp;하지만 다중 치환 암호에서는 상황에 따라 달라질 수 있다.<br/>
* 첫 번째 a → X
* 두 번째 a → M
* 세 번째 a → P

&ensp;이렇게 하면 암호문에서 특정 문자의 빈도가 평문과 똑같이 드러나지 않는다. -> 빈도 분석이 어려워진다.<br/>

&ensp;대표적인 다중 치환 암호<br/>
1. 비장느르 암호 Vigenere Cipher
2. 에니그마 기계 Enigma Machine

# 대칭 암호

&ensp;1. 암호화 방식의 큰 흐름<br/>
1. 대칭 암호
2. 비대칭 암호
3. 하이브리드 암호

&ensp;1-1. 대칭 암호<br/>
&ensp;대칭 암호는 암호화 키와 복호화 키가 동일한 암호화 기법이다.<br/>
&ensp;`암호화 키 = 복호화 키` <br/>
&ensp;고대 암호부터 1976년 공개키 암호기술이 제안되기 전까지의 대부분의 암호는 대칭 암호 방식이었다. 예전 암호 방식는 대부분 사람과 받는 사람이 같은 비밀키를 공유하고 있어야 하는 구조였다고 보면 된다.<br/>

&ensp;1-2. 비대칭 암호<br/>
&ensp;비대칭 암호는 암호화 키와 복호화 키가 다른 암호화 기법이다.<br/>
&ensp;`암호화 키 ≠ 복호화 키` <br/>
&ensp;1976년 Diffie, Hellman, Merkle이 공개키 암호기술을 제안하면서 등장한 방식이다.<br/>

&ensp;1-3. 하이브리드 암호<br/>
&ensp;하이브리드 암호는 대칭 암호와 비대칭 암호를 함께 사용하는 방식이다.<br/>
&ensp;실제 대부분의 통신보안 프로토콜에서는 하나만 쓰는 것이 아니라 두 방식을 섞어 쓴다.<br/>
* 대칭 암호: 실제 데이터 암호화, 메시지 인증
* 비대칭 암호: 키 교환, 전자서명

&ensp;왜 섞어 쓰냐면, 대칭 암호는 빠르지만 키를 안전하게 공유하기 어렵고, 비대칭 암호는 키 교환에 유리하지만 상대적으로 느리기 때문이다.<br/>
&ensp;그래서 실제 통신에서는 보통 비대칭 암호로 안전하게 키를 교환한 뒤, 그 키를 이용해 대칭 암호로 데이터를 빠르게 암호화한다.<br/>

&ensp;2. 암호 시스템의 구성요소<br/>
&ensp;암호 시스템은 단순히 “암호화한다”로 끝나는 것이 아니라 몇 가지 구성요소로 이루어진다.<br/>
<p align="center"><img src="/assets/img/database/11주차/11-6.png" width="600"></p>

&ensp;2-1. 평문 Plaintext<br/>
&ensp;평문은 암호화되기 전의 원래 데이터이다.<br/>

&ensp;2-2. 암호문 Ciphertext<br/>
&ensp;암호문은 평문이 암호화 과정을 거친 결과이다.<br/>
&ensp;`평문 → 암호화 → 암호문` <br/>
&ensp;암호문은 제3자가 봐도 원래 의미를 알기 어려운 형태여야 한다.<br/>

&ensp;2-3. 암호화 알고리즘 Encryption Algorithm<br/>
&ensp;암호화 알고리즘은 평문을 암호문으로 바꾸는 규칙이다. 예를 들어 시저 암호에서는 “알파벳을 3칸 이동한다”가 암호화 규칙이었다. 현대 암호에서는 DES, AES 같은 알고리즘이 대표적이다.<br/>

&ensp;2-4. 복호화 알고리즘 Decryption Algorithm<br/>
&ensp;복호화 알고리즘은 암호문을 다시 평문으로 복원하는 규칙이다. 대칭 암호에서는 보통 암호화 알고리즘의 역순으로 복호화가 이루어진다.<br/>
* 평문 → 암호화 알고리즘 → 암호문
* 암호문 → 복호화 알고리즘 → 평문

&ensp;2-5. 키 Key<br/>
&ensp;키는 암호화와 복호화에 사용되는 값이다. 대칭 암호에서는 송신자와 수신자가 같은 키를 가지고 있어야 한다.<br/>
&ensp;`송신자 키 = 수신자 키` <br/>

&ensp;3. 암호 시스템의 기호적 표현<br/>
&ensp;3-1. 암호화 식<br/>
&ensp;`C = E_K(P) = E(K, P)` <br/>
&ensp;평문 P를 키 K를 이용하여 암호화 알고리즘 E로 암호화하면 암호문 C가 생성된다.<br/>

&ensp;각 기호는 이렇게 보면 된다.<br/>
* P = Plaintext, 평문
* C = Ciphertext, 암호문
* E = Encryption Algorithm, 암호화 알고리즘
* K = Key, 키

&ensp;암호문 = 암호화 알고리즘(키, 평문)<br/>

&ensp;3-2. 복호화 식<br/>
&ensp;`P = D_K(C) = D(K, C)` <br/>
&ensp;암호문 C를 키 K를 이용하여 복호화 알고리즘 D로 복호화하면 평문 P를 얻는다.<br/>

* D = Decryption Algorithm, 복호화 알고리즘
* K = Key, 키
* C = Ciphertext, 암호문
* P = Plaintext, 평문

&ensp;평문 = 복호화 알고리즘(키, 암호문)<br/>

&ensp;4. 대칭 암호화의 정의<br/>
&ensp;대칭 암호화는 암호화와 복호화에 동일한 비밀키를 사용하는 암호화 방식이다.<br/>
&ensp;`암호화 키 = 복호화 키` <br/>

&ensp;대칭 암호화의 다양한 명칭<br/>
* 대칭(키) 암호화
* 관용 암호화 (Conventional Encryption)
* 비밀키 암호화 (Secret-Key Encryption)
* 단일키 암호화 (Single-Key Encryption)

&ensp;5. 대칭 암호화 과정<br/>
&ensp;대칭 암호화의 흐름은 다음과 같다.<br/>
```txt
송신자 앨리스
↓
평문 입력
↓
공유 비밀키 사용
↓
암호 알고리즘으로 암호화
↓
암호문 전송
↓
수신자 밥
↓
공유 비밀키 사용
↓
복호 알고리즘으로 복호화
↓
평문 출력
```

&ensp;5-1. 송신자 입장<br/>
<p align="center"><img src="/assets/img/database/11주차/11-7.png" width="600"></p>

&ensp;송신자 앨리스는 평문을 가지고 있다.<br/>
&ensp;`x = 평문` <br/>
&ensp;앨리스는 밥과 공유하고 있는 비밀키 K를 사용해서 평문 x를 암호화한다.<br/>
&ensp;`y = E_K(x)` <br/>
&ensp;이렇게 만들어진 y가 암호문이다.<br/>

&ensp;5-2. 전송 과정<br/>
&ensp;암호문 y는 인터넷 같은 안전하지 않은 채널을 통해 전송될 수 있다. 여기서 중요한 점은 공격자가 암호문 y를 훔쳐볼 수 있다는 것이다. 하지만 암호문은 키가 없으면 원래 내영을 알기 어렵다. 그래서 암호문 자체는 노출되더라도 키 K는 노출되면 안 된다.<br/>

&ensp;5-3. 수신자 입장<br/>
&ensp;수신자 밥은 앨리스와 같은 비밀키 K를 가지고 있다. 밥은 받은 암호문 y를 같은 K로 복호화한다.<br/>
&ensp;`x = D_K(y)` <br/>
&ensp;그러면 원래 평문 x를 얻을 수 있다.<br/>

&ensp;6. 대칭 암호화 수식<br/>
&ensp;암호화 식<br/>
&ensp;`Y = E_K(X)` <br/>
&ensp;`평문 X를 키 K로 암호화하여 암호문 Y를 만든다.` <br/>

&ensp;복호화 식<br/>
&ensp;`X = D_K(Y)` <br/>
&ensp;`암호문 Y를 키 K로 복호화하여 평문 X를 복원한다.` <br/>
* X = 평문 Plaintext
* Y = 암호문 Ciphertext
* K = 키 Key
* E = 암호화 함수 Encryption
* D = 복호화 함수 Decryption

&ensp;7. 키공간 Key Space<br/>
&ensp;키의 집합을 키공간이라고 표현한다.<br/>
&ensp;`키의 집합 {K1, K2, ..., Kn} = 키공간 Key Space` <br/>
&ensp;어떤 암호 시스템에서 사용할 수 있는 모든 가능한 키들의 집합이다.<br/>
&ensp;예를 들어 가능한 키가 다음처럼 있다면, `K1, K2, K3, K4` . 이 전체 집합이 키공간이다. 키공간이 작으면 공격자가 모든 키를 하나씩 시도해볼 수 있다. 이런 공격이 **전사공격** 이다.<br/>
&ensp;따라서 안전한 암호 시스템에서는 키공간이 충분히 커야 한다.<br/>

&ensp;8. 대칭 암호화의 핵심 문제: 키 공유<br/>
&ensp;대칭 암호화의 가장 큰 문제는 비밀키를 어떻게 안전하게 공유할 것인가이다.<br/>
&ensp;`앨리스와 밥은 암호화된 메시지를 주고받기 전에, 먼저 안전한 전송 채널을 통해 비밀키를 서로 공유해야 한다.` <br/>

&ensp;왜 키 공유가 문제일까?<br/>
&ensp;대칭 암호에서는 앨리스와 밥이 같은 키 K를 가지고 있어야 한다. 그런데 이 키를 인터넷처럼 안전하지 않은 채널로 보내면 공격자가 가로챌 수 있다. `앨리스 → 인터넷 → 밥` <br/>
&ensp;인터넷 중간에 공격자가 있다면 키를 훔쳐볼 수 있다.<br/>
&ensp;키가 공격자에게 노출되면 공격자는 암호문을 복호화할 수 있다. 대칭 암호의 보안은 키의 비밀성에 크게 의존한다.<br/>
<p align="center"><img src="/assets/img/database/11주차/11-8.png" width="600"></p>

&ensp;대칭 암호의 딜레마<br/>
&ensp;대칭 암호는 데이터를 빠르게 암호화할 수 있지만 그 전에 반드시 같은 키를 공유해야 한다. 그런데 키를 공유하려면 안전한 채널이 필요하다.<br/>
* 암호화하려면 키가 필요함
* 키를 공유하려면 안전한 채널이 필요함
* 안전한 채널을 만들려면 또 보안 기술이 필요함

&ensp;9. 대칭 암호화의 장점과 단점<br/>
&ensp;장점<br/>
* 대칭 암호화는 일반적으로 속도가 빠르다. -> 실제 데이터 자체를 암호화할 때 많이 사용된다.

&ensp;단점<br/>
* 키 분배 문제: 송신자와 수신자가 같은 비밀키를 가져야 하는데 이 키를 안전하게 전달하는 것이 어렵다. 또한 통신 상대가 많아질수록 관리해야 하는 키의 수가 많아진다.

## 대칭 암호화 알고리즘

&ensp;1. 대칭 암호화 알고리즘의 종류<br/>
1. DES
2. Triple-DES
3. AES

&ensp;대칭 암호화 알고리즘은 모두 암호화와 복호화에 같은 비밀키를 사용하는 방식이다. 차이는 블록 크기, 키 길이, 보안성, 현재 사용 여부에 있다.<br/>

```txt
DES
↓
키 길이가 짧아 전사 공격에 취약해짐
↓
Triple-DES 등장
↓
DES를 3번 적용해 보안성 강화
↓
하지만 더 새로운 표준 필요
↓
AES 등장
↓
현재 가장 널리 사용되는 대칭 암호 표준
```

&ensp;2. DES<br/>
&ensp;2-1. DES의 의미<br/>
&ensp;DES는 `Data Encryption Standard`의 약자이다. DES는 1977년에 미국 연방 정보처리 표준 규격인 FIPS로 채택된 대칭 암호 알고리즘이다.<br/>
&ensp;DES는 오래된 알고리즘이지만, 그만큼 많이 연구된 대표적인 대칭 암호 알고리즘이다.<br/>

&ensp;3. DES 알고리즘 구조<br/>
&ensp;DES는 블록 암호이다. 블록 암호는 데이터를 일정한 크기의 블록으로 나누어 암호화하는 방식이다. DES에서는 평문을 64비트 블록으로 나눈다. 그리고 각 블록을 56비트 키를 사용하여 암호문으로 만든다.<br/>
* 평문 블록 크기: 64비트
* 암호문 블록 크기: 64비트
* 키 길이: 56비트

&ensp;평문을 64비트의 블록으로 나누고, 각 블록을 56비트의 키를 사용해 암호문을 생성한다.<br/>

&ensp;3-1. DES의 처리 흐름<br/>
<p align="center"><img src="/assets/img/database/11주차/11-9.png" width="600"></p>

```txt
64비트 평문 입력
↓
Initial Permutation
↓
Encryption Round 1
↓
Encryption Round 2
↓
...
↓
Encryption Round 16
↓
Final Permutation
↓
64비트 암호문 출력
```

&ensp;동일한 연산을 수행하는 16라운드를 이용한다. DES는 한 번에 끝나는 단순한 암호화가 아니라 같은 형태의 연산을 여러 번 반복한다.<br/>

&ensp;3-2. 라운드와 서브키<br/>
&ensp;DES는 전체 키 하나만 그대로 계속 사용하는 것이 아니라, 메인 키에서 각 라운드에 사용할 서브키를 만들어 사용한다.<br/>

```txt
메인 키 K
↓
서브키 K1, K2, ..., K16
```

&ensp;각 라운드에서는 서로 다른 서브키가 사용된다.<br/>
```txt
Round 1 → K1 사용
Round 2 → K2 사용
...
Round 16 → K16 사용
```

&ensp;이렇게 여러 라운드와 서브키를 사용하는 이유는 암호문을 더 복잡하게 만들기 위해서이다.<br/>

&ensp;4. DES의 특징 정리<br/>
1. 64비트 크기의 블록 단위로 암호화를 수행한다.
2. 56비트 크기의 키를 이용한다.
3. 동일한 연산을 수행하는 16라운드를 이용한다.
4. 메인 키에서 유도되는 서로 다른 서브키가 각 라운드에서 사용된다.

&ensp;5. DES가 현재 안전하지 않은 이유<br/>
&ensp;DES는 과거에는 표준으로 사용되었지만, 현재는 안전하지 않다고 간주된다. 가장 큰 이유는 **키 길이가 56비트로 짧기 때문** 이다.<br/>
&ensp;키 길이가 짧다는 말은 가능한 키의 개수가 상대적으로 적다는 뜻이다. 그러면 공격자가 가능한 키를 모두 하나씩 시도하는 **전사 공격** 으로 해독할 수 있다.<br/>
&ensp;`전사 공격 = 가능한 모든 키를 하나씩 대입해보는 공격` <br/>
&ensp;시간이 지나면서 컴퓨터 성능이 좋아졌고, DES는 현실적인 시간 안에 깨질 수 있는 암호가 되었다.<br/>
&ensp;그래서 현재 DES는 단독으로 사용하지 않는다.<br/>

&ensp;6. DES의 대안 알고리즘<br/>

| 알고리즘           | I/O 비트 |            키 길이 | 비고                     |
| -------------- | -----: | --------------: | ---------------------- |
| AES / Rijndael |    128 | 128 / 192 / 256 | DES 대체, 전세계적으로 사용되는 표준 |
| Triple DES     |     64 |         112 효과적 | 보수적인 선택                |
| Mars           |    128 | 128 / 192 / 256 | AES 최종 후보              |
| RC6            |    128 | 128 / 192 / 256 | AES 최종 후보              |
| Serpent        |    128 | 128 / 192 / 256 | AES 최종 후보              |
| Twofish        |    128 | 128 / 192 / 256 | AES 최종 후보              |
| IDEA           |     64 |             128 | 특허가 걸려있음               |

&ensp;7. Triple-DES<br/>
&ensp;7-1. Triple-DES가 등장한 이유<br/>
&ensp;Triple-DES, 또는 3DES는 DES의 짧은 키 길이 문제를 보완하기 위해 등장했다. DES는 56비트 키를 사용하기 때문에 전사 공격으로 현실적인 시간 내에 해독될 수 있다. 그래서 DES를 한 번만 적용하지 않고, **세 번 겹쳐서 적용하는 방식** 이 만들어졌다.<br/>

&ensp;7-2. Triple-DES의 키 길이<br/>
&ensp;Triple-DES는 키 길이를 확장한다.(`키 길이를 112/168비트로 확장`) <br/>

&ensp;7-3. DES-EDE3 암호화 과정<br/>
&ensp;Triple-DES의 암호화 방식 = DES-EDE3<br/>
* E = Encryption, 암호화
* D = Decryption, 복호화
* E = Encryption, 암호화

&ensp;암호화 과정<br/>
```txt
평문
↓ K1로 암호화
암호화
↓ K2로 복호화
복호화
↓ K3로 암호화
암호화
↓
암호문
```

<p align="center"><img src="/assets/img/database/11주차/11-10.png" width="600"></p>

&ensp;`암호문 = E_K3(D_K2(E_K1(평문)))` <br/>
&ensp;“왜 암호화하는데 중간에 복호화가 들어가?”라고 헷갈릴 수 있다. 중간에 복호화가 들어가는 이유는 기존 DES와의 호환성을 유지하면서 보안성을 높이기 위해서이다.br/>

&ensp;8. Triple-DES의 키 구성<br/>
&ensp;`K1, K2, K3` <br/>

&ensp;8-1. K1, K2, K3가 모두 다른 경우<br/>
&ensp;세 키가 모두 다르면 다음과 같다.<br/>
&ensp;`56 + 56 + 56 = 168비트` <br/>

&ensp;`K1, K2, K3가 다른 경우: 168비트` <br/>

&ensp;8-2. K1과 K3가 같은 경우<br/>
&ensp;K1과 K3가 같으면 실제로는 서로 다른 키가 두 개만 사용된다.<br/>
```txt
K1 = K3
K2는 다름
```

&ensp;그러면 키 길이는 다음과 같다.<br/>
&ensp;`56 + 56 = 112비트` <br/>

&ensp;이 방식을 DES-EDE2이라고 설명<br/>

&ensp;9. Triple-DES 복호화 과정<br/>
&ensp;`복호화: K3 복호화 → K2 암호화 → K1 복호화` <br/>

<p align="center"><img src="/assets/img/database/11주차/11-11.png" width="600"></p>

```txt
암호문
↓ K3로 복호화
복호화
↓ K2로 암호화
암호화
↓ K1로 복호화
복호화
↓
평문
```

&ensp;10. Triple-DES 핵심 정리<br/>
* Triple-DES는 DES의 짧은 키 길이 문제를 보완하기 위해 등장한 알고리즘이다.
* DES를 3중으로 적용하며, 키 길이는 112비트 또는 168비트로 확장된다.
* 암호화는 암호화-복호화-암호화 순서로 진행되고,
* 복호화는 복호화-암호화-복호화 순서로 진행된다.

&ensp;11. AES<br/>
&ensp;AES는 Advanced Encryption Standard의 약자이다.<br/>
&ensp;AES는 DES를 대신한 새로운 표준 대칭 암호 알고리즘이다.<br/>
* DES를 대신한 새로운 표준 대칭 암호 알고리즘
* 현재 가장 널리 사용되는 대칭 암호
* AES의 후보로 제안된 다수의 대칭 암호 알고리즘 중 Rijndael 선정

&ensp;12. AES 알고리즘 구조<br/>
<p align="center"><img src="/assets/img/database/11주차/11-12.png" width="600"></p>

&ensp;AES도 DES처럼 블록 암호이다. 하지만 DES와 비교했을 때 블록 크기와 키 길이가 다르다. AES는 평문을 128비트 블록으로 나눈다. 그리고 AES 알고리즘과 키를 통해 128비트 암호문을 생성한다.<br/>
* 평문 블록 크기: 128비트
* 암호문 블록 크기: 128비트
* 키 길이: 128 / 192 / 256비트

&ensp;13. AES의 키 길이와 라운드 수<br/>

|  키 길이 | 라운드 수 |
| ----: | ----: |
| 128비트 | 10라운드 |
| 192비트 | 12라운드 |
| 256비트 | 14라운드 |

&ensp;키 길이가 길수록 가능한 키의 개수가 많아진다. 그래서 보안성은 높아진다. 하지만 라운드 수도 늘어나므로 암호화 시간이 길어진다.<br/>

&ensp;14. DES, Triple-DES, AES 비교<br/>

| 구분    | DES        | Triple-DES          | AES                 |
| ----- | ---------- | ------------------- | ------------------- |
| 블록 크기 | 64비트       | 64비트                | 128비트               |
| 키 길이  | 56비트       | 112/168비트           | 128/192/256비트       |
| 방식    | DES 1회 적용  | DES 3회 적용           | Rijndael 기반 표준 알고리즘 |
| 보안성   | 현재 안전하지 않음 | DES보다 안전            | 현재 널리 사용            |
| 현재 사용 | 단독 사용 X    | 사용 가능하지만 AES가 더 표준적 | 가장 널리 사용            |

# 비대칭 공개키 암호화

&ensp;1. 대칭 암호와 비대칭 암호 비교<br/>
* 대칭 암호화 → 암호화/복호화에 사용되는 키가 동일함
* 비대칭 암호화 → 암호화/복호화에 사용되는 키가 서로 다름

&ensp;앞에서 배운 AES, 3DES는 대표적인 대칭 암호 알고리즘이다. AES와 3DES는 안전하고 빠르기 때문에 널리 사용된다. 하지만 대칭 암호에는 큰 문제가 있다. -> 키 분배 문제<br/>

&ensp;2. 대칭 암호의 단점: 키 분배 문제<br/>

&ensp;2-1. 키 분배 문제란?<br/>
&ensp;대칭 암호에서는 송신자와 수신자가 같은 비밀키를 가지고 있어야 한다.<br/>
&ensp;`송신자 키 = 수신자 키` <br/>
&ensp;같은 키를 써야 한다면, 그 키를 처음에 어떻게 안전하게 전달할 것인가? <- 키 분배 문제<br/>

&ensp;2-2. 왜 문제가 되는가?<br/>
&ensp;예를 들어 앨리스가 밥에게 암호화된 메시지를 보내고 싶다고 하자.<br/>
&ensp;대칭 암호를 사용하려면 앨리스와 밥은 먼저 같은 비밀키를 공유해야 한다.<br/>
* 앨리스 ↔ 밥
* 공유 비밀키 K 필요

&ensp;그런데 이 비밀키 K를 인터넷으로 보내면 공격자가 중간에서 훔쳐볼 수 있다.<br/>
&ensp;비밀키가 공격자에게 노출되면, 공격자는 암호문을 복호화할 수 있다. 그러면 암호화를 한 의미가 사라진다.<br/>
&ensp;따라서 대칭 암호에서 비밀키는 반드시 안전하게 전달되어야 한다.<br/>

&ensp;2-3. 키 분배 문제의 해결 방법<br/>
1. 키 사전 공유에 의한 해결
2. 키 배포 센터 KDC에 의한 해결
3. Diffie-Hellman 키 교환
4. 공개키 암호에 의한 해결

&ensp;3. 대칭 암호의 또 다른 문제: 관리해야 하는 키의 수<br/>
&ensp;대칭 암호는 사용자 수가 많아지면 관리해야 하는 키의 수가 급격히 증가한다.<br/>
* `총 필요한 키 수 = n(n - 1) / 2`
* `각 사용자가 보관해야 하는 키 수 = n - 1`

&ensp;4. 비대칭 공개키 암호화의 기본 원리<br/>
&ensp;비대칭 암호화의 핵심 원리는 **키를 나누는 것** 이다.<br/>
&ensp;대칭 암호에서는 하나의 키를 같이 썼다<br/>
* 대칭 암호
* K 하나만 사용

&ensp;하지만 비대칭 암호에서는 키가 두 개로 나뉜다.<br/>
* 공개키 Public Key
* 개인키 Private Key

&ensp;하나의 키 쌍이 만들어진다.<br/>
&ensp;`키 쌍 Key Pair = 공개키 + 개인키` <br/>

&ensp;5. 공개키와 개인키<br/>
&ensp;5-1. 공개키 Public Key<br/>
&ensp;공개키는 말 그대로 공개해도 되는 키이다.<br/>
&ensp;다른 사람들이 이 키를 사용해서 나에게 보낼 메시지를 암호화할 수 있다.<br/>

&ensp;5-2. 개인키 Private Key<br/>
&ensp;개인키는 본인만 가지고 있어야 하는 키이다.<br/>
&ensp;공개키로 암호화된 암호문은 그 공개키와 쌍이 되는 개인키로만 복호화할 수 있다.<br/>
* 공개키: 누구나 사용할 수 있는 자물쇠
* 개인키: 나만 가지고 있는 열쇠

&ensp;6. 비대칭 암호화의 특성<br/>
1. 암호화 키와 복호화 키가 분리된다.
2. 송신자는 암호화 키를 사용해 메시지를 암호화한다.
3. 수신자는 복호화 키를 사용해 암호문을 복호화한다.
4. 공개키와 개인키는 한 쌍이다.
5. 공개키로 암호화한 암호문은 그 공개키와 쌍이 되는 개인키가 아니면 복호화할 수 없다.

&ensp;7. 공개키 암호 시스템의 분류<br/>
1. 암호화/복호화 Encryption/Decryption
2. 디지털 서명 Digital Signature
3. 키 분배 Key Distribution

&ensp;7-1. 암호화/복호화<br/>
&ensp;암호화/복호화 목적에서는 데이터를 기밀하게 전달하는 것이 핵심이다. 예를 들어 밥이 앨리스에게 비밀 메시지를 보내고 싶다면 밥은 앨리스의 공개키로 메시지를 암호화한다.<br/>
&ensp;그러면 그 메시지는 앨리스의 개인키로만 복호화할 수 있다.<br/>
* 밥 → 앨리스에게 메시지 전송

* 밥: 앨리스의 공개키로 암호화
* 앨리스: 자신의 개인키로 복호화

<p align="center"><img src="/assets/img/database/11주차/11-13.png" width="600"></p>

&ensp;수신자만 읽을 수 있게 만드는 방식이다.<br/>

&ensp;흐름<br/>
```txt
송신자 밥
↓
평문 준비
↓
수신자 앨리스의 공개키 사용
↓
암호 알고리즘 RSA로 암호화
↓
암호문 전송
↓
수신자 앨리스
↓
앨리스의 개인키 사용
↓
복호 알고리즘으로 복호화
↓
평문 복원
```

&ensp;수신자의 공개키로 암호화한다.<br/>

&ensp;7-2. 디지털 서명<br/>
&ensp;디지털 서명은 메시지를 보낸 사람이 진짜 누구인지 확인하기 위한 용도이다. 암호화/복호화에서는 보통 수신자의 공개키를 사용했다. 하지만 디지털 서명에서는 반대로 송신자의 개인키가 중요하다. 예를 들어 밥이 자신의 개인키로 서명하면, 다른 사람들은 밥의 공개키로 그 서명이 진짜 밥의 것인지 확인할 수 있다.<br/>
* 밥: 자신의 개인키로 서명
* 다른 사람들: 밥의 공개키로 검증

<p align="center"><img src="/assets/img/database/11주차/11-14.png" width="600"></p>

&ensp;흐름<br/>
```txt
송신자 밥
↓
자신의 개인키 사용
↓
서명 생성
↓
메시지와 서명 전송
↓
수신자 앨리스
↓
밥의 공개키 사용
↓
서명 검증
```

* 전자서명 생성: 송신자의 개인키
* 전자서명 검증: 송신자의 공개키

&ensp;7-3. 키 분배<br/>
&ensp;비대칭 암호는 대칭 암호의 키를 안전하게 전달하는 데에도 사용된다.<br/>
&ensp;대칭 암호는 빠르지만 키 공유가 어렵다. 비대칭 암호는 느리지만 키를 안전하게 전달하는 데 유리하다.<br/>
&ensp;그래서 실제로 다음처럼 사용한다.<br/>
1. 비대칭 암호로 대칭키, 즉 세션키를 안전하게 전달한다.
2. 이후 실제 데이터는 빠른 대칭 암호로 암호화한다.

<p align="center"><img src="/assets/img/database/11주차/11-15.png" width="600"></p>

* KB(pub) = 밥의 공개키
* KB(pri) = 밥의 개인키
* K = 세션키
* C = 밥의 공개키로 암호화된 세션키
* E = 암호화
* D = 복호화

&ensp;8. 비대칭 공개키 암호화 알고리즘<br/>
1. RSA 알고리즘
2. Diffie-Hellman 알고리즘
3. 디지털 서명 표준 DSS
4. 타원곡선 암호 ECC

&ensp;비대칭 암호 알고리즘별 용도<br/>

| 알고리즘           | 암호/복호 | 디지털 서명 | 키 교환 |
| -------------- | ----- | ------ | ---- |
| RSA            | Yes   | Yes    | Yes  |
| Diffie-Hellman | No    | No     | Yes  |
| DSS            | No    | Yes    | No   |
| 타원곡선 ECC       | Yes   | Yes    | Yes  |

&ensp;9. RSA 알고리즘<br/>
&ensp;9-1. RSA의 등장<br/>
&ensp;RSA는 1977년에 Ronald Rivest, Adi Shamir, Leonard Adleman이 제안한 비대칭 암호시스템이다. RSA라는 이름도 세 사람의 이름 앞글자에서 나왔다.<br/>
* Rivest Shamir Adleman → RSA

&ensp;9-2. RSA 키 쌍<br/>
&ensp;RSA에서는 공개키와 개인키가 다음과 같은 형태로 표현된다.<br/>
* 공개키: 수 E와 수 N
* 개인키: 수 D와 수 N

&ensp;N은 공개키와 개인키 양쪽에 함께 들어간다.<br/>
* 공개키 = (E, N)
* 개인키 = (D, N)

&ensp;9-3. RSA 암호화 식<br/>
&ensp;암호문 = $(평문)^E$ mod N <br/>
&ensp;평문을 E제곱해서 N으로 나눈 나머지를 암호문으로 사용한다.<br/>

&ensp;9-4. RSA 복호화 식<br/>
&ensp;평문 = $(암호문)^D$ mod N<br/>
&ensp;암호문을 D제곱해서 N으로 나눈 나머지를 구하면 원래 평문이 된다.<br/>

<p align="center"><img src="/assets/img/database/11주차/11-16.png" width="600"></p>

&ensp;10. 타원곡선 암호 ECC<br/>
&ensp;ECC의 의미<br/>
&ensp;ECC는 Elliptic-Curve Cryptography의 약자이다.<br/>

&ensp;ECC의 특징<br/>
* 최근 주목받고 있는 공개키 암호 알고리즘
* RSA에 비해 작은 사이즈의 키로 높은 성능을 내는 것이 특징

&ensp;ECC는 RSA보다 더 작은 키를 사용해도 비슷하거나 높은 보안성을 낼 수 있다.<br/>

&ensp;대칭 암호와 비대칭 암호의 핵심 차이<br/>

| 구분        | 대칭 암호      | 비대칭 암호                        |
| --------- | ---------- | ----------------------------- |
| 키 구조      | 하나의 비밀키    | 공개키 + 개인키                     |
| 암호화/복호화 키 | 동일         | 서로 다름                         |
| 속도        | 빠름         | 상대적으로 느림                      |
| 대표 알고리즘   | AES, 3DES  | RSA, Diffie-Hellman, DSS, ECC |
| 주요 문제/특징  | 키 분배 문제    | 키 분배 문제 해결에 유리                |
| 사용 예      | 실제 데이터 암호화 | 키 교환, 전자서명, 인증                |

# 데이터베이스 암호화 방식

&ensp;1. 데이터 암호화 방식의 전체 분류<br/>
&ensp;데이터베이스 암호화 방식을 크게 DB 서버 내부 방식과 DB 서버 외부 방식으로 나눈다.<br/>
<p align="center"><img src="/assets/img/database/11주차/11-17.png" width="600"></p>

&ensp;각 방식의 차이는 다음 두 가지 기준으로 보면 된다.<br/>
1. 암·복호화 모듈이 어디에 있는가?
2. 암·복호화 요청을 누가 하는가?

&ensp;2. DB 서버 내부 암호화 방식<br/>
1. DB 서버 암호화
2. DBMS 자체 암호화
3. DBMS 암호화 기능 호출

&ensp;3. DB 서버 암호화<br/>
&ensp;3-1. DB 서버 암호화의 개념<br/>
&ensp;DB 서버 암호화는 암·복호화 모듈이 DB 서버에 설치되고, DBMS에서 플러그인으로 연결된 암·복호화 모듈을 호출하는 방식이다.<br/>
&ensp;`DB 서버 암호화 = 암·복호화 모듈이 DB 서버에 설치됨 = DBMS가 플러그인 방식으로 암·복호화 모듈을 호출함`<br/>

&ensp;흐름<br/>
```css
응용 프로그램
↓
DB 서버에 요청
↓
DBMS가 플러그인 형태의 암·복호화 모듈 호출
↓
암호화 또는 복호화 수행
↓
암호화 데이터 저장 또는 평문 데이터 반환
```

&ensp;응용 프로그램이 직접 암호화 로직을 처리하는 것이 아니라, DB 서버 내부에서 암·복호화가 이루어진다.<br/>

<p align="center"><img src="/assets/img/database/11주차/11-18.png" width="600"></p>

&ensp;3-2. DB 서버 암호화의 장점<br/>
&ensp;첫 번째 장점은 응용 프로그램 수정이 거의 필요하지 않다는 점이다.<br/>
&ensp;기존 프로그램 로직을 크게 바꾸지 않아도 적용할 수 있기 때문에 구현이 비교적 쉽다.<br/>
* 응용 프로그램 수정이 거의 필요하지 않음
* 구현 용이성이 뛰어남
* 어플리케이션 서버 성능에 영향을 주지 않음

&ensp;3-3. DB 서버 암호화의 단점<br/>
&ensp;단점은 DB 서버에 부하가 발생할 수 있다는 점이다. DBMS가 암, 복호화 모듈을 플러그인으로 호출할 때 추가 작업이 발생한다. 그래서 DB 서버 성능이 저하 될 수 있다. 또한 기존 DB 스키마에 대응하는 뷰를 생성하거나 암호화할 테이블을 추가하는 작업이 필요할 수 있다.<br/>
* DB 서버에 추가 부하 발생 가능
* 기존 DB 스키마와 대응하는 View 생성 필요
* 암호화할 테이블 추가 작업 필요
* 성능이 중요한 환경에서는 BMT 필요

&ensp;3-4. DB 서버 암호화 주요 특성<br/>

| 분류         | 특성                |
| ---------- | ----------------- |
| 암·복호화 모듈   | DB 서버             |
| 암·복호화 요청   | DB 서버             |
| DB 서버의 부하  | 있음                |
| 색인 검색      | 가능                |
| 배치 처리      | 가능                |
| 응용 프로그램 수정 | 기본적으로 수정 없이 적용 가능 |
| DB 스키마 수정  | 필요                |

&ensp;DB 서버 암호화는 응용 프로그램 수정은 적지만, DB 서버 부하와 DB 스키마 수정이 발생할 수 있다.<br/>

&ensp;4. DBMS 자체 암호화<br/>
&ensp;4-1. DBMS 자체 암호화의 개념<br/>

<p align="center"><img src="/assets/img/database/11주차/11-19.png" width="600"></p>

&ensp;DBMS 자체 암호화는 DBMS에 내장되어 있는 암호화 기능을 이용하는 방식이다.<br/>
&ensp;대표적으로 TDE가 있다.<br/>

&ensp;4-2. DBMS 자체 암호화의 특징<br/>
&ensp;DBMS 자체 암호화는 DBMS 커널 수준에서 처리된다. 그래서 기존 응용 프로그램을 거의 수정하지 않아도 되고, DB 스키마 변경도 거의 필요하지 않다.<br/>
&ensp;`DBMS 자체 암호화 = DBMS 내부 기능으로 암·복호화 처리 = 커널 수준에서 처리 = 기존 응용 프로그램 수정 거의 없음 = DB 스키마 변경 거의 없음` <br/>

&ensp;4-3. DBMS 자체 암호화의 장점<br/>
1. 기존 응용 프로그램 수정이나 DB 스키마 변경이 거의 필요하지 않음
2. DBMS 엔진에 최적화된 성능 제공

&ensp;4-4. DBMS 자체 암호화의 단점<br/>
&ensp;단점은 비용이 많이 들 수 있다.<br/>

&ensp;4-5. DBMS 자체 암호화 주요 특성<br/>

| 분류         | 특성         |
| ---------- | ---------- |
| 암·복호화 모듈   | DB 서버      |
| 암·복호화 요청   | DBMS 엔진    |
| DB 서버의 부하  | 있음         |
| 색인 검색      | 가능         |
| 배치 처리      | 가능         |
| 응용 프로그램 수정 | 필요하지 않음    |
| DB 스키마 수정  | 거의 필요하지 않음 |
| 단점         | 많은 비용 소요   |

&ensp;DBMS 자체 암호화는 DBMS에 내장된 TDE와 같은 암호화 기능을 사용하여 DBMS 엔진 수준에서 암·복호화를 처리하는 방식이다.<br/>
&ensp;응용 프로그램 수정과 DB 스키마 변경이 거의 필요하지 않지만, 비용이 많이 소요될 수 있다.<br/>

&ensp;5. DBMS 암호화 기능 호출<br/>
&ensp;5-1. DBMS 암호화 기능 호출의 개념<br/>

<p align="center"><img src="/assets/img/database/11주차/11-20.png" width="600"></p>

&ensp;DBMS 암호화 기능 호출은 DBMS가 자체적으로 암, 복호화 기능을 수행하는 API를 제공하고, 응용 프로그램에서 해당 함수를 호출하는 방식이다. 암호화 기능 자체는 DBMS가 제공하지만, 그 기능을 언제 호출할지는 응용 프로그램이 결정한다.<br/>
&ensp;`DBMS 암호화 기능 호출 = DBMS가 암·복호화 API 제공 = 응용 프로그램이 해당 API를 호출` <br/>

&ensp;흐름<br/>
```txt
응용 프로그램
↓
DBMS 암호화 API 호출
↓
DBMS 내부 암·복호화 기능 수행
↓
암호화 데이터 저장 또는 복호화 데이터 반환
```
                                                   
&ensp;5-2. DBMS 자체 암호화와의 차이<br/>
&ensp;DBMS 자체 암호화와 DBMS 암호화 기능 호출은 둘 다 DBMS의 암호화 기능을 사용한다. 하지만 차이는 누가 요청하느냐이다.<br/>
* DBMS 자체 암호화 → DBMS 엔진이 자동 또는 내부적으로 처리
* DBMS 암호화 기능 호출 → 응용 프로그램이 DBMS의 암·복호화 API를 직접 호출

&ensp;5-3. DBMS 암호화 기능 호출의 단점<br/>
* 암·복호화 API를 사용하는 응용 프로그램 수정 필요
* DB 서버에 추가적인 부하 발생 가능

&ensp;5-4. DBMS 암호화 기능 호출 주요 특성<br/>

| 분류         | 특성       |
| ---------- | -------- |
| 암·복호화 모듈   | DB 서버    |
| 암·복호화 요청   | 응용 프로그램  |
| DB 서버의 부하  | 있음       |
| 색인 검색      | 불가능      |
| 배치 처리      | 가능       |
| 응용 프로그램 수정 | 수정 필요    |
| DB 스키마 수정  | 일부 수정 필요 |


&ensp;색인 검색이 불가능하다.<br/>

&ensp;6. DB 서버 내부 방식 3가지 비교<br/>

| 구분          | DB 서버 암호화 | DBMS 자체 암호화 | DBMS 암호화 기능 호출 |
| ----------- | --------- | ----------- | -------------- |
| 암·복호화 모듈 위치 | DB 서버     | DB 서버       | DB 서버          |
| 암·복호화 요청    | DB 서버     | DBMS 엔진     | 응용 프로그램        |
| DB 서버 부하    | 있음        | 있음          | 있음             |
| 색인 검색       | 가능        | 가능          | 불가능            |
| 배치 처리       | 가능        | 가능          | 가능             |
| 응용 프로그램 수정  | 거의 없음     | 필요 없음       | 필요             |
| DB 스키마 수정   | 필요        | 거의 필요 없음    | 일부 필요          |
| 특징          | 플러그인 방식   | TDE, 커널 방식  | API 호출 방식      |


&ensp;7. DB 서버 외부 암호화 방식<br/>
1. 응용 프로그램 자체 암호화
2. 운영체제 암호화

&ensp;8. 응용 프로그램 자체 암호화<br/>
&ensp;8-1. 응용 프로그램 자체 암호화의 개념<br/>
<p align="center"><img src="/assets/img/database/11주차/11-21.png" width="600"></p>

&ensp;응용 프로그램 자체 암호화는 암, 복호화 모듈이 API 라이브러리 형태로 각 어플리케이션 서버에 설치되고 응용프로그램에서 해당 모듈을 호출하는 방식이다.<br/>
&ensp;`응용 프로그램 자체 암호화 = 암·복호화 모듈이 어플리케이션 서버에 설치됨 = 응용 프로그램이 암·복호화 모듈을 호출함` <br/>

&ensp;흐름<br/>
```txt
응용 프로그램
↓
어플리케이션 서버의 암·복호화 모듈 호출
↓
개인정보 등 민감 데이터 암호화
↓
암호화된 데이터가 DB 서버로 전송
↓
DB에는 암호화 데이터 저장
```

&ensp;8-2. 응용 프로그램 자체 암호화의 장점<br/>
&ensp;DB 서버에는 영향을 주지 않는다.<br/>
&ensp;암·복호화를 어플리케이션 서버에서 처리하기 때문에 DB 서버의 암호화 부하는 줄어든다. 또한 어플리케이션 서버와 DB 서버 간 통신 구간에서도 암호화된 개인정보가 전송된다.<br/>
* DB 서버에는 영향을 주지 않음
* DB 서버 부하 없음
* 어플리케이션 서버와 DB 서버 간 통신에서 암호화된 개인정보 전송 보장

&ensp;8-3. 응용 프로그램 자체 암호화의 단점<br/>
&ensp;단점은 응용프로그램 수정이 필요하다는 것이다. 암호화 모듈은 직접 호출해야 하므로 기존 코드 전체 또는 일부를 수정해야 한다. 그리고 암·복호화 처리를 어플리케이션 서버에서 하기 때문에 어플리케이션 서버에 추가 부하가 발생한다.<br/>
* 어플리케이션 서버에 추가 부하 발생
* 구축 시 응용 프로그램 전체 또는 일부 수정 필요

&ensp;8-4. 응용 프로그램 자체 암호화 주요 특성<br/>

| 분류         | 특성                         |
| ---------- | -------------------------- |
| 암·복호화 모듈   | 어플리케이션 서버                  |
| 암·복호화 요청   | 응용 프로그램                    |
| DB 서버의 부하  | 없음                         |
| 색인 검색      | 일치검색 가능, 별도 색인 테이블 생성 시 가능 |
| 배치 처리      | 가능                         |
| 응용 프로그램 수정 | 필요함                        |
| DB 스키마 수정  | 거의 필요하지 않음                 |

&ensp;암호화하면 데이터 길이가 바뀔 수 있기 때문에 속성 타입이나 길이 변경이 필요할 수 있다.<br/>

&ensp;대량 OLTP 환경 → 여러 어플리케이션 서버에서 암·복호화 처리 → 효율적일 수 있음<br/>

&ensp;9. 운영체제 암호화<br/>
&ensp;9-1. 운영체제 암호화의 개념<br/>
<p align="center"><img src="/assets/img/database/11주차/11-22.png" width="600"></p>

&ensp;운영체제 암호화는 OS에서 발생하는 입출력 시스템 호출을 이용하여 암, 복호화를 수행하는 방식이다. DBMS나 응용 프로그램이 직접 컬럼 단위로 암호화하는 것이 아니라, DB 파일 자체를 암호화하는 방식이다.<br/>
&ensp;`운영체제 암호화 = OS의 입출력 시스템 호출을 이용한 암·복호화 = DB 파일 자체를 암호화` <br/>
&ensp;흐름<br/>

```txt
DBMS가 DB 파일에 접근
↓
운영체제 또는 파일 서버의 암·복호화 모듈 동작
↓
DB 파일 자체 암호화 또는 복호화
```

&ensp;9-2. 운영체제 암호화의 장점<br/>
* 응용 프로그램 수정 필요 없음
* DB 스키마 수정 필요 없음

&ensp;9-3. 운영체제 암호화의 단점<br/>
* DB 파일 전체 암호화로 인해 파일 서버 및 DB 서버에 추가 부하 발생

&ensp;9-4. 운영체제 암호화 주요 특성<br/>

| 분류         | 특성             |
| ---------- | -------------- |
| 암·복호화 모듈   | 파일 서버 또는 DB 서버 |
| 암·복호화 요청   | 운영체제           |
| DB 서버의 부하  | 있음             |
| 색인 검색      | 가능             |
| 배치 처리      | 가능             |
| 응용 프로그램 수정 | 필요하지 않음        |
| DB 스키마 수정  | 필요하지 않음        |

&ensp;운영체제 암호화는 OS의 입출력 시스템 호출을 이용하여 DB 파일 자체를 암호화하는 방식이다. 응용 프로그램과 DB 스키마 수정이 필요하지 않지만, 파일 서버 및 DB 서버에 추가 부하가 발생할 수 있다.<br/>

&ensp;10. DB 서버 외부 방식 2가지 비교<br/>

| 구분          | 응용 프로그램 자체 암호화        | 운영체제 암호화       |
| ----------- | --------------------- | -------------- |
| 암·복호화 모듈 위치 | 어플리케이션 서버             | 파일 서버 또는 DB 서버 |
| 암·복호화 요청    | 응용 프로그램               | 운영체제           |
| DB 서버 부하    | 없음                    | 있음             |
| 색인 검색       | 일치검색 가능, 별도 색인 테이블 필요 | 가능             |
| 배치 처리       | 가능                    | 가능             |
| 응용 프로그램 수정  | 필요함                   | 필요하지 않음        |
| DB 스키마 수정   | 거의 필요 없음              | 필요하지 않음        |
| 특징          | DB 전송 전 암호화           | DB 파일 자체 암호화   |

&ensp;11. 혼합 방식<br/>
* DB 서버 암호화
* DBMS 자체 암호화
* DBMS 암호화 기능 호출
* 응용 프로그램 자체 암호화
* 운영체제 암호화

&ensp;→ 두 가지 이상의 방식을 혼합하여 구현 가능<br/>

&ensp;혼합 방식의 장점은 어플리케이션 서버와 DB 서버의 성능과 보안성을 극대화할 수 있다는 점이다.<br/>
&ensp;하지만 단점은 구축 시 많은 비용이 든다.<br/>

# 데이터베이스 암호화 방식 선택 시 고려사항

&ensp;1. 왜 암호화 방식 선택이 중요한가?<br/>
&ensp;위 방식들은 모두 데이터를 암호화한다는 목적은 같지만 실제로 암호화가 수행되는 위치와 성능에 미치는 영향이 다르다. 예를 들어 어떤 방식은 DB 서버에 부하가 많이 걸리고, 어떤 방식은 어플리케이션 서버에 부하가 걸린다. 또 어떤 방식은 응용 프로그램 수정이 거의 필요 없지만 비용이 많이 들 수 있고, 어떤 방식은 비용은 줄일 수 있지만 개발자가 직접 코드를 많이 수정해야 할 수 있다.<br/>
&ensp;그래서 암호화 방식은 단순히 “보안이 좋아 보이는 것”을 고르는 게 아니라, 현재 시스템 환경에 맞게 선택해야 한다.<br/>

&ensp;2. 데이터베이스 암호화 방식 선택 기준<br/>
1. 일반적 고려사항
2. 기술적 고려사항

&ensp;2-1. 일반적 고려사항<br/>
&ensp;일반적 고려사항은 시스템 운영, 비용, 보안 인증, 유지보수와 관련된 부분이다.<br/>
* 구현 용이성, 구축 비용, 기술지원 및 유지보수 여부
  - 암호화 방식은 현재 운영 중이거나 앞으로 개발할 정보처리시스템과 DBMS의 목적 및 환경에 맞게 쉽게 구현 가능한 방식을 선택해야 한다.
* 암호화 성능 및 안전성
  - 암호화는 보안을 위한 기능이지만, 시스템 입장에서는 추가 연산이다.
  - DB 암호화에서는 다음을 고려해야 한다.
    + 안전한 암호화 알고리즘 사용
    + 암호키 관리
    + 암호키 접근 통제
    + 허가된 인력만 접근 가능하도록 보안 적용
* 공공기관의 경우 국가정보원 인증 또는 검증 여부
  - 국가정보원의 DB 암호화 제품의 핵심 보안 요구사항을 준수한 인증제품 선택
  - 검증필 암호 모듈이 탑재된 솔루션인지 확인


&ensp;2-2. 기술적 고려사항<br/>
&ensp;기술적 고려사항은 실제 시스템 구조와 성능에 직접 영향을 주는 부분이다.<br/>
* 암·복호화 위치
  - 암·복호화 위치는 어플리케이션 서버, DB 서버, 파일 서버 중 어디에서 암호화가 이루어지는지를 말한다. -> 암·복호화 모듈의 위치와 요청 위치에 따라 어플리케이션 서버 또는 DB 서버의 성능에 영향을 미칠 수 있다.
* 색인검색 가능 여부
* 배치처리 가능 여부
