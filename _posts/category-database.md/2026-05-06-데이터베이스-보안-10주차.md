# 강제적 접근제어, MAC

&ensp;MAC은 Mandatory Access Control, 즉 강제적 접근제어다.<br/>
&ensp;말 그대로 사용자가 마음대로 권한을 주고받는 방식이 아니라 **중앙 관리자 또는 시스템이 미리 정해둔 보안 등급과 규칙에 따라 접근을 강제로 통제하는 방식** 이다.<br/>
&ensp;예를 들어 어떤 문서가 Top Secret 이고 어떤 사용자가 Confidential 등급이라면 그 사용자가 보고 싶다고 해서 볼 수 있는 것이 아니다. 시스템이 등급을 비교해서 접근 가능 여부를 결정한다.<br/>

&ensp;1. 접근제어 모델 전체 흐름<br/>

| 모델   | 기준               | 핵심                 |
| ---- | ---------------- | ------------------ |
| DAC  | 사용자 신분, 접근 규칙    | 소유자 중심 권한 부여       |
| MAC  | 주체와 객체의 보안 분류 등급 | 등급 기반 강제 통제        |
| RBAC | 역할, 직무           | 역할에 따른 권한 부여       |
| ABAC | 속성               | 사용자/객체/환경 속성 기반 통제 |

&ensp;2. MAC의 정확한 개념<br/>
> 주체와 객체에 보안 등급을 부여하고, 미리 정해진 보안 정책에 따라 접근 가능 여부를 판단하는 접근제어 방식이다.

&ensp;규칙 기반 접근제어이다.<br/>
&ensp;주체: 접근을 시도하는 대상<br/>
&ensp;객체: 접근의 대상이 되는 자원<br/>

&ensp;MAC에서는 주체와 객체 모두에게 보안 등급을 부여한다.<br/>

&ensp;3. MAC의 특징<br/>
&ensp;1) 보안 등급 기반이다<br/>
&ensp;MAC은 사용자의 이름이나 소유자 권한보다 보안 등급을 중요하게 본다.<br/>
&ensp;예를 들어 사용자가 누구인지보다, `이 사용자의 보안 등급이 무엇인가?, 이 객체의 보안 등급이 무엇인가?` 를 비교한다.<br/>

&ensp;2) 중앙 집중식 관리 방식이다<br/>
&ensp;MAC에서는 일반 사용자가 임의로 권한을 바꾸기 어렵다.<br/>
&ensp;권한, 보안 등급, 규칙은 보통 관리자만 수정 가능하다. 이 점이 DAC와 가장 큰 차이다. DAC에서는 파일 소유자가 다른 사용자에게 권한을 줄 수 있지만, MAC에서는 개인이 마음대로 권한을 줄 수 없다.<br/>

&ensp;3) 접근 규칙 수가 상대적으로 적다<br/>
&ensp;DAC에서는 사용자와 객체가 많아질수록 권한 관계가 복잡해진다. 예를 들어 사용자 100명, 파일 100개가 있으면 각각에 대해 권한을 따져야 할 수 있다.<br/>
&ensp;하지만 MAC은 등급 중심이다.<br/>
&ensp;그래서 주체와 객체 수가 많아져도 접근 규칙은 비교적 단순하게 유지된다.<br/>

&ensp;4) 기밀성이 중요한 조직에서 사용된다<br/>
&ensp;“낮은 보안 수준의 사용자가 높은 보안 수준의 정보에 접근하지 못하게 하는 것”이 중요할 때 사용된다.<br/>

&ensp;4. MAC의 장점과 단점<br/>
&ensp;장점<br/>
&ensp;MAC의 가장 큰 장점은 보안성이 높다는 점이다.<br/>
&ensp;왜냐하면 사용자가 임의로 권한을 줄 수 없고, 중앙 관리자와 시스템 규칙에 의해 강제적으로 통제되기 때문이다. 즉, DAC처럼 “소유자가 실수로 다른 사람에게 권한을 줘서 정보가 유출되는 문제”를 줄일 수 있다.<br/>

&ensp;단점<br/>
* 모든 접근에 대한 보안 등급 정의, 보안 정책 확인으로 개발, 구현의 어려움
* 매우 제한적인 사용자 기능
* 많은 관리적 부담 요구
* 상업적인 환경에서 적용 힘듦

&ensp;6. MAC의 대표 모델<br/>
&ensp;MAC의 대표 모델은 두 가지다.<br/>
1. Bell-LaPadula, BLP 모델
2. Biba 모델

| 모델      | 핵심 목적  |
| ------- | ------ |
| BLP 모델  | 기밀성 보호 |
| Biba 모델 | 무결성 보호 |


## Bell-LaPadula, BLP 모델

&ensp;BLP 모델은 정보의 기밀성 보호를 목적으로 만들어진 최초의 수학적 모델이다.<br/>
&ensp;중요한 정보가 낮은 보안 수준으로 흘러 내려가서 유출되는 것을 막는 모델이다. (= 높은 등급의 비밀 정보가 낮은 등급 사용자에게 새어나가지 않게 막는 모델)<br/>

&ensp;BLP 모델의 핵심 규칙<br/>
1. No Read Up
2. No Write Down

&ensp;1) 단순 보안 속성: No Read Up<br/>
> 낮은 등급의 주체는 높은 등급의 객체를 읽을 수 없다는 뜻이다.

&ensp;주체 등급 ≥ 객체 등급이면 읽기 가능<br/>
&ensp;주체 등급 < 객체 등급이면 읽기 불가능<br/>
* 상위 등급 → 하위 등급 읽기 가능
* 하위 등급 → 상위 등급 읽기 불가능

<p align="center"><img src="/assets/img/database/10주차/10-3.png" width="600"></p>

&ensp;2) 성형 보안 속성: No Write Down<br/>
> 높은 등급의 주체는 낮은 등급의 객체에 쓸 수 없다는 뜻이다.

* 주체 등급 ≤ 객체 등급이면 쓰기 가능
* 주체 등급 > 객체 등급이면 쓰기 불가능

&ensp;높은 등급의 사용자가 낮은 등급 문서에 정보를 쓰면, 높은 등급 정보가 낮은 등급으로 유출될 수 있기 때문이다.<br/>

&ensp;예를 들어 교수가 Top Secret이고 강의자료가 Confidential이라고 하자. 교수가 강의자료에 성적 정보를 적어버리면, 학생도 볼 수 있는 낮은 등급 자료에 중요한 정보가 유출될 수 있다.그래서 BLP는 높은 등급 사용자가 낮은 등급 객체에 쓰는 것을 금지한다.<br/>

<p align="center"><img src="/assets/img/database/10주차/10-4.png" width="600"></p>

&ensp;BLP 모델 예제<br/>
&ensp;BLP 모델을 데이터베이스 보안 수업에 적용했을 때<br/>

&ensp;BLP에서 읽기 권한<br/>
&ensp;BLP 읽기 규칙은 No Read Up이다.<br/>
* 자기 등급보다 높은 객체는 읽을 수 없다.
* 자기 등급 이하 객체는 읽을 수 있다.

| 주체 | 읽을 수 있는 객체    |
| -- | ------------- |
| 교수 | 성적, 출석표, 강의자료 |
| 조교 | 출석표, 강의자료     |
| 학생 | 강의자료          |

&ensp;학생은 성적과 출석표를 읽을 수 없다. 왜냐하면 학생의 등급은 Confidential이고, 성적은 Top Secret, 출석표는 Secret이기 때문이다.<br/>

&ensp;BLP에서 쓰기 권한<br/>
&ensp;BLP 쓰기 규칙은 No Write Down이다.<br/>
* 자기 등급보다 낮은 객체에는 쓸 수 없다.
* 자기 등급 이상 객체에는 쓸 수 있다.

| 주체 | 쓸 수 있는 객체     |
| -- | ------------- |
| 교수 | 성적            |
| 조교 | 성적, 출석표       |
| 학생 | 성적, 출석표, 강의자료 |

&ensp;여기서 이상한 점이 보인다. 학생이 성적에 쓸 수 있다.<br/>
&ensp;BLP는 기밀성 보호가 목적이기 때문에, 낮은 등급 사용자가 높은 등급 객체에 쓰는 것은 정보 유출 관점에서는 문제가 덜하다고 본다. 하지만 현실적으로는 학생이 성적을 수정하면 안 된다. 그래서 BLP는 학교 성적 시스템 적용에 적합하지 않은 모델이다.<br/>

&ensp;BLP 모델의 한계<br/>
&ensp;장점<br/>
* 권한 없는 사용자의 정보 접근을 차단한다.
* 기밀성을 보장한다.

&ensp;단점<br/>
* 낮은 등급 주체가 높은 등급 객체를 변경할 수 있다.
* 정보의 무결성을 보장하지 못한다.

&ensp;즉, BLP는 “읽기”를 통한 정보 유출 방지는 잘하지만, “쓰기”를 통한 데이터 변조 방지는 약하다. 그래서 등장한 모델이 Biba 모델이다.<br/>

## Biba 모델

&ensp;Biba 모델은 정보의 무결성 보호를 목적으로 만들어진 모델이다.<br/>
&ensp;여기서 무결성은, 정보가 함부로 변경되지 않고 정확하게 유지되는 성질<br/>
&ensp;예를 들어 성적 데이터, 금융 거래 데이터, 회계 데이터는 기밀성도 중요하지만 무엇보다 틀리게 변경되면 안 된다. 그래서 Biba 모델은 정보의 불법적인 변경을 막는 데 초점을 둔다.<br/>

&ensp;Biba 모델의 핵심 규칙<br/>
1. No Read Down
2. No Write Up

&ensp;BLP가 기밀성을 위해 정보가 아래로 새는 것을 막는 모델이라면, Biba는 무결성을 위해 낮은 신뢰도의 정보가 위로 올라가 중요한 정보를 오염시키는 것을 막는 모델이다.<br/>

&ensp;1) 단순 무결성 속성: No Read Down<br/>
> 높은 등급의 주체는 낮은 등급의 객체를 읽을 수 없다는 뜻이다.

* 주체 등급 ≤ 객체 등급이면 읽기 가능
* 주체 등급 > 객체 등급이면 읽기 불가능

&ensp;왜 높은 등급 사용자가 낮은 등급 자료를 읽으면 안 될까?<br/>
&ensp;낮은 등급 자료는 신뢰성이 낮을 수 있다. 높은 등급 사용자가 낮은 등급 자료를 참고해서 중요한 판단을 하면, 높은 무결성의 정보가 오염될 수 있다.<br/>
&ensp;예를 들어 교수가 학생이 작성한 검증 안 된 강의자료를 읽고 성적 처리에 반영하면 문제가 생길 수 있다. 그래서 Biba는 높은 무결성 주체가 낮은 무결성 객체를 읽는 것을 제한한다.<br/>

<p align="center"><img src="/assets/img/database/10주차/10-6.png" width="600"></p>

&ensp;2) 성형 무결성 속성: No Write Up<br/>
> 낮은 등급의 주체는 높은 등급의 객체에 쓸 수 없다는 뜻이다.

* 주체 등급 ≥ 객체 등급이면 쓰기 가능
* 주체 등급 < 객체 등급이면 쓰기 불가능

&ensp;낮은 등급 사용자가 높은 등급 객체를 오염시키지 못하게 막는 것이다.<br/>
<p align="center"><img src="/assets/img/database/10주차/10-7.png" width="600"></p>

&ensp;Biba 모델 예제<br/>
<p align="center"><img src="/assets/img/database/10주차/10-5.png" width="600"></p>

&ensp;Biba에서 쓰기 권한<br/>
&ensp;Biba 쓰기 규칙은 No Write Up이다.<br/>
&ensp;`자기 등급보다 높은 객체에는 쓸 수 없다. 자기 등급 이하 객체에는 쓸 수 있다.` <br/>

| 주체 | 쓸 수 있는 객체     |
| -- | ------------- |
| 교수 | 성적, 출석표, 강의자료 |
| 조교 | 출석표, 강의자료     |
| 학생 | 강의자료          |

&ensp;이제 학생은 성적에 쓸 수 없다. 즉, Biba는 성적 데이터의 무결성을 보호하는 데 적합하다.<br/>

&ensp;Biba에서 읽기 권한<br/>
&ensp;Biba 읽기 규칙은 No Read Down이다.<br/>
&ensp;`자기 등급보다 낮은 객체는 읽을 수 없다. 자기 등급 이상 객체는 읽을 수 있다.` <br/>

| 주체 | 읽을 수 있는 객체    |
| -- | ------------- |
| 교수 | 성적            |
| 조교 | 성적, 출석표       |
| 학생 | 성적, 출석표, 강의자료 |

&ensp;여기서 문제가 생긴다. 학생이 성적을 읽을 수 있다. 즉, Biba는 무결성 보호에는 강하지만, 기밀성 보호에는 문제가 생길 수 있다.<br/>

&ensp;BLP와 Biba 비교<br/>
| 구분     | BLP 모델                  | Biba 모델                    |
| ------ | ----------------------- | -------------------------- |
| 목적     | 기밀성 보호                  | 무결성 보호                     |
| 막으려는 것 | 정보 유출                   | 정보 변조                      |
| 읽기 규칙  | No Read Up              | No Read Down               |
| 쓰기 규칙  | No Write Down           | No Write Up                |
| 정보 흐름  | 높은 정보가 낮은 곳으로 유출되는 것 방지 | 낮은 신뢰 정보가 높은 곳을 오염시키는 것 방지 |
| 대표 예시  | 군사 기밀 시스템               | 금융, 성적, 회계 시스템             |
| 한계     | 무결성 보장 약함               | 기밀성 보장 약함                  |

# 역할기반 접근제어, RBAC

&ensp;1. RBAC의 핵심 개념<br/>
&ensp;RBAC는 Role-Based Access Control, 즉 역할기반 접근제어다.<br/>
&ensp;RBAC는 사용자에게 직접 권한을 부여하는 것이 아니라, 사용자에게 역할을 부여하고, 그 역할이 가진 권한을 통해 자원 접근을 제어하는 방식이다.<br/>
&ensp;`사용자 → 역할 → 권한 → 자원 접근` <br/>

&ensp;2. 기존 접근제어와의 차이<br/>
&ensp;DAC, MAC 방식<br/>
&ensp;기존 방식은 보통 사용자에게 직접 권한을 부여한다.<br/>
```txt
사용자 A → 파일1 읽기 가능
사용자 A → 파일2 쓰기 가능
사용자 B → 파일1 읽기 불가능
사용자 B → 파일3 수정 가능
```

&ensp;이 방식은 사용자가 적을 때는 괜찮다. 그런데 사용자가 많아지고 입사, 퇴사, 부서 이동이 자주 발생하면 관리가 어려워진다. 예를 들어 어떤 직원이 회계팀에서 개발팀으로 이동하면 기존 회계 권한을 빼고 개발 권한을 새로 줘야 한다. 이걸 사용자마다 직접 처리하면 굉장히 번거롭다.<br/>

&ensp;RBAC 방식<br/>
&ensp;RBAC는 사용자에게 직접 권한을 주지 않고 역할을 부여한다.<br/>
```txt
사용자 A → 회계 담당자 역할
회계 담당자 역할 → 회계장부 읽기/쓰기 권한
```

&ensp;사용자가 다른 부서로 이동하면 권한 하나하나를 수정하는 것이 아니라 역할만 바꾸면 된다.<br/>
```txt
사용자 A: 회계 담당자 역할 제거
사용자 A: 개발자 역할 추가
```

&ensp;그래서 RBAC는 사용자 정보가 자주 바뀌는 조직에서 권한 관리가 훨씬 효율적이다.<br/>

&ensp;3. RBAC의 구성요소<br/>
&ensp;RBAC는 네 가지 구성요소를 꼭 알아야 한다.<br/>
* 사용자(User)
* 역할(Role)
* 권한(Permission)
* 자원(Resource)


&ensp;1) 사용자, User<br/>
&ensp;사용자는 특정 자원에 접근하고자 하는 대상이다.<br/>
&ensp;사용자는 사람, 사용자 계정, 사용자 그룹, 응용 프로그램, 프로세스 등도 사용자가 될 수 있다.<br/>
&ensp;쉽게 말하면 권한을 받아서 자원에 접근하려는 대상이다.<br/>

&ensp;2) 역할, Role<br/>
&ensp;역할은 조직 안에서 사용자가 맡는 직무, 책임, 자격을 의미한다.<br/>
&ensp;RBAC에서 가장 중요한 것은 이 역할이다. 사용자는 권한을 직접 받는 것이 아니라 역할을 부여받는다. 그리고 이 역할이 권한을 가진다.<br/>

&ensp;3) 권한, Permission<br/>
&ensp;권한은 자원에 대해 수행할 수 있는 특정 기능이다.<br/>

&ensp;4. RBAC 수행 과정<br/>
1. 역할 생성
2. 역할에 권한 부여
3. 사용자 또는 사용자 그룹에 역할 연결
4. 사용자가 접근 요청
5. 사용자의 역할을 확인
6. 역할에 연결된 권한을 기준으로 접근 허용/거부

<p align="center"><img src="/assets/img/database/10주차/10-8.png" width="600"></p>

&ensp;5. RBAC의 핵심 개념: UA와 PA<br/>
* 사용자 할당(User Assignment, UA)
* 권한 할당(Permission Assignment, PA)

&ensp;사용자 할당, UA<br/>
&ensp;UA는 사용자를 역할에 연결하는 것이다.<br/>

&ensp;권한 할당, PA<br/>
&ensp;PA는 권한을 역할에 연결하는 것이다.<br/>

&ensp;6. RBAC가 등장한 배경<br/>
&ensp;RBAC는 기존 접근제어 방식의 비효율성을 해결하기 위해 등장했다. 기존 방식에서는 사용자마다 권한을 직접 부여했다. 문제는 사용자가 많아질수록 권한 관리가 너무 복잡해진다는 것이다. 예를 들어 회사에 직원이 1,000명 있고, 시스템이 20개 있다고 하자. 각 직원마다 어떤 시스템에 접근할 수 있는지 직접 관리하면 관리자가 계속 권한을 수정해야 한다.<br/>
&ensp;하지만 RBAC에서는 역할 단위로 관리한다.<br/>

&ensp;7. RBAC의 장점<br/>
&ensp;1) 권한 관리가 효율적이다<br/>
&ensp;RBAC의 가장 큰 장점은 권한 관리가 쉽다는 것이다. DAC처럼 객체마다 사용자에게 권한을 직접 주면 계속 권한을 수정해야 한다. 하지만 RBAC는 역할을 기준으로 관리한다.<br/>
* 사용자에게 직접 권한 부여 X
* 사용자에게 역할 부여 O
* 역할에 권한 부여 O

&ensp;그래서 사용자의 직무가 바뀌면 역할만 바꾸면 된다.<br/>

&ensp;2) 조직 구조를 반영하기 쉽다<br/>
&ensp;RBAC의 역할은 조직 내 직무, 책임, 자격을 표현한다.<br/>

&ensp;3) DAC, MAC보다 유연하다<br/>
&ensp;MAC은 보안 등급 중심이라 강력하지만 너무 딱딱하다. DAC은 사용자가 직접 권한을 줄 수 있어 유연하지만 관리가 복잡하고 보안 문제가 생길 수 있다. RBAC는 역할을 기준으로 하기 때문에, 조직의 변화에 따라 비교적 유연하게 권한을 조정할 수 있다.<br/>

&ensp;8. RBAC의 단점: 역할 폭발<br/>
&ensp;RBAC의 대표적인 단점은 역할 폭발(Role Explosion)이다.<br/>
&ensp;역할 폭발: 조직과 시스템이 복잡해지면서 역할의 수가 지나치게 많이 증가하여, 역할 관리가 어려워지는 현상이다.<br/>

&ensp;예를 들어 처음에는 역할이 단순했다.<br/>
```txt
관리자
일반 사용자
```

&ensp;그런데 시간이 지나면서 권한 요구가 세밀해진다.<br/>
```txt
상품 관리자
주문 관리자
배송 관리자
정산 관리자
리뷰 관리자
고객센터 관리자
이벤트 관리자
쿠폰 관리자
```

&ensp;그런데 어떤 사용자가 “상품 관리자는 맞는데 삭제 권한은 없어야 함”이라는 조건이 생긴다. 또 다른 사용자는 “주문 조회는 가능하지만 배송 상태 변경은 불가능해야 함”이라는 조건이 생긴다. 그러면 역할이 계속 쪼개진다.<br/>
```txt
상품 조회 관리자
상품 수정 관리자
상품 삭제 관리자
상품 조회+수정 관리자
상품 조회+삭제 관리자
상품 수정+삭제 관리자
```

&ensp;이렇게 역할이 너무 많아지면 RBAC의 장점이 사라진다.<br/>

&ensp;9. RBAC 예시<br/>
* 사용자 A, 사용자 B, 사용자 C
* 역할: 개발자, 회계사
* 자원: 회계장부

&ensp;회계장부는 회계사 역할을 가진 사용자만 접근해야 한다. 따라서 사용자에게 직접 회계장부 접근 권한을 주는 것이 아니라, `회계사 역할 → 회계장부 접근 권한, 사용자 B → 회계사 역할` 처럼 관리한다. 그러면 사용자 B는 회계장부에 접근 가능하다. 반대로 개발자 역할만 가진 사용자는 회계장부에 접근할 수 없다.<br/>

&ensp;10. RBAC 적용 분야<br/>
&ensp;RBAC는 여러 분야에서 사용된다.<br/>
* 데이터베이스
* 시스템 관리
* 운영체제
* 제품

&ensp;특히 실무에서는 관리자 페이지, 회사 내부 시스템, DB 권한 관리, 클라우드 IAM 같은 곳에서 많이 볼 수 있다.<br/>
&ensp;예를 들어 AWS IAM이나 GitHub Organization 권한도 RBAC와 비슷한 사고방식을 가진다.<br/>

&ensp;11. 기본형 RBAC, Flat/Core RBAC<br/>
&ensp;기본형 RBAC는 가장 기본적인 RBAC 구조다. 핵심 구성요소는 다음과 같다.<br/>
* Users
* Roles
* Permissions
* Sessions
* Objects
* Operations

<p align="center"><img src="/assets/img/database/10주차/10-9.png" width="600"></p>

&ensp;1) Users<br/>
&ensp;사람이나 자율적인 에이전트를 의미한다.<br/>

&ensp;2) Roles<br/>
&ensp;조직과 관련된 직무, 책임, 자격을 나타낸다.<br/>

&ensp;3) Permissions<br/>
&ensp;권한은 특정 객체에 대해 특정 행위를 할 수 있는 특권이다.<br/>
&ensp;`Permission = Object + Operation`<br/>

&ensp;4) Sessions<br/>
&ensp;세션은 사용자가 특정 권한을 사용하기 위해 사용자와 역할을 연결해서 활성화하는 것이다. 조금 어렵게 느껴질 수 있는데, 쉽게 말하면 로그인 후 현재 활성화된 역할 상태라고 생각하면 된다.<br/>
&ensp;예를 들어 한 사용자가 여러 역할을 가질 수 있다. 그런데 매 순간 모든 역할을 다 쓰는 것이 아니라, 특정 세션에서 어떤 역할을 활성화할 수 있다.<br/>

&ensp;12. 기본형 RBAC의 관계<br/>
&ensp;사용자와 역할의 관계: `사용자 U는 역할 R에 배정된다.` <br/>
&ensp;이것이 User Assignment, UA다.<br/>
&ensp;그리고 사용자와 역할은 다대다 관계다. 한 사용자는 여러 역할을 가질 수 있다. 하나의 역할은 여러 사용자에게 배정될 수 있다.<br/>

## 계층형 RBAC, Hierarchical RBAC

&ensp;계층형 RBAC는 기본형 RBAC에 역할 간 계층 구조를 추가한 모델이다.<br/>
&ensp;계층형 RBAC의 핵심<br/>
> 계층 구조상 상위 역할은 하위 역할의 권한을 소유한다.

&ensp;즉, 상위 역할은 자기 권한뿐만 아니라 하위 역할의 권한도 가진다.<br/>
&ensp;예를 들어 역할 계층이 다음과 같다고 하자.<br/>
```txt
Admin
 ↓
Power User
 ↓
User
 ↓
Guest
```

&ensp;그러면 권한 관계는 이렇게 된다.<br/>
```txt
Guest: 기본 조회 권한
User: Guest 권한 + 일반 사용자 권한
Power User: User 권한 + 고급 사용자 권한
Admin: Power User 권한 + 관리자 권한
```

&ensp;즉, Admin은 Guest, User, Power User의 권한까지 모두 포함한다.<br/>

&ensp;1. 계층형 RBAC의 구조<br/>
&ensp;기본형 RBAC 구조에 Role Hierarchy, RH가 추가되어 있다.<br/>
<p align="center"><img src="/assets/img/database/10주차/10-10.png" width="600"></p>

&ensp;기본형 RBAC에는 원래 다음 관계가 있었다.<br/>
```txt
사용자 할당, UA: 사용자 → 역할
권한 할당, PA: 역할 → 권한
세션: 사용자와 역할의 활성화 관계
```

&ensp;계층형 RBAC에서는 여기에 하나가 추가된다.<br/>
&ensp;`역할 계층, RH: 역할 ↔ 역할 사이의 상하 관계` <br/>
&ensp;그래서 계층형 RBAC는 이렇게 이해하면 된다.<br/>
&ensp;`기본형 RBAC + 역할 계층 구조` <br/>

&ensp;2. 계층형 RBAC의 종류<br/>
1. 일반적 계층형 RBAC, GH-RBAC
2. 제한적 계층형 RBAC, LH-RBAC

&ensp;1) 일반적 계층형 RBAC, GH-RBAC<br/>
&ensp;**General Hierarchical RBAC**는 역할 계층에서 **다중 상속**을 허용한다.<br/>
&ensp;다중 상속이란 하나의 역할이 여러 역할의 권한을 물려받을 수 있다는 뜻이다.<br/>
&ensp;예를 들어 어떤 역할이 다음 두 역할의 권한을 동시에 물려받을 수 있다.<br/>
```txt
보안 관리자 권한
시스템 관리자 권한
        ↓
통합 관리자 역할
```

&ensp;Guest Role Set, User Role Set, Power User Role Set, Admin Role Set이 계층적으로 연결되고, 다중 상속이 가능하다.<br/>
&ensp;쉽게 말하면 GH-RBAC는 역할 계층 구조가 더 자유롭다.<br/>
* 여러 상위/하위 역할 관계를 가질 수 있음
* 복잡한 조직 구조 표현 가능

&ensp;2) 제한적 계층형 RBAC, LH-RBAC<br/>
&ensp;**Limited Hierarchical RBAC**는 역할 계층에서 **1단계 직계 상속만 허용**하고, **다중 상속을 금지**한다.<br/>
&ensp;즉, GH-RBAC보다 구조가 제한적이다.<br/>
&ensp;LH-RBAC가 트리 또는 역트리 형태의 계층 구조를 지원한다.<br/>

&ensp;트리 구조<br/>
```css
상위 역할
 ├─ 하위 역할 1
 ├─ 하위 역할 2
 └─ 하위 역할 3
```

&ensp;역트리 구조는 이런 느낌이다.<br/>
```css
하위 역할 1
하위 역할 2
하위 역할 3
 └─ 상위 역할
```

&ensp;핵심은 복잡한 다중 상속을 막고, 더 단순한 계층 구조만 허용한다는 것이다.<br/>

<p align="center"><img src="/assets/img/database/10주차/10-11.png" width="600"></p>

## 제약형 RBAC, Constrained RBAC

&ensp;제약형 RBAC는 계층형 RBAC에 임무분리, SoD를 추가한 모델이다.<br/>
* SSD: 정적 임무분리
* DSD: 동적 임무분리

&ensp;`계층형 RBAC + 임무분리 제약` <br/>
<p align="center"><img src="/assets/img/database/10주차/10-12.png" width="600"></p>

&ensp;임무분리, SoD<br/>
&ensp;임무분리는 Separation of Duty, SoD라고 한다.<br/>
&ensp;목적: 사용자 간의 이해관계 충돌을 막고, 사용자가 자신의 직위나 직책을 벗어나는 행위를 하지 못하게 하는 것<br/>

&ensp;쉽게 말하면, 한 사람이 서로 충돌하는 역할을 동시에 가지거나 동시에 사용하는 것을 막는 것이다.<br/>
&ensp;예를 들어 회사에서 돈을 처리하는 업무를 생각해보자.<br/>
&ensp;결제 요청자, 결제 승인자, 감사자 이 역할을 한 사람이 모두 가지면 위험하다. 왜냐하면 본인이 결제 요청하고, 본인이 승인하고, 본인이 감사를 통과시킬 수 있기 때문이다. 그래서 RBAC에서는 이런 충돌 관계를 제약으로 막는다.<br/>

&ensp;정적 임무분리, SSD<br/>
&ensp;SSD는 Static Separation of Duty, 정적 임무분리다.<br/>
> 동일 사용자에게 정적인 임무분리가 선언된 두 개 이상의 역할에 배정되지 못하게 하는 것.

&ensp;쉽게 말하면, 애초에 충돌하는 역할들을 같은 사용자에게 부여하지 못하게 하는 것이다.<br/>
&ensp;예를 들어 다음 두 역할이 충돌한다고 하자.<br/>
* 결제 요청자
* 결제 승인자

&ensp;SSD가 적용되면 한 사용자는 이 둘을 동시에 배정받을 수 없다.<br/>
&ensp;즉, 역할 배정 단계에서부터 막는다.<br/>

&ensp;SSD의 핵심<br/>
&ensp;`충돌 역할을 동시에 보유 불가` <br/>

&ensp;동적 임무분리, DSD<br/>
&ensp;DSD는 Dynamic Separation of Duty, 동적 임무분리다.<br/>
> 동일 사용자에게 동적인 임무분리가 선언된 두 개 이상의 역할에 배정될 수는 있지만, 동일 사용자가 동시에 이 역할들을 사용할 수 없게 하는 것

&ensp;돌하는 역할을 “가지는 것”은 가능하지만, “동시에 사용하는 것”은 불가능하다.<br/>
&ensp;예를 들어 다음 두 역할이 있다고 하자.<br/>
* 결제 요청자
* 결제 승인자

&ensp;DSD가 적용되면 한 사용자가 두 역할을 모두 배정받을 수는 있다. 하지만 같은 세션에서 두 역할을 동시에 활성화할 수 없다.<br/>

&ensp;DSD의 핵심<br/>
&ensp;`충돌 역할을 동시에 활성화 불가` <br/>

&ensp;SSD와 DSD 비교<br/>
| 구분          | SSD                             | DSD                                             |
| ----------- | ------------------------------- | ----------------------------------------------- |
| 이름          | 정적 임무분리                         | 동적 임무분리                                         |
| 기준          | 역할 배정 단계                        | 역할 사용/세션 단계                                     |
| 충돌 역할 보유    | 불가능                             | 가능                                              |
| 충돌 역할 동시 사용 | 당연히 불가능                         | 불가능                                             |
| 예시          | 한 사용자가 요청자와 승인자 역할을 동시에 배정받지 못함 | 한 사용자가 요청자와 승인자 역할은 가질 수 있지만 같은 세션에서 동시에 사용 못 함 |

## 대칭형 RBAC, Symmetric RBAC

&ensp;대칭형 RBAC는 제한형 RBAC에 권한 배정, PA에 대한 제약조건을 추가한 모델이다.<br/>
&ensp;`제약형 RBAC + 권한-역할 배정 제약조건` <br/>
<p align="center"><img src="/assets/img/database/10주차/10-13.png" width="600"></p>

&ensp;대칭형 RBAC의 특징<br/>
&ensp;대칭형 RBAC는 “어떤 권한을 어떤 역할에 배정할 것인가”를 중요하게 본다.<br/>
&ensp;대칭형 RBAC는 “어떤 권한을 어떤 역할에 배정할 것인가”를 중요하게 본다. 즉 역할을 잘 만드는 것도 중요하지만, 그 역할에 어떤 권한을 넣을지도 매우 중요하다는 뜻이다. 예를 들어 일반 사용자 역할에 관리자 권한이 들어가 있으면 큰 문제가 된다. `일반 사용자 역할 → 회원 삭제 권한` 이건 권한-역할 배정이 잘못된 것이다.<br/>
&ensp;또한 과거에는 적절했던 권한 배정도 시간이 지나면 부적절해질 수 있다. 예를 들어 예전에는 개발자가 운영 DB에 직접 접근해도 됐지만, 조직이 커진 후에는 보안 정책상 금지될 수 있다.<br/>
* 과거: 개발자 → 운영 DB 수정 가능
* 현재: 개발자 → 운영 DB 조회만 가능

&ensp;그래서 대칭형 RBAC는 상황 변화에 따라 권한-역할 배정을 관리하고 제약하는 모델이라고 보면 된다.<br/>

&ensp;RBAC 모델 확장 흐름<br/>
| 모델       | 핵심               |
| -------- | ---------------- |
| 기본형 RBAC | 사용자-역할-권한의 기본 구조 |
| 계층형 RBAC | 역할 간 상하 계층 추가    |
| 제약형 RBAC | 임무분리, SSD/DSD 추가 |
| 대칭형 RBAC | 권한-역할 배정 제약 추가   |

## Ravi S. Sandhu의 RBAC 모델

&ensp;다음 기준으로 RBAC 모델을 구분한다.<br/>
* 계층, Hierarchies
* 제약, Constraints

| 모델    | 계층  | 제약  | 의미            |
| ----- | --- | --- | ------------- |
| RBAC0 | No  | No  | 기본형 RBAC와 동일  |
| RBAC1 | Yes | No  | 계층형 RBAC와 동일  |
| RBAC2 | No  | Yes | 제약이 있는 RBAC   |
| RBAC3 | Yes | Yes | 계층과 제약을 모두 포함 |

# 속성기반 접근제어, ABAC

&ensp;ABAC의 핵심 개념<br/>
&ensp;ABAC는 Attribute-Based Access Control, 즉 속성기반 접근제어다.<br/>
> ABAC는 주체와 객체의 속성, 그리고 환경 조건을 기준으로 접근 가능 여부를 판단하는 접근제어 방식이다.

&ensp;쉽게 말하면, 단순히 “이 사람이 관리자 역할인가?”만 보는 것이 아니라,<br/>
```txt
이 사용자는 누구인가?
어느 부서 소속인가?
어떤 직책인가?
어떤 객체에 접근하려는가?
지금 시간이 언제인가?
접근 장소가 어디인가?
정책 조건을 만족하는가?
```

&ensp;이런 여러 조건을 함께 보고 접근을 허용하거나 거부하는 방식이다.<br/>

&ensp;1. ABAC가 왜 필요한가?<br/>
&ensp;RBAC는 역할 중심이다. `사용자 → 역할 → 권한` <br/>
&ensp;예를 들어 사용자가 의사 역할이면 의료정보에 접근할 수 있게 할 수 있다.<br/>
&ensp;그런데 실제 병원에서는 단순히 “의사면 모두 접근 가능”하면 안 된다. 예를 들어 다음과 같은 조건이 필요할 수 있다.<br/>
```txt
내과 의사인가?
환자 A의 담당의인가?
근무 시간인가?
진료실 A10호에 있는가?
접근하려는 정보가 환자 A의 의료정보인가?
```

&ensp;이런 조건은 단순한 역할만으로는 표현하기 어렵다. 그래서 ABAC는 역할보다 더 세밀한 속성 조건을 사용한다.<br/>

&ensp;2. ABAC의 주요 요소<br/>
* 주체 Subject
* 객체 Object
* 속성 Attribute
* 환경 조건 Environment Condition
* 접근제어 정책 Security Policy

&ensp;1) 주체, Subject<br/>
&ensp;주체는 특정 객체에 접근하고자 하는 대상이다.<br/>
* 사용자
* 사용자 그룹
* 애플리케이션
* 프로세스

&ensp;주체는 “접근을 요청하는 쪽”이라고 생각하면 된다.<br/>

&ensp;2) 객체, Object<br/>
&ensp;객체는 무단 접근으로부터 보호해야 하는 대상이다.<br/>
&ensp;RBAC에서 말한 자원(Resource)과 비슷하다.<br/>
&ensp;예를 들면 다음과 같다.<br/>
* 파일
* 데이터베이스
* 의료정보
* 문서
* 시스템 메뉴
* API
* 환자 기록

&ensp;객체도 속성을 가진다. 이것을 객체 속성, Object Attributes라고 한다.<br/>

&ensp;3) 속성, Attribute<br/>
&ensp;ABAC의 핵심은 바로 속성이다. 속성은 수치나 형태로 표현할 수 있는 유무형의 모든 정보를 말한다.<br/>
&ensp;즉, ABAC는 단순히 “권한 있음/없음”만 보는 것이 아니라, 여러 속성을 조건식처럼 비교한다.<br/>
&ensp;예를 들어 정책이 이렇게 정의될 수 있다.<br/>
```txt
부서가 내과이고,
환자 A의 담당의이고,
현재 시간이 오전 9시부터 오후 6시 사이이고,
장소가 A10호이면,
환자 A의 의료정보를 읽을 수 있다.
```

&ensp;4) 환경 조건, Environment Condition<br/>
&ensp;환경 조건은 주체나 객체 자체의 속성은 아니지만, 접근 판단에 영향을 주는 동적 요소다.<br/>
&ensp;환경 조건은 주체 및 객체와는 독립적인 동적 요소이다.<br/>

&ensp;예를 들어 같은 의사라도 상황에 따라 접근 가능 여부가 달라질 수 있다.<br/>
* 오전 11시, 병원 내부 A10호 → 접근 가능
* 밤 11시, 외부 카페 Wi-Fi → 접근 불가능

&ensp;이게 ABAC의 강점이다.<br/>
&ensp;RBAC는 보통 “의사 역할이면 접근 가능”처럼 정적이다. 하지만 ABAC는 “의사이면서, 담당의이고, 근무 시간이며, 특정 장소에 있을 때만 접근 가능”처럼 동적으로 판단할 수 있다.<br/>

&ensp;ABAC의 동작 방식<br/>
1. 주체가 객체에 접근 요청
2. 접근제어 메커니즘이 정책, 주체 속성, 객체 속성, 환경 조건을 수집
3. 속성들이 정책을 만족하는지 판단
4. 접근 허용 또는 거부 결정
5. 결정 결과를 시행

&ensp;ABAC의 장점<br/>
&ensp;1) 환경 조건을 고려한 세밀한 접근제어 가능<br/>
&ensp;ABAC는 시간, 장소, 요일 같은 동적인 환경 조건을 접근제어에 포함할 수 있다.<br/>
&ensp;예를 들어 RBAC에서는 보통 이렇게 설정한다. `의사 역할 → 의료정보 접근 가능` <br/>
&ensp;하지만 ABAC에서는 이렇게 설정할 수 있다.<br/>
```txt
의사 역할이면서,
환자의 담당의이고,
오전 9시부터 오후 6시 사이이고,
병원 내부에서 접속한 경우에만,
의료정보 접근 가능
```

&ensp;2) 주체와 객체 속성을 통한 세밀한 접근제어 가능<br/>
&ensp;ABAC는 주체의 속성과 객체의 속성을 비교해서 접근 여부를 결정할 수 있다.<br/>
&ensp;의료 분야 예시<br/>
* 특정 환자명 속성을 가진 의료 파일
* 특정 환자 담당의 속성을 가진 의사

&ensp;즉 다음 조건을 만족해야 접근 가능하다.<br/>
* 의사의 담당 환자 = 환자 A
* 의료 파일의 환자명 = 환자 A

&ensp;이렇게 하면 단순히 “의사면 모두 접근 가능”이 아니라, 환자의 담당의만 해당 환자의 의료정보에 접근 가능하게 만들 수 있다.<br/>

&ensp;3) 유연한 접근제어 가능<br/>
&ensp;ABAC는 환경 변화에 따라 접근 조건을 동적으로 바꿀 수 있다. RBAC는 역할 중심이라 동적인 변화에 약하다. 예를 들어 사용자가 관리자 역할이면 접근 가능하고, 아니면 접근 불가능한 식이다. 하지만 ABAC는 다음과 같은 조건을 함께 볼 수 있다.<br/>
* 현재 위치
* 접속 시간
* 기기 상태
* 사용자 소속
* 객체 민감도
* 네트워크 보안 수준

&ensp;그래서 분산 환경이나 빠르게 변화하는 환경에 적응하기 쉽다.<br/>

&ensp;ABAC의 단점<br/>
&ensp;1) 속성 관리가 필요하다<br/>
&ensp;ABAC는 주체와 객체에 대한 속성을 계속 관리해야 한다. 예를 들어 사용자의 부서가 바뀌면 주체 속성을 수정해야 한다.<br/>
&ensp;즉, ABAC는 속성을 정확하고 최신 상태로 유지해야 한다.<br/>

&ensp;2) 판단 과정에서 성능 비용이 발생할 수 있다.<br/>
&ensp;ABAC는 단순히 역할 하나만 보는 것이 아니라 여러 속성과 조건을 평가한다.<br/>
&ensp;그래서 인가 여부를 판단하는 과정에서 성능 비용이 발생할 수 있다.<br/>

&ensp;3) 실제로는 RBAC와 함께 사용되기도 한다.<br/>
* RBAC: 큰 틀의 접근제어
* ABAC: 세부적인 접근제어

&ensp;예를 들어 병원 시스템에서 큰 틀은 RBAC로 나눌 수 있다.<br/>
```txt
의사
간호사
원무과 직원
관리자
```

&ensp;그리고 세부 조건은 ABAC로 처리한다.<br/>
```txt
담당 환자인가?
근무 시간인가?
병원 내부 접속인가?
해당 진료과 소속인가?
```

&ensp;ABAC 예시: 병원 의료정보 접근<br/>
&ensp;병원에서 의사가 환자 A의 의료정보를 토대로 진료를 보려고 하는 상황<br/>

&ensp;RBAC와 ABAC 비교<br/>

| 구분    | RBAC               | ABAC                              |
| ----- | ------------------ | --------------------------------- |
| 기준    | 역할                 | 속성                                |
| 접근 판단 | 사용자가 어떤 역할을 가졌는가   | 주체, 객체, 환경 속성이 정책을 만족하는가          |
| 장점    | 권한 관리가 효율적         | 세밀하고 유연한 접근제어 가능                  |
| 단점    | 동적 환경 조건 반영이 어려움   | 속성 관리와 정책 평가 비용 필요                |
| 예시    | 의사 역할이면 의료정보 접근 가능 | 담당의이고, 근무 시간이고, A10호에 있을 때만 접근 가능 |

&ensp;RBAC는 역할을 기준으로 접근을 제어하여 관리가 효율적이지만 세밀한 조건 표현이 어렵고, ABAC는 주체·객체·환경 속성을 기준으로 접근을 제어하여 더 세밀하고 유연하지만 속성 관리와 정책 평가 비용이 필요하다.<br/>
