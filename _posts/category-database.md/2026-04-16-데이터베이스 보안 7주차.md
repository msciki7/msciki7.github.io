# 사용자 인증

&ensp;사용자 인증은 **특정 시스템에 접속을 시도하는 사용자가 올바른 사용자인지 판단하는 과정이다.** <br/>
&ensp;즉 사용자 신분을 검증하여 적합한 사용자인지 확인하는 것이다.<br/>

&ensp;인증 요소의 4가지 분류<br/>
&ensp;1. 지식 기반 인증<br/>
&ensp;사용자가 알고 있는 것으로 인증하는 방식이다.<br/>
* 예: 패스워드, CAPTCHA

&ensp;가장 대표적인 예가 아이디 + 패스워드 로그인이다. 장점은 구현이 단순하다는 점이지만 단점은 유출되기 쉽고 유출되면 다른 공격에도 악용될 수 있다는 점이다.<br/>

&ensp;2. 소유 기반 인증<br/>
&ensp;사용자가 가지고 있는 것으로 인증하는 방식이다.<br/>
* 예: 토큰, 열쇠, 보안카드, OTP 발생기

&ensp;비밀번호를 아는 것만으로는 부족하고, 실제로 그 장치를 가지고 있어야 인증이 가능하다.<br/>

&ensp;3. 존재 기반 인증<br/>
&ensp;사용자의 생체적 특징을 이용한 인증 방식이다.<br/>
* 예: 지문, 홍채, 얼굴 인식

&ensp;장점은 분실·도난 위험이 적고 복제가 어렵다는 점이다. 하지만 인식 정확도 문제가 있을 수 있고, 한 번 복제되면 재발행이 불가능하다는 치명적인 단점도 있다. 비밀번호는 바꿀 수 있지만, 지문은 바꾸기 어렵기 때문이다.<br/>

&ensp;4. 행위 기반 인증<br/>
&ensp;사용자의 행동 패턴이나 습관을 바탕으로 인증하는 방식이다.<br/>
* 예: 걸음걸이, 서명 방식, 키보드 입력 속도, 마우스 움직임

&ensp;존재 기반 인증과 비슷하지만, 차이는 신체 그 자체가 아니라 행동 특성에 초점을 둔다는 점이다. 다만 신체 상태나 주변 환경에 따라 결과가 달라질 수 있다.<br/>

# 다중 인증 요소 기반 인증 방식(MFA)

&ensp;다중 인증(Multi-Factor Authentication)은 두 개 이상의 인증 요소를 함께 사용하는 방식이다.<br/>
&ensp;예를 들어<br/>
&ensp;아이디/패스워드(지식 기반) +  인증서 또는 OTP(소유 기반) 를 함께 사용하는 방식이다.<br/>

&ensp;중요한 이유<br/>
&ensp;비밀번호만 사용하는 경우, 비밀번호가 털리면 바로 침입당할 수 있다. 하지만 여기에 OTP나 인증서가 추가되면, 공격자는 비밀번호 + 물리적 장치를 동시에 확보해야 한다. 즉, 공격 난이도가 크게 올라간다.<br/>

# DBMS 사용자 인증

&ensp;DBMS도 기본적으로는 **패스워드 기반 인증**을 사용한다. 즉, 데이터베이스에 로그인할 때 사용자 계정과 비밀번호를 확인한다.<br/>
&ensp;그런데 일부 DBMS는 여기서 더 나아가 다음 기능도 지원한다.<br/>

&ensp;1. OS 인증<br/>
&ensp;일부 DBMS(예: Oracle, MSSQL)는 운영체제 사용자 정보를 활용하여 사용자를 인증할 수 있다. 즉, 운영체제에서 이미 인증된 사용자를 DBMS에서도 신뢰하는 방식이다.<br/>

&ensp;2. 네트워크 인증<br/>
&ensp;Oracle, MySQL은 네트워크 인증도 지원한다. 사용자가 네트워크 서버에 접속할 때 인증 정보가 유효한지 검증하는 방식이며, 대표적인 예로 Kerberos 인증이 있다.<br/>

&ensp;3. 토큰 기반 관점<br/>
&ensp;사용자가 어떤 서비스나 리소스를 사용할 수 있는지 정보가 담긴 토큰을 이용하는 관점. 이는 단순 로그인만이 아니라, 이후 권한 확인까지 연결되는 개념으로 보면 이해가 쉽다.<br/>

# 사용자 권한 부여 및 관리

&ensp;인증이 끝났다고 해서 모든 작업을 다 할 수 있는 것은 아니다. 그다음 필요한 것이 권한 부여이다.<br/>

&ensp;1. 시스템 권한 부여<br/>
&ensp;DBA가 시스템 관리 작업을 위한 권한을 사용자에게 부여하는 것이다.<br/>
&ensp;예를 들면,<br/>
* B사용자 생성
* 테이블 생성
* 데이터베이스 관리 기능 수행

&ensp;같이 시스템 차원의 작업 권한이 여기에 해당한다.<br/>

&ensp;2. 객체 권한 부여<br/>
&ensp;테이블, 뷰 같은 특정 객체에 대해 객체 소유자가 사용 권한을 부여하는 것이다.<br/>
&ensp;예를 들면,<br/>
* 특정 테이블 조회 가능
* 특정 컬럼 수정 가능
* 특정 뷰만 접근 가능

&ensp;이런 식의 세부 권한이다.<br/>

# 사용자 관리에서 DBA의 역할

&ensp;데이터베이스 관리자의 주요 업무로는 다음이 제시된다.<br/>
* 권한 회수(REVOKE)
* 권한 부여 진행 상황 모니터링
* 사용자 계정 및 패스워드 관리
* 권한 부여 기간 설정을 통한 무분별한 권한 남용 방지

&ensp;여기서 중요한 포인트는, 보안은 “권한을 주는 것”보다 오히려 불필요한 권한을 안 주는 것이 더 중요하다는 점이다.<br/>

&ensp;모니터링 수단<br/>
* Oracle: 데이터 사전 뷰(Data Dictionary View)
* MySQL: 정보 스키마(Information Schema)

&ensp;즉, 현재 누가 어떤 권한을 갖고 있는지, 어떤 객체가 존재하는지, 어떤 설정이 적용되어 있는지 추적할 수 있어야 한다.<br/>

# 데이터베이스 접근제어 관리

&ensp;접근제어는 “데이터를 누구에게, 어디까지 보여줄 것인가”의 문제다.<br/>
* 뷰 기반 접근통제
* SQL문 기반 접근통제

# 뷰(View) 기반 접근통제

&ensp;뷰: 뷰는 하나 이상의 테이블에서 일부 컬럼들을 모아 만든 가상의 테이블이다.
실제 데이터를 새로 저장하는 물리적 테이블이 아니라, 필요한 정보만 보여주기 위한 논리적 창이라고 생각하면 된다.<br/>

&ensp;왜 보안에 유리한가?<br/>
* 뷰는 이미 생성된 다른 뷰를 기반으로도 만들 수 있다.
* 객체 소유자는 뷰를 이용하여 접근통제를 수행할 수 있다.
* 물리적 테이블의 특정 컬럼만 노출할 수 있으므로 민감한 데이터 노출을 막을 수 있다.

&ensp;예시<br/>
<p align="center"><img src="/assets/img/database/7주차/7-2.png" width="600"></p>

&ensp;응용 프로그래머가 아이디 중복 체크 기능만 만들면 된다면, 사실 ID 컬럼만 보면 된다.
그런데 원본 테이블 전체를 보여주면 비밀번호, 이메일, 카드 정보 같은 민감한 개인정보까지 노출된다.
이때 ID만 포함한 뷰를 따로 만들어 제공하면 필요한 정보만 공개할 수 있다.<br/>
&ensp;즉, 뷰 기반 접근통제의 핵심은 **“필요한 정보만 보이게 하여 민감 정보 노출을 차단하는 것”**이다.<br/>

&ensp;뷰 기반 접근통제 시나리오 이해<br/>
&ensp;예제1<br/>
&ensp;“고객 감사 이벤트 기간(2022-01-01 ~ 2022-03-30)에 제품을 20개 이상 구매한 고객”에게 증정품을 보내기 위한 뷰를 만든다. 즉, 전체 주문 데이터가 아니라 이벤트 대상자 식별에 필요한 데이터만 추려내는 전용 뷰를 만든다는 뜻이다.<br/>

<p align="center"><img src="/assets/img/database/7주차/7-4.png" width="600"></p>

&ensp;예제2<br/>
&ensp;“회원 등급이 gold 이상이고 제품을 30개 이상 구매한 고객”에게 초청장을 보내기 위한 뷰를 만든다. 여기서는 고객 테이블과 주문 테이블을 함께 활용해 등급 조건 + 구매 조건을 동시에 만족하는 정보만 추출한다.<br/>

&ensp;변경 불가능한 뷰<br/>
&ensp;이런 뷰는 데이터를 바꾸지 못하게 하여 더 강한 접근통제를 수행할 수 있다.<br/>
* 기본 테이블의 기본키 속성이 포함되지 않은 뷰
* 기본 테이블에서 NOT NULL 속성이 빠진 뷰
* 집계 함수로 계산된 값을 포함한 뷰
* DISTINCT 포함
* GROUP BY 포함
* 여러 테이블을 조인해서 만든 뷰

&ensp;수정 가능한 뷰는 편리하지만 잘못하면 원본 데이터까지 바뀔 수 있다. 반대로 변경 불가능한 뷰는 조회 전용 보안창구처럼 사용할 수 있다.<br/>

# SQL문 기반 접근통제

&ensp;SQL문 기반 접근통제는 DCL(Data Control Language) 을 사용하여 특정 권한만 부여하는 방식이다. 즉, 사용자가 할 수 있는 작업을 SQL 수준에서 직접 제한한다.<br/>

&ensp;핵심 명령어<br/>
&ensp;1. GRANT<br/>
&ensp;객체 소유자가 다른 사용자에게 객체에 대한 권한을 부여하는 명령이다.<br/>
* 여러 권한 부여 가능
* 역할(Role)에 대한 권한 부여 가능
* 특정 컬럼에 대해서만 SELECT, UPDATE 권한 부여 가능

&ensp;2. REVOKE<br/>
&ensp;부여했던 권한을 회수하는 명령이다.<br/>

&ensp;예제1<br/>
&ensp;행사 담당자 Lee가 고객을 식별하지 못하도록, 고객이름과 고객아이디는 조회하지 못하게 한다.<br/>
<p align="center"><img src="/assets/img/database/7주차/7-7.png" width="600"></p>

```sql
GRANT SELECT(나이, 등급, 직업, 적립금) ON 고객 TO Lee;
```

&ensp;이 명령은 Lee에게 고객 테이블 전체 SELECT 권한을 주는 것이 아니라 나이, 등급, 직업, 적립금 컬럼만 조회할 수 있게 하는 부분 권한 부여다.<br/>

&ensp;예제2<br/>
&ensp;응용 프로그램 사용자 Hong이 고객 테이블 데이터를 수정하거나 삭제하지 못하도록 한다.<br/>

```sql
GRANT SELECT ON 고객 TO Hong;
```

&ensp;즉 조회만 가능하고 INSERT, UPDATE, DELETE는 허용되지 않는다. 읽기 전용 권한 부여의 대표 예시다.<br/>

&ensp;예제3<br/>
&ensp;응용 프로그램 사용자 'Lee'는 나이 18세 이상이면서 silver이상 등급인 고객에게 일정 조건이 충족되면 gold 또는 vip 등급으로 업그레이드해주는 프로그래머이다.<br/>
&ensp;프로그래머 Lee가 고객 등급을 업그레이드하는 작업을 해야 한다.<br/>

```sql
GRANT SELECT(나이, 등급, 고객아이디), UPDATE(등급)
ON 고객 TO Lee;
```

&ensp;이 경우 Lee는<br/>
* 나이, 등급, 고객아이디를 조회할 수 있고
* 등급 컬럼만 수정할 수 있다.

# 데이터베이스 취약점 분석 개요

&ensp;데이터 보안은 외부·내부의 여러 사용자로부터 데이터베이스를 안전하게 보호하는 것이다. 정보보호의 3대 요소인 **기밀성, 무결성, 가용성**을 보장해야 한다.<br/>

&ensp;취약점은 **위협에 의해 손실이 발생하게 되는 자산의 약점**이다.<br/>
&ensp;취약점은 위협이 자산에 손실을 입히기 위해 이용하는 수단이다.<br/>

&ensp;위협·취약점·공격 관계<br/>
* 위협은 100% 제거하기 어렵다.
* 하지만 취약점은 제거 가능하다.
* 따라서 취약점을 분석하고 제거하는 것이 중요하다.

&ensp;공격자를 완전히 없앨 수는 없지만, 공격자가 이용할 틈은 줄일 수 있다는 뜻<br/>

&ensp;데이터베이스 취약점 분석 절차<br/>
* 분석 설계
* 분석 구축
* 취약점 점검
* 취약점 발견 및 제거

&ensp;분석 설계 단계<br/>
&ensp;어떤 데이터베이스를 대상으로, 어느 범위까지 취약점 분석을 수행할지 정하는 단계다.
가장 기초 단계이지만 매우 중요하다. 조사가 제대로 되지 않으면 취약점을 식별하지 못하고, 결국 제거도 할 수 없기 때문이다.<br/>
<p align="center"><img src="/assets/img/database/7주차/7-8.png" width="600"></p>

&ensp;분석 구축 단계<br/>
&ensp;설계 단계에서 정한 범위를 바탕으로, 어떤 항목을 어떤 방식으로 점검할지 실제 정책을 세우는 단계다. 내부 사용자 경로를 볼지, 외부 웹서버 경로를 볼지 등을 정한다.<br/>
<p align="center"><img src="/assets/img/database/7주차/7-9.png" width="600"></p>

&ensp;접근 경로 관점<br/>
&ensp;취약점은 보안 솔루션을 우회한 공격, 내부자 공격, 외부 공격 툴 등을 통해 악용될 수 있다.
애플리케이션, 내부 인가자, 웹서버도 모두 위협의 경로가 될 수 있다.<br/>

&ensp;취약점 분석 방식: 모의 해킹 vs 내부 보안 감사<br/>
&ensp;1. 모의 해킹(Penetration Test)<br/>
&ensp;외부 사용자에 대한 침해 공격을 시뮬레이션하여 취약점을 검출하는 방식이다.<br/>
&ensp;대표 점검 항목:<br/>
* TNS Attack
* DoS
* Password Attack
* Configurations

&ensp;즉, 공격자 입장에서 실제로 침입 가능한 경로를 시험해보는 방식이다.<br/>

&ensp;2. 내부 보안 감사(Security Auditing)<br/>
&ensp;데이터베이스가 안전하게 운영되고 있는지 내부적으로 점검하는 방식이다.<br/>
&ensp;주요 점검 항목:<br/>
* Authentication
* Oracle Audit
* Networking
* OS Integrity
* Patch Management
* Backup/Availability

&ensp;즉, 관리자가 설정과 정책이 적절한지 확인하는 절차라고 보면 된다.<br/>

&ensp;DBMS 취약점 점검<br/>
&ensp;이 단계는 설계·구축 단계에서 정한 범위와 방법을 바탕으로 실제로 점검하고 조치를 취하는 단계다.<br/>
&ensp;국내 가이드라인은 MySQL, MSSQL, Oracle, MongoDB, PostgreSQL 등 다양한 DBMS에 대한 보안 가이드를 제공한다.<br/>
<p align="center"><img src="/assets/img/database/7주차/7-10.png" width="600"></p>

&ensp;MySQL 취약점 점검 핵심<br/>
* 불필요한 계정 제거
* 취약한 패스워드 사용 제한
* 타 사용자에 권한 부여 옵션 사용 제한
* DB 사용자 계정 정보 테이블 접근 권한
* root 권한으로 서버 구동 제한
* 환경설정 파일 접근 권한
* 안전한 암호화 알고리즘 사용
* 로그 활성화
* 최신 패치 적용

&ensp;1. 취약한 패스워드 사용 제한<br/>
&ensp;패스워드가 계정명과 같거나 default 패스워드를 쓰면 공격자가 쉽게 로그인할 수 있다.
그래서 이를 점검하고 제한해야 한다.<br/>

&ensp;사용자 계정과 패스워드가 동일한지 여부 조회<br/>
```sql
SELECT host, user FROM user WHERE password = password(user);
```

&ensp;사용자 계정의 패스워드가 Null인지 여부 조회<br/>
```sql
SELECT host, user FROM user WHERE password = "";
```

&ensp;2. 패스워드 복잡도<br/>
&ensp;권고사항은 대체로 다음과 같다.<br/>
* 영문/숫자/특수문자 3종류 혼용 시 8자리 이상
* 2종류 혼용 시 10자리 이상

&ensp;3. 패스워드 관리<br/>
&ensp;패스워드는 시스템 차원에서 규칙을 적용하고, 저장 시에는 일방향 암호화(One-Way Encryption) 처리해야 한다. 또 사용자가 규칙 범위 내에서 스스로 변경할 수 있어야 한다.<br/>

&ensp;4. root 권한으로 서버 구동 제한<br/>
&ensp;MySQL 데몬이 root 권한으로 동작하면 위험하다. root는 최고 권한이므로 꼭 필요한 경우가 아니면 제한되어야 한다.

&ensp;프로세스 확인이나 설정 파일 확인을 통해 점검하고, 필요하면 MySQL 전용 일반 사용자 계정으로 실행하도록 변경해야 한다.<br/>

&ensp;5. 최신 패치 적용<br/>
&ensp;최신 패치가 적용되지 않으면 알려진 취약점 때문에 침해 사고가 발생할 수 있다.
다만 업데이트는 시스템 운영에 큰 영향을 줄 수 있으므로, 영향도 평가 후 적용해야 한다.<br/>

# Oracle 취약점 점검

&ensp;1. DBA 권한은 꼭 필요한 계정에만<br/>
&ensp;관리자 권한은 남용되면 매우 위험하다. 그래서 정말 필요한 계정과 그룹에만 부여되었는지 점검해야 한다. 이는 관리자 권한 유출 시 비인가자의 접근 가능성을 줄이기 위한 것이다.<br/>

&ensp;2. 비인가 사용자의 시스템 테이블 접근 제한<br/>
&ensp;일반 사용자가 시스템 테이블에 접근할 수 있으면 매우 위험하다. 시스템 구조나 권한 정보가 노출될 수 있기 때문이다. 따라서 DBA 이외 사용자의 접근을 제한해야 한다.<br/>

&ensp;3. OS_ROLES, REMOTE_OS_AUTHENTICATION, REMOTE_OS_ROLES = FALSE<br/>
&ensp;TRUE이면<br/>
* OS 그룹이 데이터베이스 권한에 영향을 줄 수 있고
* 인증 절차 없이 원격 접속이 가능해질 수 있으며
* 원격 사용자가 다른 OS 사용자로 가장할 수 있기 때문이다.
