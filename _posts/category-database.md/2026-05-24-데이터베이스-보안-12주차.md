# 데이터베이스 암호화 설계

&ensp;1. 데이터베이스 암호화 설계란?<br/>
&ensp;데이터베이스 암호화 설계는 단순히 DB 데이터를 암호화한다.는 뜻이 아니다.<br/>
&ensp;데이터베이스 암호화를 구축하기 전에 **누가 접근하는지, 누구에게 복호화를 허용할지, 어떤 데이터를 암호화할지, 어떤 방식으로 암호화할지** 를 미리 정하는 단계<br/>

| 질문                       | 의미          |
| ------------------------ | ----------- |
| 누가 DB를 사용하는가?            | 사용자 식별      |
| 허가받지 않은 사용자는 어떻게 막을 것인가? | 비인가 사용자 통제  |
| 누가 원본 데이터를 볼 수 있는가?      | 복호화 권한 통제   |
| 어떤 데이터를 암호화할 것인가?        | 암호화 대상 선정   |
| 어떤 알고리즘을 사용할 것인가?        | 암호화 알고리즘 선정 |

&ensp;2. 데이터베이스 암호화 설계의 전체 흐름<br/>

| 단계 | 내용             |
| -- | -------------- |
| 1  | 데이터베이스 사용자 식별  |
| 2  | 비인가 사용자에 대한 통제 |
| 3  | 복호화 권한 통제      |
| 4  | 암호화 대상 선정      |
| 5  | 암호화 알고리즘 선정    |

&ensp;암호화는 기술만의 문제가 아니라 관한 설계 문제이다.<br/>
&ensp;예를 들어 주민등록번호를 AES로 암호화했다고 해도 아무 사용자나 복호화 키를 받아서 원본 주민등록번호를 볼 수 있다면 보안 설계가 실패한 것이다.<br/>
&ensp;그래서 가장 먼저 해야 하는 게 사용자 식별이다.<br/>

&ensp;3. 사용자 식별 및 비인가 사용자 통제<br/>
&ensp;3-1. 사용자 식별<br/>
&ensp;사용자 식별은 데이터베이스 암호화를 수행하기 전에 **해당 DB를 사용하는 사용자가 누구인지 파악하는 것** 이다.<br/>
&ensp;적절한 사용자에게만 암호 키를 제공하기 위해서<br/>

&ensp;모든 사용자에게 복호화 권한을 주는 것이 아니라 업무상 필요한 사용자에게만 키를 주기 위해 사용자를 구분하는 것이다.<br/>

&ensp;3-2. 데이터베이스 접근 방식의 종류<br/>

| 구분       | 설명                       | 예시                     |
| -------- | ------------------------ | ---------------------- |
| 정형적인 접근  | 정기적이고 반복적인 SQL 작업        | 웹 서버, WAS, 응용 프로그램     |
| 비정형적인 접근 | 사람이 직접 DB에 접속해서 조회/변경/삭제 | DBA, 개발자, 외주 개발자, 컨설턴트 |


&ensp;3-3. 정형적인 접근(Bulletin Job)<br/>
&ensp;특정 업무를 위해 정기적으로 DB에 접속해서 반복적인 SQL 작업을 수행하는 접근<br/>
&ensp;예를 들어 웹 서비스에서 사용자가 로그인하면 서버가 DB에 다음과 같은 SQL을 날릴 수 있다.<br/>
```sql
SELECT * FROM member WHERE id = ?;
```

&ensp;이런 식으로 애플리케이션이 정해진 로직에 따라 반복적으로 DB를 조회하는 게 정형적인 접근이다.<br/>

| 사용자/시스템 | 설명                  |
| ------- | ------------------- |
| 웹 서버    | 사용자의 요청을 받아 DB 조회   |
| WAS     | 비즈니스 로직 처리 중 DB 접근  |
| 응용 프로그램 | 정해진 기능 수행을 위해 DB 접근 |


&ensp;정형적인 접근은 보통 애플리케이션 레벨 보안 로직으로 통제할 수 있다.<br/>

&ensp;3-4. 비정형적인 접근(Non-Bulletin Job)<br/>
&ensp;사람이 DBMS에 직접 접속해서 데이터를 조회, 변경, 삭제하는 접근<br/>

&ensp;예시<br/>

| 사용자         | 설명                      |
| ----------- | ----------------------- |
| DBA         | DB 운영 및 유지보수            |
| 애플리케이션 개발자  | 개발 및 장애 확인을 위해 DB 직접 조회 |
| 외주 개발자/컨설턴트 | 프로젝트 수행 중 DB 접근         |

&ensp;이 사람들은 보통 DBeaver, DataGrip, MySQL Workbench 같은 DB 툴을 사용해서 직접 DB에 접속할 수 있다. 애플리케이션에서는 권한 체크를 잘 해도 DB에 직접 붙으면 애플리케이션 보안 로직을 우회할 수 있다. 예를 들어 애플리케이션에서는 일반 직원이 주민등록번호를 볼 수 없게 막아놨는데 개발자가 DB 툴로 직접 접속해서 다음 SQL을 실행하면 문제가 생길 수 있다.<br/>

```sql
SELECT name, rrn, phone_number FROM member;
```

&ensp;4. 접근 유형별 사용자 식별<br/>

<p align="center"><img src="/assets/img/database/12주차/12-1.png" width="600"></p>

| 사용자 유형      | 접근 특징              |
| ----------- | ------------------ |
| 일반 고객       | 애플리케이션을 통해 접근      |
| 콜센터 직원      | 내부 정보 조회 가능        |
| 비즈니스 애플리케이션 | 웹/WAS/포털/그룹웨어 등    |
| 애플리케이션 개발자  | DB 계정 보유 가능        |
| DBA         | DB 전체 접근 가능성 높음    |
| 외주 개발자/컨설턴트 | 프로젝트 기간 중 DB 접근 가능 |

&ensp;같은 DB에 접근하더라도 사용자마다 봐야 하는 데이터의 범위가 다르다.<br/>

&ensp;예를 들어 고객 정보 테이블이 있다.<br/>

| 사용자     | 볼 수 있어야 하는 정보        |
| ------- | -------------------- |
| 일반 고객   | 본인 정보                |
| 콜센터 직원  | 고객 상담에 필요한 일부 정보     |
| 개발자     | 장애 분석에 필요한 최소 정보     |
| DBA     | 운영에 필요한 DB 구조와 상태    |
| 비인가 사용자 | 아무 의미 없는 암호문 또는 NULL |

&ensp;DB 암호화 설계는 단순히 데이터를 암호화하는 것이 아니라 **사용자별로 데이터 노출 수준을 다르게 설계하는 것** 이다.<br/>

&ensp;5. 사용자 식별 시 추가로 확인해야 하는 정보<br/>
&ensp;사용자를 이름이나 계정만으로 식별하면 부족할 수 있다.<br/>

| 식별 정보      | 이유                   |
| ---------- | -------------------- |
| IP 주소      | 허용된 위치에서 접속하는지 확인    |
| 접속 날짜 및 시간 | 비정상 시간대 접근 탐지        |
| 사용자 계정     | 누가 접근했는지 확인          |
| 애플리케이션 이름  | 어떤 프로그램을 통해 접근했는지 확인 |

&ensp;예를 들어 같은 admin 계정이라도 다음 두 상황은 다르게 봐야 한다.<br/>

| 상황                   | 판단         |
| -------------------- | ---------- |
| 회사 내부 IP에서 업무 시간에 접속 | 정상 가능성 높음  |
| 해외 IP에서 새벽 3시에 접속    | 비정상 가능성 높음 |

&ensp;그래서 암호 키 발급이나 복호화 수행은 단순히 계정만 보는 것이 아니라 접속 환경까지 함께 확인해서 정당한 상황에서만 수행되도록 해야 한다.<br/>

&ensp;6. 사용자 식별을 하지 않으면 생기는 문제<br/>
&ensp;사용자 식별을 하지 않으면 다음 흐름으로 사고가 발생할 수 있다.<br/>
```css
사용자 식별 미수행
        ↓
불필요한 키 발급, 접근 허용
        ↓
데이터베이스 침입 사고 발생
```

&ensp;사용자 식별을 제대로 하지 않으면 원래 복호화 권한이 없어야 할 사용자에게도 키가 발급될 수 있다.<br/>
&ensp;암호화된 데이터라도 키가 잘못 발급되면 결국 원본 데이터가 노출될 수 있다.<br/>

&ensp;7. 비인가 사용자에 대한 통제<br/>
&ensp;7-1. 비인가 사용자<br/>
&ensp;적절한 권한을 가지지 않았는데 암호화된 DB에 접근하려는 사용자<br/>

&ensp;7-2. 인가 사용자와 비인가 사용자의 차이<br/>

| 구분      | 볼 수 있는 데이터            |
| ------- | --------------------- |
| 인가된 사용자 | 원본 데이터 또는 복호화된 데이터    |
| 비인가 사용자 | 암호문, 의미 없는 문자, NULL 등 |

&ensp;예를 들어 주민등록번호 컬럼이 있다.<br/>

| 사용자     | 표시 결과            |
| ------- | ---------------- |
| 인가 사용자  | 990101-1234567   |
| 비인가 사용자 | `a8f9xZ...`      |
| 비인가 사용자 | `NULL`           |
| 비인가 사용자 | `******-*******` |

&ensp;비인가 사용자에게는 원본 데이터가 보이면 안 된다.<br/>

&ensp;7-3. 비인가 사용자에게 보여주는 방식<br/>

| 방식           | 설명               |
| ------------ | ---------------- |
| 암호문 그대로 보여주기 | 암호화된 문자열을 그대로 표시 |
| NULL 값으로 표현  | 데이터가 없는 것처럼 표시   |
| 마스킹 처리       | 일부만 가리고 표시       |
| 의미 없는 데이터 표시 | 해석 불가능한 형태로 표시   |


&ensp;예를 들어 전화번호가 있다고 하면 다음처럼 처리할 수 있다.<br/>

| 원본            | 비인가 사용자 표시      |
| ------------- | --------------- |
| 010-1234-5678 | `NULL`          |
| 010-1234-5678 | `010-****-5678` |
| 010-1234-5678 | `x93ksl29a...`  |

&ensp;보안 수준만 보면 NULL이나 암호문 표시가 더 안전할 수 있고 업무 편의성까지 고려하면 마스킹 처리가 유용할 수 있다.<br/>

&ensp;8. 암호화 대상 선정<br/>
&ensp;8-1. 암호화 대상<br/>
&ensp;암호화 대상은 데이터베이스 내 데이터 중에서 **암호화를 수행할 대상** 을 의미한다.<br/>
&ensp;암호화 대상은 크게 두 가지 방식으로 선정할 수 있다.<br/>

| 방식            | 의미                         |
| ------------- | -------------------------- |
| 특정 컬럼 암호화     | 민감한 컬럼만 암호화                |
| 데이터베이스 전체 암호화 | 파일, 테이블스페이스 등 전체 저장 단위 암호화 |

&ensp;9. 컬럼 암호화<br/>
&ensp;9-1. 컬럼 암호화(Column-Level Encryption)<br/>
&ensp;테이블 전체가 아니라 일부 컬럼에 대해서만 암호화를 수행하는 방식<br/>

&ensp;예를 들어 회원 테이블이 있다.<br/>

| member_id | name | phone_number  | rrn            |
| --------- | ---- | ------------- | -------------- |
| 1         | 김철수  | 010-1234-5678 | 990101-1234567 |

&ensp;여기서 name은 그대로 두고 phone_number, rrn만 암호화할 수 있다.<br/>

&ensp;암호화 후에는 이런 느낌이 된다.<br/>

| member_id | name | phone_number | rrn        |
| --------- | ---- | ------------ | ---------- |
| 1         | 김철수  | `A8x92...`   | `Ksl29...` |

&ensp;민감한 컬럼만 골라서 암호화하는 방식<br/>

&ensp;9-2. 컬럼 암호화 대상 선정 기준<br/>
&ensp;일반적으로 민감하다고 판단되는 컬럼을 암호화 대상으로 선정한다.<br/>

| 민감 데이터 | 설명           |
| ------ | ------------ |
| 주민등록번호 | 개인 식별 가능     |
| 질병 정보  | 매우 민감한 의료 정보 |
| 바이오 정보 | 지문, 얼굴, 홍채 등 |
| 신용카드번호 | 금융 사고 가능     |
| 계좌번호   | 금융 정보        |

&ensp;특정 개인을 알아낼 수 있거나 지극히 개인적인 데이터는 암호화 대상이 된다.<br/>

&ensp;9-3. 컬럼 암호화의 장점<br/>
* 사용자마다 다르게 보여줄 수 있다.

&ensp;환자의 의료 정보를 포함하는 테이블이 있다.<br/>

| 사용자 | 질병 정보 표시 방식              |
| --- | ------------------------ |
| 의사  | 질병 정보를 복호화해서 원본으로 확인     |
| 간호사 | 암호화된 질병 정보 또는 보이지 않도록 처리 |

&ensp;예를 들어 환자 테이블이 있다.<br/>
| patient_id | name | disease |
| ---------- | ---- | ------- |
| 1          | 김철수  | 당뇨      |

&ensp;의사는 진료를 위해 질병 정보를 알아야 하니까 원본을 볼 수 있어야 한다.<br/>
* 의사 화면: 김철수 / 당뇨

&ensp;하지만 간호사는 업무 범위에 따라 질병 정보를 직접 볼 필요가 없을 수도 있다.<br/>
* 간호사 화면: 김철수 / ****

&ensp;또는<br/>
* 간호사 화면: 김철수 / NULL

&ensp;이런 식으로 사용자별로 복호화 권한을 다르게 설정할 수 있다.<br/>

&ensp;9-4. 컬럼 암호화의 단점<br/>
* 성능 문제

&ensp;특히 암호화된 컬럼에 인덱스가 걸려 있는 경우 문제가 생길 수 있다.<br/>
```css
암호화된 컬럼에 대해 인덱스 활용 불가
        ↓
DBMS 부하 발생
        ↓
응답시간 저하
```

&ensp;10. 데이터베이스 전체 암호화<br/>
&ensp;10-1. 데이터베이스 전체 암호화<br/>
&ensp;데이터베이스 전체 암호화는 특정 컬럼만 암호화하는 것이 아니라 **파일, 테이블페이스, 블록 같은 저장 단위 전체를 암호화하는 방식** 이다.<br/>

| 명칭          | 의미                       |
| ----------- | ------------------------ |
| 디스크 암호화     | Storage Level Encryption |
| 테이블스페이스 암호화 | 테이블스페이스 단위 암호화           |
| 블록 암호화      | DB 블록 단위 암호화             |

&ensp;DB 파일 자체를 암호화해서 비인가 사용자가 파일을 열어도 내용을 알 수 없게 만드는 방식이다.<br/>

&ensp;10-2. 데이터베이스 전체 암호화의 장점<br/>
* 구현이 비교적 간단하다
* 민감 컬럼 식별 부담 감소
* 비인가자 데이터 확인 불가
* 상대적으로 높은 안전성

&ensp;10-3. 데이터베이스 전체 암호화의 단점<br/>
* 빈번한 암·복호화 과정 -> DBMS 부하 발생
* 사용자 식별 불가 -> 사용자별 세밀한 권한 관리 어려움

&ensp;전체 암호화는 “전부 잠그는 방식”에 가깝기 때문에 사용자별로 누구는 보고, 누구는 못 보게 하는 세밀한 제어가 어렵다.<br/>

&ensp;11. 컬럼 암호화 vs 데이터베이스 전체 암호화 비교<br/>

| 구분      | 컬럼 암호화                  | 데이터베이스 전체 암호화                 |
| ------- | ----------------------- | ----------------------------- |
| 암호화 범위  | 특정 컬럼                   | DB 파일, 테이블스페이스, 블록 등 전체 저장 단위 |
| 대상 선정   | 민감 컬럼 선정 필요             | 민감 컬럼 식별 부담 적음                |
| 사용자별 제어 | 가능                      | 어려움                           |
| 보안성     | 민감 데이터 중심 보호            | 전체 데이터 보호                     |
| 성능      | 암호화 컬럼 검색 시 성능 저하 가능    | 전체 암복호화로 DBMS 부하 가능           |
| 대표 예시   | 주민등록번호, 질병, 카드번호 컬럼 암호화 | 디스크 암호화, 테이블스페이스 암호화          |
| 적합한 상황  | 사용자별 접근 권한이 중요한 경우      | DB 파일 탈취 방지가 중요한 경우           |

# 데이터베이스 암호화 구축

&ensp;1. 데이터베이스 암호화 구축<br/>
&ensp;데이터베이스 암호화 구축: 암호화 설계 단계에서 정한 내용을 바탕으로 실제 데이터베이스에 암호화를 수행하는 단계<br/>

```css
암호화 설계
   ↓
실제 DB에 암호화 적용
   ↓
원본 데이터 삭제
   ↓
제약사항 유지
   ↓
암호 키 관리
```

&ensp;2. 데이터베이스 암호화 구축의 핵심 요소<br/>

| 핵심 요소       | 의미                                     |
| ----------- | -------------------------------------- |
| 원본 데이터 삭제   | 암호화 후 남아 있는 평문 데이터를 제거                 |
| 제약사항 유지     | 인덱스, PK, FK, Unique Key, Trigger 등을 유지 |
| DB 암호화 키 관리 | 암·복호화에 사용하는 키를 안전하게 관리                 |

&ensp;3. 원본 데이터 삭제<br/>
&ensp;3-1. 원본 데이터 삭제가 필요한 이유<br/>
&ensp;암호화 이전의 원본 데이터, 즉 평문 데이터가 다른 저장소에 남아 있을 수 있다 예를 들어 이런 상황이 있을 수 있다.<br/>
* 운영 DB
* 백업 DB
* 서브 스토리지
* 로그 파일
* 임시 파일
* 인덱스 정보
* 복제 서버

&ensp;여기 중 하나라도 평문 데이터가 남아 있으면, DB 본체를 암호화해도 보안 사고가 날 수 있다.<br/>

&ensp;3-2. 쉬운 예시<br/>
&ensp;회원 테이블에 주민등록번호가 있다.<br/>
| id | name | rrn            |
| -- | ---- | -------------- |
| 1  | 김철수  | 990101-1234567 |


&ensp;이후 rrn 컬럼을 암호화해서 이렇게 만들었다고 해보자.<br/>
| id | name | rrn           |
| -- | ---- | ------------- |
| 1  | 김철수  | `a8F9xZ12...` |


&ensp;그런데 백업 서버에 예전 데이터가 그대로 남아 있으면?<br/>
```css
backup_member.sql
김철수, 990101-1234567
```

&ensp;이러면 암호화한 의미가 약해진다. 공격자가 실제 운영 DB가 아니라 백업 파일을 가져가면 원본 주민등록번호가 그대로 노출되기 때문이다. 그래서 암호화 후에는 **원본 데이터를 가진 모든 스토리지에 포함된 평문 데이터를 삭제해야 한다.** <br/>

&ensp;3-3. 삭제해야 하는 대상<br/>
&ensp;원본 데이터뿐 아니라 원본 데이터와 관련 있는 인덱스 정보까지 삭제해야 한다.<br/>

| 삭제 대상           | 이유               |
| --------------- | ---------------- |
| 평문 원본 데이터       | 원본 정보 노출 방지      |
| 백업 파일의 평문 데이터   | 백업 경로를 통한 유출 방지  |
| 서브 스토리지의 복제 데이터 | 복제본 유출 방지        |
| 원본 데이터 관련 인덱스   | 인덱스를 통한 원본 유추 방지 |

&ensp;데이터 본문만 지우는 것이 아니라, 원본 데이터와 연결된 부가 정보까지 확인해야 한다.<br/>

&ensp;4. 원본 데이터 삭제 시기<br/>
&ensp;원본 데이터를 언제 삭제할지는 암호화 적용 방식에 따라 나뉜다.<br/>

| 방식                    | 설명                      |
| --------------------- | ----------------------- |
| 기존 DBMS 서비스를 유지하면서 삭제 | 서비스 운영 중 암호화 및 삭제 수행    |
| 서비스를 일시정지하고 삭제        | 서비스를 잠시 멈추고 암호화 및 삭제 수행 |

&ensp;4-1. 기존 DBMS 서비스를 유지하면서 삭제하는 방식<br/>
&ensp;이 방식은 서비스가 계속 동작하는 상태에서 암호화와 삭제를 진행한다. 예를 들어 쇼핑몰, 은행 서비스, 병원 시스템처럼 서비스를 멈추기 어려운 경우에 사용할 수 있다.<br/>

&ensp;장점<br/>
* 시스템의 가용성 유지

&ensp;단점<br/>
* 암호화 시간 증가

&ensp;운영 중인 DB는 계속 요청을 처리해야 하니까 암호화 작업을 빠르게 몰아서 하기가 어렵다. 그래서 전체 작업 시간이 길어질 수 있다.<br/>

&ensp;4-2. 서비스를 일시정지하고 삭제하는 방식<br/>
&ensp;이 방식은 서비스를 잠시 멈춘 뒤 암호화와 삭제를 진행하는 것이다. 예를 들어 새벽 점검 시간에 이런 식으로 진행할 수 있다.<br/>
```css
서비스 점검 공지
   ↓
서비스 일시 중지
   ↓
DB 암호화 수행
   ↓
평문 원본 데이터 삭제
   ↓
제약사항 확인
   ↓
서비스 재개
```

&ensp;장점: 빠른 암호화 시간<br/>

&ensp;단점: 시스템 가용성 보장 X<br/>

&ensp;4-3. 두 방식 비교<br/>

| 구분           | 서비스 유지 방식   | 서비스 일시정지 방식     |
| ------------ | ----------- | --------------- |
| 서비스 사용 가능 여부 | 가능          | 불가능             |
| 가용성          | 높음          | 낮음              |
| 암호화 시간       | 길어질 수 있음    | 빠름              |
| 적합한 상황       | 중단이 어려운 서비스 | 점검 시간이 허용되는 서비스 |
| 단점           | 작업 시간이 증가   | 서비스 중단 발생       |


&ensp;5. 제약사항 유지<br/>
&ensp;5-1. 제약사항 유지<br/>
&ensp;DB 암호화를 적용한 후에도 기존 DB가 가지고 있던 구조와 규칙이 유지되어야 한다.<br/>

| 제약사항/객체     | 의미                     |
| ----------- | ---------------------- |
| Index       | 검색 속도를 높이는 색인          |
| Primary Key | 테이블의 기본키               |
| Foreign Key | 테이블 간 관계를 연결하는 외래키     |
| Unique Key  | 중복을 허용하지 않는 키          |
| Trigger     | 특정 이벤트 발생 시 자동 실행되는 로직 |

&ensp;5-2. 제약사항 유지가 중요한 이유<br/>
&ensp;예를 들어 회원 테이블과 주문 테이블이 있다고 해보자.<br/>
* member.user_id  ←  order.user_id

&ensp;order.user_id는 member.user_id를 참조하는 외래키이다. 그런데 암호화 과정에서 user_id 값이 바뀌거나 관계가 깨지면?<br/>
* 주문 정보가 어떤 회원의 것인지 알 수 없음

&ensp;그러면 서비스 정상적으로 동작하기 어렵다.<br/>

&ensp;5-3. 인덱스를 가진 컬럼을 암호화할 때 문제<br/>
&ensp;인덱스가 걸린 컬럼을 암호화하면 특히 조심해야 한다. 예를 들어 전화번호 검색을 빠르게 하기 위해 phone_number 컬럼에 인덱스를 걸어두었다고 해보자.<br/>
```sql
CREATE INDEX idx_member_phone
ON member(phone_number);
```

&ensp;그런데 전화번호를 암호화하면 값이 이렇게 바뀔 수 있다.<br/>
```css
010-1234-5678
↓
a8f9Zx2k...
```

&ensp;그래서 두 가지 방식을 설명<br/>

| 방식                | 설명                        |
| ----------------- | ------------------------- |
| 인덱스도 함께 암호화       | 복호화되었을 때 사용할 수 있도록 구현     |
| 암호화되지 않은 별도 컬럼 사용 | 검색용 컬럼을 따로 두어 인덱스 가능하게 구축 |

&ensp;5-4. 예시<br/>

| member_id | name | phone_number  |
| --------- | ---- | ------------- |
| 1         | 김철수  | 010-1234-5678 |

| member_id | name | phone_number |
| --------- | ---- | ------------ |
| 1         | 김철수  | `A8x92k...`  |

&ensp;그런데 전화번호로 검색해야 한다면 문제가 생긴다.<br/>
```sql
SELECT * FROM member
WHERE phone_number = '010-1234-5678';
```

&ensp;DB에는 원본 전화번호가 없고 암호문만 있으니까, 그냥 검색하면 원하는 결과가 안 나올 수 있다.<br/>
&ensp;그래서 실무에서는 이런 식으로 검색용 값을 따로 둘 수도 있다.<br/>
| member_id | name | phone_number_enc | phone_hash            |
| --------- | ---- | ---------------- | --------------------- |
| 1         | 김철수  | `A8x92k...`      | `HASH(010-1234-5678)` |

&ensp;검색할 때는 원본 전화번호를 같은 방식으로 해시해서 비교한다.<br/>
```sql
SELECT * FROM member
WHERE phone_hash = HASH('010-1234-5678');
```

&ensp;이렇게 하면 원본 전화번호는 숨기면서도 검색은 가능해진다.<br/>

&ensp;6. DB 암호화 키 관리<br/>
&ensp;6-1. DB 암호화 키 관리<br/>
&ensp;DB 암호화 키 관리는 암호화와 복호화에 사용되는 암호 키를 안전하게 관리하는 것이다.<br/>
&ensp;왜냐하면 데이터가 아무리 강한 알고리즘으로 암호화되어 있어도, 암호 키가 유출되면 공격자가 복호화해서 원본 데이터를 얻을 수 있기 때문이다.<br/>
&ensp;흐름<br/>
```css
허술한 암호 키 관리
   ↓
악의적인 공격자의 암호 키 취득
   ↓
복호화를 통해 원본 데이터 취득
```

&ensp;7. 암호 키 관리 방법<br/>
| 방법                 | 의미                   |
| ------------------ | -------------------- |
| 마스터 키 사용           | 데이터 키를 다시 마스터 키로 암호화 |
| HSM 사용             | 하드웨어 보안 모듈로 키 보호     |
| 암호 키 접근제어          | 키에 접근 가능한 사용자 제한     |
| 암호 키 발급 및 폐기 내역 관리 | 키 생성, 재발급, 폐기 이력 관리  |

&ensp;8. 마스터 키 사용<br/>
&ensp;8-1. 마스터 키<br/>
&ensp;다른 암호 키를 보호하기 위한 상위 암호 키<br/>
&ensp;데이터베이스를 직접 암호화하는 키를 데이터 키라고 하면, 그 데이터 키를 다시 암호화해서 보호하는 키가 마스터 키이다.<br/>
&ensp;구조<br/>
```css
마스터 키
   ↓ 암호화
데이터 키
   ↓ 암호화
데이터베이스
```

<p align="center"><img src="/assets/img/database/12주차/12-2.png" width="600"></p>

&ensp;데이터베이스를 암호화한 키를 그대로 저장하지 않고, 그 키 자체도 마스터 키로 암호화해서 저장하는 방식<br/>

&ensp;8-2. 마스터 키 사용 예시<br/>
&ensp;예를 들어 member 테이블의 주민등록번호를 암호화하는 데이터 키가 있다.<br/>
* 데이터 키: K_data_001

&ensp;이 키를 그대로 DB나 파일에 저장하면 위험하다. 그래서 마스터 키로 한 번 더 암호화한다.<br/>
```css
K_data_001
↓ 마스터 키로 암호화
ENC(K_data_001)
```

&ensp;이렇게 저장하면 공격자가 키 테이블을 탈취해도 바로 원본 데이터 키를 얻기 어렵게 된다.<br/>

&ensp;8-3. 마스터 키 방식의 장점<br/>
* 암호 키가 임의 테이블에 저장되어도 암호화되어 있기 때문에 상대적으로 안전 -> 암호화되어 있으므로
바로 DB를 복호화하기 어렵다.

&ensp;8-4. 마스터 키 방식의 단점<br/>
* 많은 암호 키 관리 -> 데이터 키가 많아질수록 관리 복잡도 증가
* 마스터 키 관리 필요 -> 마스터 키가 유출되면 전체 키 체계가 위험

&ensp;마스터 키는 특히 안전하게 관리해야 한다.<br/>

&ensp;9. HSM<br/>
&ensp;9-1. HSM<br/>
&ensp;Hardware Security Module의 약자<br/>
&ensp;암호 키를 안전하게 생성하고 저장하고 사용하는 전용 하드웨어 장치<br/>

&ensp;9-2. HSM의 역할<br/>

| HSM 특징      | 설명                         |
| ----------- | -------------------------- |
| 암호 키 생성     | 내부에서 키 생성                  |
| 암호 키 저장     | 키를 안전하게 보관                 |
| 키 유출 방지     | 내부에서 생성된 키가 외부로 나가지 않도록 구성 |
| 공격 시 키 파기   | 악의적 공격이 감지되면 키를 스스로 파기     |
| 자체 OS/SW 사용 | 네트워크 공격으로부터 키 유출 방지        |
| 상용 DBMS 지원  | 많은 DBMS에서 안전한 키 관리를 위해 지원  |

&ensp;HSM 내부에서 생성된 암호 키는 외부로 유출되지 않도록 설계된다.<br/>

&ensp;9-3. 쉬운 비유<br/>
&ensp;마스터 키를 일반 서버의 설정 파일에 저장하는 것은 열쇠를 사무실 서랍에 넣어두는 것과 비슷하다.<br/>
&ensp;반면 HSM은 열쇠를 은행 금고 안에 넣어두고, 필요한 작업도 금고 안에서 처리하는 느낌이다.<br/>
&ensp;그래서 공격자가 서버에 침입하더라도 키 자체를 빼내기 어렵게 만드는 것이 HSM의 목적이다.<br/>

&ensp;10. 암호 키 변경 및 접근제어<br/>
&ensp;10-1. 키를 주기적으로 변경해야 하는 이유<br/>
&ensp;암호 키를 한 번 만들고 계속 사용하면 위험하다. 시간이 지날수록 다음 가능성이 커지기 때문이다.<br/>
* 키가 노출될 가능성 증가
* 키를 알고 있는 사람 증가
* 오래된 키 관리 방식의 취약점 증가

&ensp;10-2. KMS<br/>
&ensp;Key Management System의 약자<br/>

| 기능      | 설명                        |
| ------- | ------------------------- |
| 키 생성    | 새로운 암호 키 생성               |
| 키 폐기    | 더 이상 사용하지 않는 키 삭제 또는 비활성화 |
| 키 재발급   | 유효기간이 지난 키를 새 키로 교체       |
| 키 접근제어  | 누가 키를 사용할 수 있는지 제한        |
| 키 이력 관리 | 발급, 폐기, 변경 기록 관리          |

&ensp;KMS는 키를 체계적으로 관리하는 시스템<br/>

# 데이터베이스 암호화 운영

&ensp;1. 데이터베이스 암호화 운영<br/>
&ensp;데이터베이스 암호화 운영은 암호화가 적용된 이후에 암호 키와 사용자 접근 기록을 지속적으로 관리하는 단계이다.<br/>
> 암호화된 DB가 실제 서비스 환경에서 안전하게 유지되도록 키 변경 이력, 키 백업, 사용자 로그, 보안 감사를 관리하는 과정

| 운영 단계 핵심           | 의미                              |
| ------------------ | ------------------------------- |
| 암호 키 변경 이력 및 백업 관리 | 키가 언제 생성·변경·폐기되었는지 관리하고, 분실에 대비 |
| 사용자 로그 관리          | 누가 암호화된 데이터에 어떤 작업을 했는지 기록하고 감사 |

&ensp;2. 암호 키 변경 이력 및 백업 관리<br/>
&ensp;2-1. 암호 키 관리의 중요성<br/>
&ensp;구축 단계에서 키를 안전하게 저장했다면, 운영 단계에서는 다음을 관리한다.<br/>

| 단계        | 주요 내용                     |
| --------- | ------------------------- |
| 암호화 구축 단계 | HSM, 마스터 키 등 사용           |
| 암호화 운영 단계 | 암호 키 변경 이력 관리, 암호 키 백업 관리 |

&ensp;키를 “어디에 안전하게 저장할까?”가 구축 단계라면, 운영 단계에서는 “그 키를 어떻게 계속 관리할까?”가 핵심이다.<br/>

&ensp;2-2. 암호 키 관리가 필요한 이유<br/>

| 상황                  | 발생 가능한 문제             |
| ------------------- | --------------------- |
| 암호 키를 변경하지 않고 계속 사용 | 의도치 않은 보안 사고 가능성 증가   |
| 하나의 키로 모든 DB를 암호화   | 키 유출 시 대규모 보안 사고 발생   |
| 암호 키를 분실            | 데이터 복호화 불가, 데이터 손실 발생 |

&ensp;2-3. 키를 변경하지 않고 계속 쓰면 왜 위험할까?<br/>
&ensp;암호 키를 한 번 만들고 계속 사용하면 시간이 지날수록 유출 가능성이 커진다.<br/>
* 개발자가 키를 알고 있음 → 시간이 지나면서 담당자가 바뀜 → 키가 여러 설정 파일에 복사됨 → 어느 순간 키가 노출될 가능성 증가

&ensp;그래서 암호 키는 주기적으로 변경해야 한다.<br/>

&ensp;2-4. 하나의 키로 모든 DB를 암호화하면 왜 위험할까?<br/>
&ensp;예를 들어 다음처럼 모든 DB를 하나의 키로 암호화했다.<br/>
* user_db      → key_A
* payment_db   → key_A
* medical_db   → key_A
* log_db       → key_A

&ensp;이 경우 key_A 하나만 유출되어도 모든 DB가 위험해질 수 있다. 반대로 여러 키를 나눠서 쓰면 피해 범위를 줄일 수 있다.<br/>
* user_db      → key_user
* payment_db   → key_payment
* medical_db   → key_medical
* log_db       → key_log

&ensp;이렇게 하면 key_user가 유출되어도 결제 DB나 의료 DB까지 바로 위험해지지는 않다.<br/>

&ensp;2-5. 암호 키를 분실하면 왜 문제일까?<br/>
&ensp;암호 키는 데이터를 복호화하는 데 반드시 필요하다. 즉 키가 없으면 암호화된 데이터를 원래대로 돌릴 수 없다.<br/>
* 암호화된 데이터 + 암호 키 = 원본 데이터 복호화 가능
* 암호화된 데이터 + 키 없음 = 복호화 불가

&ensp;그래서 키를 분실하면 단순한 불편함이 아니라 데이터 손실로 이어질 수 있다. 예를 들어 고객 정보 DB는 남아 있는데 복호화 키가 사라지면, DB 파일은 있어도 실제 고객 정보를 읽을 수 없게 된다. 그래서 운영 단계에서는 암호 키 백업 관리가 중요하다.<br/>

&ensp;3. 키 관리 시스템, KMS<br/>
&ensp;3-1. KMS(Key Management System)<br/>
&ensp;암호 키를 생성, 저장, 변경, 폐기, 백업, 접근제어하는 시스템<br/>

&ensp;암호 키 관리를 위해 다음이 필요하다.<br/>
* 여러 암호 키 사용
* 주기적인 암호 키 변경
* 암호 키 백업 관리
* 키 관리 시스템(KMS) 

&ensp;KMS는 키를 그냥 파일로 보관하는 게 아니라 키의 전체 생명주기를 관리하는 시스템이다.<br/>

&ensp;3-2. KMS가 관리하는 것<br/>

| 관리 항목   | 설명                     |
| ------- | ---------------------- |
| 키 생성    | 새로운 암호 키 발급            |
| 키 변경    | 일정 주기마다 키 교체           |
| 키 폐기    | 더 이상 사용하지 않는 키 제거      |
| 키 백업    | 키 분실에 대비               |
| 키 사용 이력 | 누가, 언제, 어떤 키를 사용했는지 기록 |
| 접근제어    | 키에 접근 가능한 사용자 제한       |

&ensp;4. Oracle Key Vault<br/>
&ensp;Oracle에서 지원하는 TDE 암호화를 위한 암호 키를 효율적으로 관리할 수 있도록 설계된 솔루션<br/>

&ensp;4-1. Oracle Key Vault의 주요 기능<br/>
<p align="center"><img src="/assets/img/database/12주차/12-4.png" width="600"></p>

| 기능                    | 설명                     |
| --------------------- | ---------------------- |
| TDE 관리 콘솔             | 암호 키 관리                |
| 오라클 월렛과 자바 키스토어 파일 관리 | 다른 키스토어 파일 관리 지원       |
| 애플리케이션 백업             | 암호 키 분실 시 복호화를 위한 키 백업 |
| 관리 콘솔                 | 암호 키 발급 이력 관리          |

&ensp;Oracle Key Vault는 단순히 키를 저장하는 곳이 아니라 키 백업, 키 이력, 인증서, 키스토어 파일까지 함께 관리하는 보안 솔루션<br/>

&ensp;4-3. Oracle Key Vault에서 확인할 수 있는 정보<br/>

| 확인 정보      | 의미                  |
| ---------- | ------------------- |
| 암호 키 생성 일자 | 키가 언제 만들어졌는지        |
| 키 상태       | 현재 사용 중인지, 폐기되었는지 등 |
| 키 사용 내역    | 어떤 엔드포인트에서 사용했는지    |
| 인증서 생성 일자  | 인증서가 언제 만들어졌는지      |
| 인증서 현재 상태  | 유효한지, 만료되었는지 등      |

&ensp;이 정보가 중요한 이유는 보안 사고가 났을 때 “어떤 키가 언제 사용되었고, 어느 시스템에서 문제가 발생했는지” 추적할 수 있기 때문이다.<br/>

&ensp;5. 암호화된 데이터에 대한 모니터링 필요<br/>
&ensp;암호화된 데이터에 대해서도 누가, 언제, 무엇을, 어떻게 조회했는지 모니터링해야 한다.<br/>

&ensp;6. 사용자 로그 관리<br/>
&ensp;6-1. 사용자 로그 관리<br/>
&ensp;사용자가 암호화된 데이터에 어떤 행동을 수행하는지 모니터링하는 것<br/>

&ensp;6-2. 보안 감사<br/>
&ensp;보안 감사는 데이터베이스의 데이터에 대해 여러 사용자나 응용 프로그램이 어떤 작업을 수행했는지 모니터링하는 과정이다.<br/>

&ensp;목적<br/>
| 목적       | 설명                   |
| -------- | -------------------- |
| 위협 행위 탐지 | 비정상적인 접근이나 조작을 찾음    |
| 사고 조사    | 문제가 발생했을 때 원인과 책임 추적 |

&ensp;6-3. 사용자 행동을 실시간으로 기록해야 하는 이유<br/>
&ensp;로그 없음 → 누가 접근했는지 모름 → 어떤 데이터를 봤는지 모름 → 언제 문제가 발생했는지 모름 → 사고 분석 불가능<br/>

&ensp;반대로 로그가 있으면 이렇게 추적할 수 있다.<br/>
&ensp;로그 있음 → 사용자 확인 → 시간 확인 → 실행 SQL 확인 → 성공/실패 여부 확인 → 보안 사고 원인 분석 가능<br/>

&ensp;7. Oracle의 보안 감사<br/>
&ensp;7-1. Oracle 보안 감사 방식<br/>
&ensp;Oracle에서는 파라미터 파일(Parameter File)을 변경해서 보안 감사를 수행할 수 있다. 또한 적절한 감사 규칙을 설정해서 다음 감사를 수행할 수 있다.<br/>

| 감사 종류  | 의미                             |
| ------ | ------------------------------ |
| 로그인 감사 | 누가 로그인했는지 기록                   |
| 행동 감사  | 어떤 SQL 작업을 했는지 기록              |
| 객체 감사  | 특정 테이블, 뷰 등 객체에 어떤 접근이 있었는지 기록 |

&ensp;예를 들어 member 테이블에 대한 조회를 감시하고 싶다면, 해당 객체에 대한 감사 규칙을 설정할 수 있다.<br/>

&ensp;7-2. 감사 레코드 저장 방식<br/>
&ensp;감사 레코드는 파라미터 값에 따라 기록 방식이 달라질 수 있다.<br/>

| 저장 방식        | 설명               |
| ------------ | ---------------- |
| 데이터베이스 내부 저장 | DB 내부 데이터 사전에 저장 |
| 외부 파일 저장     | 파일 형태로 외부에 기록    |

&ensp;DB 내부에 저장하는 경우, 감사 레코드 데이터 사전을 통해 조회할 수 있다.<br/>

&ensp;8. 감사 레코드에 저장되는 주요 정보<br/>

| 이름          | 내용         |
| ----------- | ---------- |
| USERNAME    | 사용자 이름     |
| TIMESTAMP   | SQL문 실행 시간 |
| OBJ_NAME    | 객체 이름      |
| ACTION_NAME | SQL문 내용    |

&ensp;여기에 추가로 다음 정보도 저장된다.<br/>
* SQL문 성공/실패 여부
* 객체 소유자
* 권한 정보

&ensp;9. 데이터 사전을 통한 모니터링<br/>
&ensp;DB 관리자는 감사 레코드가 저장된 데이터 사전에 질의해서 사용자의 행적을 모니터링할 수 있다.<br/>
&ensp;하지만 감사 로그는 너무 많아질 수 있다. 사용자가 많고 SQL이 많으면 로그가 엄청나게 쌓여서
효율적인 감사가 어려워진다. 그래서 Oracle에서는 감사를 위한 다양한 뷰를 제공한다.<br/>

&ensp;10. Oracle에서 제공하는 감사 뷰<br/>

| AUDIT TRAIL VIEW      | 내용                                 |
| --------------------- | ---------------------------------- |
| STMT_AUDIT_OPTION_MAP | 각 AUDITING 옵션과 해당 번호 출력            |
| AUDIT_ACTION          | 각 AUDITING의 행동 번호 출력               |
| ALL_DEF_AUDIT_OPTS    | DEFAULT AUDITING 옵션으로 설정된 객체 감사 출력 |
| DBA_STMT_AUDIT_OPTS   | Statement 감사의 옵션 확인                |
| DBA_PRIV_AUDIT_OPTS   | 권한 감사의 옵션 확인                       |
| DBA_OBJ_AUDIT_OPTS    | 객체 감사의 옵션 확인                       |
| USER_OBJ_AUDIT_OPTS   | 사용자의 객체 감사 옵션 확인                   |
| DBA_AUDIT_TRAIL       | 모든 감사 출력                           |
| DBA_AUDIT_OBJECT      | 객체와 관련된 모든 감사 레코드 출력               |
| USER_AUDIT_OBJECT     | 현재 사용자의 객체와 관련된 모든 감사 레코드 출력       |

&ensp;11. 외부 감사 솔루션<br/>
&ensp;Oracle 자체 기능 외에도 외부에서 감사를 수행하는 솔루션이 있다.<br/>
* Total Recall
* Audit Vault

&ensp;이런 솔루션은 Oracle뿐만 아니라 여러 상용 DBMS의 보안 감사를 지원할 수 있다.<br/>
&ensp;장점은 GUI 환경에서 효율적으로 보안 감사를 수행할 수 있다. 관리자가 SQL을 직접 많이 작성하지 않아도 화면에서 로그, 이상 접근, 감사 결과를 확인할 수 있게 해주는 도구이다.<br/>

# Oracle DBMS 암호화

&ensp;1. Oracle DB 보안 개요<br/>
&ensp;Oracle DB 보안은 크게 두 방향으로 나눌 수 있다.<br/>

| 구분            | 의미                       |
| ------------- | ------------------------ |
| 데이터베이스 사용자 관리 | 누가 DB에 접근할 수 있는지 통제      |
| 데이터베이스 자체 보호  | DB 파일이나 저장 데이터를 암호화하여 보호 |

&ensp;1-1. 데이터베이스 사용자 관리<br/>
&ensp;Oracle에서는 사용자의 권한을 관리하기 위해 다음 기능을 제공한다.<br/>
| 기능          | 설명                      |
| ----------- | ----------------------- |
| GRANT       | 사용자에게 권한 부여             |
| REVOKE      | 사용자에게 부여된 권한 회수         |
| 역할 기반 권한 부여 | Role을 만들어 여러 권한을 묶어서 관리 |
| View 접근 통제  | 원본 테이블 대신 제한된 View만 보여줌 |
| SQL문 접근 통제  | 특정 SQL 수행 권한 제한         |

&ensp;1-2. 데이터베이스 자체 보호<br/>
&ensp;사용자 권한을 잘 관리해도 DB 파일 자체가 탈취되면 문제가 생길 수 있다. 예를 들어 공격자가 DB 서버의 데이터 파일을 가져갔다고 해보자. 관한 관리는 DBMS 안에서 동작하는 기능이기 때문에, 파일 자체가 유출되면 별도의 보호가 필요하다. 그래서 필요한 것이 **데이터베이스 암호화** 이다.<br/>

&ensp;2. 데이터베이스 암호화<br/>
&ensp;민감하고 중요한 데이터를 암호화해서 저장하고, 필요할 때 활용을 위해 복호화를 수행하는 과정<br/>
&ensp;데이터베이스 암호화의 장점과 단점<br/>
| 구분 | 내용                              |
| -- | ------------------------------- |
| 장점 | 제3자가 DB를 불법 취득해도 내용을 알 수 없도록 보호 |
| 단점 | 암·복호화 과정으로 DBMS 성능 저하 발생        |

&ensp;데이터베이스 암호화는 보안성을 높이지만, 암·복호화 연산 때문에 성능 저하가 발생할 수 있다.<br/>

&ensp;3. TDE<br/>
&ensp;Transparent Data Encryption의 약자<br/>
&ensp;애플리케이션 입장에서는 암호화가 적용되었는지 거의 신경 쓰지 않아도 되도록 DBMS 내부에서 자동으로 암·복호화를 처리하는 방식<br/>

| 장점              | 설명                         |
| --------------- | -------------------------- |

&ensp;6. 블록 암호 모드<br/>
&ensp;6-1. 블록 암호 모드<br/>
&ensp;AES, DES 같은 알고리즘은 긴 평문을 한 번에 암호화하지 않고, 일정한 크기의 블록 단위로 나누어 암호화한다.<br/>
> 긴 평문을 블록 단위로 나누어 암호화할 때, 각 블록을 어떤 방식으로 처리할지 정한 운용 방식

&ensp;운용 모드<br/>
| Mode Name | Full Name             |
| --------- | --------------------- |
| ECB       | Electric CodeBook     |
| CBC       | Cipher Block Chaining |
| CFB       | Cipher FeedBack       |
| OFB       | Output FeedBack       |
| CTR       | CounTeR               |

&ensp;7. ECB 모드<br/>
&ensp;7-1. ECB 모드<br/>
&ensp;ECB 모드는 평문을 블록 단위로 쪼갠 뒤, 각각의 블록을 독립적으로 암호화하는 방식<br/>
<p align="center"><img src="/assets/img/database/12주차/12-10.png" width="600"></p>

&ensp;7-2. ECB 모드의 장점<br/>

| 장점         | 설명                   |
| ---------- | -------------------- |
| 병렬 처리 가능   | 여러 블록을 동시에 암호화할 수 있음 |
| 암호화 시간이 짧음 | 블록 간 의존성이 없어서 빠름     |

&ensp;7-3. ECB 모드의 단점<br/>

| 단점         | 설명                             |

| 낮은 안전성     | 패턴이 드러날 가능성이 있음                |

&ensp;8. CBC 모드<br/>
&ensp;Cipher Block Chaining의 약자<br/>

&ensp;8-1. CBC 모드의 암호화 방식<br/>
<p align="center"><img src="/assets/img/database/12주차/12-11.png" width="600"></p>

&ensp;흐름<br/>
* 첫 번째 블록: IV XOR 평문블록1 → 암호화 → 암호문블록1
* 두 번째 블록: 암호문블록1 XOR 평문블록2 → 암호화 → 암호문블록2
* 세 번째 블록: 암호문블록2 XOR 평문블록3 → 암호화 → 암호문블록3

&ensp;8-2. CBC 모드의 특징<br/>
&ensp;CBC에서는 각 암호문 블록이 현재 평문뿐만 아니라 이전 블록들의 영향도 받는다. 그래서 ECB 보다 패턴 노출이 줄어들어 더 안전하다.<br/>

&ensp;단점<br/>
| 특징    | 설명                         |
| ----- | -------------------------- |
| 안전성   | ECB보다 높음                   |
| 병렬 처리 | 어려움                        |
| 이유    | 이전 암호문 블록이 다음 암호화에 필요하기 때문 |

    - 결과값 XOR 평문블록2 → 암호문블록2

| ------------------------- | --------------------- |
| AES_ENCRYPT(str, key_str) | 문자열 str을 key_str로 암호화 |
| AES_DECRYPT(str, key_str) | 암호문을 key_str로 복호화     |

&ensp;12-3. AES 키 크기<br/>
| 키 크기       | 설명                     |
| ---------- | ---------------------- |
| 기본 128bits | 기본 AES 키 크기            |
| 192bits    | 확장 가능                  |
| 256bits    | 확장 가능, 더 강하지만 성능 영향 가능 |

&ensp;키 크기 증가 → 보안성 증가 가능 → 암·복호화 비용 증가 → 성능 영향 가능<br/>
