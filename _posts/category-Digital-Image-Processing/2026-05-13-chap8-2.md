## Entropy

&ensp;1) Entropy의 의미<br/>
&ensp;정보원이 평균적으로 얼마나 불확실한가? 를 나타내는 값이다.<br/>

&ensp;2) Entropy 공식<br/>
$$H(S) = E\{ -log_2P(S_i) \}$$

&ensp;기댓값이니까 각 정보량에 확률을 곱해서 더한다.<br/>

$$H(s) = \sum_{i=1}^{N}\{-log_2P(S_i) \}P(S_i) = -\sum_{i=1}^{N}P(S_i)log_2P(S_i)$$

<p align="center"><img src="/assets/img/Digital Image Processing/chap8-2/8-4.png" width="600"></p>

&ensp;3) 아까 예제로 entropy 계산<br/>
<p align="center"><img src="/assets/img/Digital Image Processing/chap8-2/8-5.jpeg" width="600"></p>

&ensp;4) Entropy와 무손실 압축의 관계<br/>
&ensp;무손실 압축에서 이론적으로 도달할 수 있는 가장 좋은 평균 비트 수는 entropy이다.<br/>
&ensp;예를 들어 entropy가 H(S) = 2.634 라면 아무리 좋은 무손실 압축을 해도 평균적으로 2.634 bits/symbol보다 훨씬 낮게 만들 수는 없다.<br/>

&ensp;Shannon의 First Coding Theorem<br/>
$$H(S) ≤ R < H(S) + 1$$

&ensp;여기서 R은 실제 평균 코드 길이이다.<br/>
&ensp;즉 Huffman coding 같은 실제 압축 코드는 보통 entropy보다 약간 크거나 같다.<br/>

$$Entropy ≤ Average Code Length$$

> Entropy는 이론적 최저 평균 코드 길이이고, Huffman coding의 평균 코드 길이는 그 근처까지 갈 수 있다.

# Huffman Coding

&ensp;Huffman Coding 전체 흐름<br/>

<p align="center"><img src="/assets/img/Digital Image Processing/chap8-2/8-6.png" width="600"></p>

&ensp;1단계: Raw Image Data<br/>
&ensp;원본 이미지 데이터가 있다.<br/>
&ensp;예를 들어 픽셀 밝기값들이 있다고 하자. [0,0,1,2,2,2,3,3,...] <br/>

&ensp;2단계: Brightness Histogram<br/>
&ensp;각 밝기값이 몇 번 나오는지 센다.<br/>
&ensp;예를 들어:<br/>

| Symbol | Count |
| ------ | ----- |
| S0     | 10    |
| S1     | 19    |
| S2     | 21    |
| S3     | 30    |

&ensp;이런 식으로 개수를 세는 게 histogram이다.<br/>

&ensp;3단계: pdf 만들기<br/>
&ensp;Histogram을 전체 픽셀 수로 나누면 확률이 된다.<br/>

$$P(S_i) = \frac{해당 심볼 개수}{전체 개수}$$

&ensp;이게 pdf, 즉 probability distribution.<br/>

&ensp;4단계: 확률 내림차순 정렬<br/>
&ensp;확률이 큰 것부터 작은 것까지 정렬한다.<br/>
&ensp;예시<br/>

| Symbol | Probability |
| ------ | ----------- |
| S3     | 0.3         |
| S2     | 0.21        |
| S1     | 0.19        |
| S0     | 0.1         |
| S6     | 0.07        |
| S5     | 0.05        |
| S4     | 0.05        |
| S7     | 0.03        |

&ensp;5단계: Huffman Tree 만들기<br/>
&ensp;핵심 규칙: 가장 작은 확률 두 개를 계속 합친다.<br/>
&ensp;그리고 합칠 때마다 0과 1을 붙여서 트리를 만든다.<br/>

&ensp;6단계: 원본 데이터를 Huffman code로 치환<br/>
&ensp;각 symbol마다 codeword가 생기면 원본 데이터를 그 코드로 바꾼다.<br/>
&ensp;예를 들어<br/>
* S3 → 11
* S2 → 01
* S7 → 10100

&ensp;그러면 원래 고정 길이로 저장하던 데이터보다 더 짧게 저장할 수 있다.<br/>

&ensp;7단계: Code Table도 함께 저장<br/>
&ensp;압축된 비트열만 있으면 복원이 안 된다. 예를 들어 `110110100...` 이런 비트열만 보고는 어떤 게 S3인지 S7인지 알 수 없다. 그래서 반드시 code table도 같이 저장해야 한다.<br/>

| Symbol | Codeword |
| ------ | -------- |
| S3     | 11       |
| S2     | 01       |
| S1     | 00       |
| S0     | 1011     |

## Huffman Coding Tree 만드는 법

&ensp;예시<br/>

| Symbol | Probability |
| ------ | ----------- |
| S3     | 0.30        |
| S2     | 0.21        |
| S1     | 0.19        |
| S0     | 0.10        |
| S6     | 0.07        |
| S5     | 0.05        |
| S4     | 0.05        |
| S7     | 0.03        |

<p align="center"><img src="/assets/img/Digital Image Processing/chap8-2/8-7.jpg" width="600"></p>

&ensp;Codeword 읽는 법<br/>
&ensp;Huffman tree에서 codeword는 루트에서 해당 symbol까지 내려가면서 읽는다. 보통 한쪽 가지는 0, 다른쪽 가지는 1로 정한다.<br/>

| Symbol | Probability | Codeword | Code Length |
| ------ | ----------: | -------: | ----------: |
| S3     |        0.30 |       11 |           2 |
| S2     |        0.21 |       01 |           2 |
| S1     |        0.19 |       00 |           2 |
| S0     |        0.10 |     1011 |           4 |
| S6     |        0.07 |     1001 |           4 |
| S5     |        0.05 |     1000 |           4 |
| S4     |        0.05 |    10101 |           5 |
| S7     |        0.03 |    10100 |           5 |

&ensp;중요한 특징:<br/>
> 확률이 큰 심볼일수록 코드가 짧다. 확률이 작은 심볼일수록 코드가 길다.

&ensp;예를 들어 S3는 확률이 0.3으로 가장 크니까 11 -> 길이 2<br/>
&ensp;반대로 S7은 확률이 0.03으로 가장 작으니까 10100 -> 길이 5<br/>
&ensp;이게 Huffman coding의 핵심<br/>

&ensp;Entropy 계산<br/>
&ensp;공식<br/>
<p align="center"><img src="/assets/img/Digital Image Processing/chap8-2/8-8.png" width="600"></p>

&ensp;각 symbol마다 $-log_2P(S_i)$ 를 구하고 거기에 확률 $P(S_i)$ 를 곱한 뒤 모두 더한다.<br/>

&ensp;각 항 계산<br/>
<p align="center"><img src="/assets/img/Digital Image Processing/chap8-2/8-9.jpg" width="600"></p>

&ensp;Average Code Length 계산<br/>
&ensp;Huffman coding에서 실제 평균 코드 길이는 다음 공식으로 구한다.<br/>

$$R = \sum P(S_i)L(S_i)$$

&ensp;여기서 $L(S_i)$ 는 해당 symbol의 codeword길이이다.<br/>

| Symbol | Probability | Code Length | $P(S_i)L(S_i)$ |
| ------ | ----------: | ----------: | -------------: |
| S3     |        0.30 |           2 |           0.60 |
| S2     |        0.21 |           2 |           0.42 |
| S1     |        0.19 |           2 |           0.38 |
| S0     |        0.10 |           4 |           0.40 |
| S6     |        0.07 |           4 |           0.28 |
| S5     |        0.05 |           4 |           0.20 |
| S4     |        0.05 |           5 |           0.25 |
| S7     |        0.03 |           5 |           0.15 |

&ensp;다 더하면 R = 0.60 + 0.42 + 0.38 + 0.40 + 0.28 + 0.20 + 0.25 + 0.15 = 2.68 bits/symbol<br/>

&ensp;Entropy와 Average Length 비교<br/>
$$H(S) = 2.634$$

$$R = 2.68$$

&ensp;H(S) ≤ R < H(S) + 1<br/>

&ensp;확인해보면 2.634 ≤ 2.68 < 3.634<br/>
&ensp;Huffman coding은 이론적 최적값인 entropy에 매우 가깝게 압축하고 있다.<br/>

&ensp;고정 길이 코드보다 좋은 이유<br/>
&ensp;예를 들어 symbol이 총 8개이다. 8개를 고정 길이 코드로 표현하려면 몇 bit가 필요할까?<br/>
&ensp;$2^3 = 8$ -> 모든 symbol을 고정 길이로 표현하면 3 bit씩 필요하다.<br/>

&ensp;그러면 평균 코드 길이는 항상 3 bits/symbol이다. 그런데 Huffman coding은 2.68 bits/symbol이므로 더 짧다. 압축률 관점으로 보면 2.68/3 = 0.893. 즉 원래 대비 약 89.3 % 정도의 비트만 사용한다.<br/>

## Huffman Coding 장단점

&ensp;장점<br/>
&ensp;1) Algorithm is easy to implement<br/>
* 확률 분포를 구하고 작은 확률 두 개씩 합쳐 트리를 만들고 0, 1을 붙이면 되기 때문

&ensp;2) lossless compression<br/>
* 압축했다가 복원해도 원래 데이터와 완전히 동일하게 복구된다.

&ensp;단점<br/>
&ensp;1) efficiency depends on accuracy of statistical model used and type of image<br/>
&ensp;Huffman coding의 성능은 확률 모델이 얼마나 정확한지 그리고 이미지 특성이 어떤지에 따라 달라진다.<br/>

&ensp;Huffman coding은 결국 어떤 심볼이 얼마나 자주 나오는가에 따라 코드 길이를 정한다. 그런데 확률 추정이 부정확하면 자주 나오는 심불에 충분히 짧은 코드를 못 주고 결과적으로 압축 효율이 떨어진다. 또한 이미지 종류에 따라 분포가 다르다. 어떤 이미지가 특정 밝기값이 몰려 있고 어떤 이미지는 거의 고르게 분포돼 있을 수 있다. 그래서 데이터 특성에 따라 효율 차이가 생긴다.<br/>

&ensp;2) RLE is better for “long” runs of identical pixels<br/>
&ensp;같은 픽셀이 길게 반복되는 경우에는 Huffman보다 RLE(Run Length Encoding)가 더 낫다.<br/>
&ensp;예를 들어<br/>
* 0000000000000
* AAAAAA

&ensp;처럼 같은 값이 길게 반복되면 Huffman은 심볼별로 코드 붙이는 방식이라 한계가 있지만 RLF는 "0이 13번 반복" 이렇게 길이 자체를 저장하니까 훨씬 효율적이다.<br/>

&ensp;3) requires two passes of data scan<br/>
&ensp;Huffman coding을 하려면 먼저 각 심볼의 확률을 알아야 한다.<br/>
&ensp;순서<br/>
&ensp;1차 스캔<br/>
* 데이터 전체를 훑으면서
* 각 심볼이 몇 번 나오는지 세고
* 확률 모델을 만든다

&ensp;2차 스캔<br/>
* 그 확률 모델로 Huffman tree를 만든 뒤
* 실제 데이터를 압축한다

&ensp;바로 즉시 압축하기 어려운 구조이다.<br/>

&ensp;4) all codes are different sizes (VLC)<br/>
&ensp;VLC는 Variable Length Code 즉 **가변 길이 부호**이다.<br/>

&ensp;Huffman coding에서는<br/>
* 어떤 심볼은 2비트
* 어떤 심볼은 4비트
* 어떤 심볼은 5비트

&ensp;이런 식으로 길이가 다 다르다.<br/>
&ensp;왜 이것이 단점인가?<br/>
&ensp;가변 길이 부호는 압축에는 유리하지만<br/>
* 처리 로직이 복잡해지고
* 코드 경계를 맞추기가 어려워지고
*  오류가 났을 때 영향이 커질 수 있다.

&ensp;5) synchronization problem - error propagation<br/>
&ensp;이건 **오류 전파(error propagation)** 문제<br/>
&ensp;Huffman은 코드 길이가 일정하지 않기 때문에 중간에 비트 하나가 잘못되면 그 뒤를 어디서 끊어 읽어야 할지 헷갈릴 수 있다.<br/>
&ensp;즉 한 비트 오류가 뒤쪽 여러 심볼 해석에 영향을 줄 수 있다.<br/>

## Summary of Entropy Coding

&ensp;Efficiency 공식<br/>

$$ Efficiency(\% ) = \frac{H(S_i; i =1, ..., N)}{AverageCodeLength}\times 100$$

&ensp;이론적 최적값(Entropy)에 비해 실제 코드가 얼마나 가까운가?를 보는 척도<br/>

&ensp;왜 최대 효율이 100%인가?<br/>
&ensp;Entropy H(S)는 이론적으로 가능한 최소 평균 비트 수이다. 즉 실제 평균 코드 길이는 entropy보다 작아질 수 없다.<br/>

<p align="center"><img src="/assets/img/Digital Image Processing/chap8-2/8-10.png" width="600"></p>

&ensp;예제 계산<br/>
$$H(S) = 2.634 , Average Code Length = 2.68$$

$$Efficiency = \frac{2.634}{2.68} \times 100 = 98.28\%$$

&ensp;Huffman coding이 이론적 최적값에 매우 가깝다.<br/>

# Arithmetic Coding

&ensp;HEVC(H.265), VVC(H.266) 같은 최신 비디오 압축 표준에서 사용된다.<br/>
&ensp;더 좋은 압축 효율이 필요한 최신 표준에서 Arithmetic coding 계열이 많이 쓰인다.<br/>

&ensp;왜 Huffman을 넘어서 Arithmetic coding을 쓸까?<br/>
&ensp;1) Non-integer length coding<br/>
&ensp;허프만은 코드 길이가 결국 정수 비트 단위이다. 예를 들어 한 심볼에 평균 2.68비트는 가능해도 개별 심볼 코드 길이는 2비트, 4비트처럼 정수여야 한다. <br/>
&ensp;그런데 arithmetic coding은 전체 시퀀스를 하나의 실수 구간으로 표현하므로 더 세밀하게 압축 가능하다.(= entropy에 더 가깝게 갈 수 있다.)<br/>

&ensp;2) Probability distribution can be derived in real time (adaptive method)<br/>
&ensp;Huffman은 보통 먼저 확률을 알아야 하니까 2-pass가 필요하다.<br/>
&ensp;Arithmetic coding은 adaptive 방식으로 데이터를 읽으면서 확률 분포를 실시간으로 갱신할 수 있다.<br/>
* 미리 전체를 다 보지 않아도 되고 데이터에 맞춰 모델을 바꿀 수 있다.

&ensp;핵심원리<br/>
&ensp;처음에는 [0,1) 구간에서 시작한다. 각 심볼의 확률에 따라 이 구간을 잘게 나눈다.
데이터가 하나 들어올 때마다 해당 심볼에 대응하는 구간만 남긴다. 이 과정을 반복하면 최종적으로 아주 작은 구간이 남고, 그 안의 아무 숫자 하나만 보내면 전체 시퀀스를 표현할 수 있다.<br/>

&ensp;Huffman: 심볼 하나마다 코드 하나<br/>
&ensp;Arithmetic coding: 문자열 전체를 하나의 숫자로 압축<br/>

&ensp;예를 들어 Huffman은 `A -> 0, B -> 10, C -> 11` 이런 식이라면 Arithmetic coding은 “ABCA라는 전체 시퀀스는 0.3945...” 이런 식으로 하나의 실수 값으로 표현하는 느낌이다.<br/>

## Example of Arithmetic Coding

<p align="center"><img src="/assets/img/Digital Image Processing/chap8-2/8-11.jpg" width="600"></p>
<p align="center"><img src="/assets/img/Digital Image Processing/chap8-2/8-12.jpg" width="600"></p>

&ensp;시퀀스 0, -1, 0, 2는 최종적으로 [0.3928, 0.396) 라는 구간으로 표현된다. 이 구간 안에 들어가는 아무 수 하나만 선택하면 그 수가 이 시퀀스를 나타내는 코드가 될 수 있다.<br/>

&ensp;$0.39453125_{10} = 0.01100101_{2}$ <br/>
&ensp;최종적으로 이 실수 값을 비트열로 저장/전송해야 하니까 이진수로 바꾸는 것이다. 이 값이 최종 구간 [0.3928,0.396) 안에 있기 때문에 이 비트열을 받는 쪽은 “아, 이건 0,−1,0,2였구나”
라고 복원할 수 있다.<br/>

&ensp;왜 8비트로 표현 가능하다고 보나?<br/>
&ensp;최종 구간을 구분할 수 있을 정도로 충분한 정밀도의 이진수면 된다.(정확히 저 숫자여야 하는 건 아니고 그 구간 안에 들어가는 적당한 binary fraction이면 된다.)<br/>

&ensp;Arithmetic coding의 장점<br/>
&ensp;Huffman은 심볼별 코드<br/>
* 0 → 11
* 1 → 0
* 2 → 101

&ensp;이런 식으로 심볼 하나하나에 코드 배정<br/>

&ensp;Arithmetic은 전체 시퀀스 하나를 구간으로 표현 
* `0, -1, 0, 2 전체 → [0.3928, 0.396)`

> 한 심볼 단위가 아니라 전체 시퀀스를 압축하므로 더 세밀하고 더 entropy에 가깝게 압축할 수 있다.

&ensp;Disadvantages of Arithmetic Coding<br/>
&ensp;1. Computational complexity<br/>
&ensp;매 심볼마다 구간을 다시 계산해야 하고 실수/분수 개념이 들어가고 구현 시 정밀도 관리도 필요<br/>

&ensp;즉, Huffman보다 구현 난이도도 높고 하드웨어/소프트웨어 처리도 복잡<br/>

&ensp;2. Dilution effect<br/>
&ensp;모델이 너무 복잡해지면 경우의 수가 폭발적으로 증가한다.<br/>
&ensp;dilution effect: 데이터를 너무 세세하게 나눠서 모델링하면 각 조건별로 관측 데이터가 너무 작이진다.<br/>
&ensp;전체 데이터는 많이도 각 세부 상황마다 나눠 보면 표본 수가 너무 적어서 확률 추정이 부정확해진다. -> dilution effect(희석 효과)<br/>

&ensp;Huffman vs Arithmetic Coding 비교 정리<br/>

| 항목     | Huffman Coding     | Arithmetic Coding      |
| ------ | ------------------ | ---------------------- |
| 기본 원리  | 심볼마다 코드워드 부여       | 전체 시퀀스를 하나의 실수 구간으로 표현 |
| 코드 길이  | 정수 비트 길이           | 비정수 평균 길이 가능           |
| 압축 효율  | 좋음                 | 보통 더 좋음                |
| 구현 난이도 | 쉬움                 | 어려움                    |
| 확률 모델  | 보통 미리 필요(2-pass)   | adaptive 가능            |
| 오류 영향  | 가변 길이 부호라 동기화 문제   | 역시 민감하지만 방식 다름         |
| 사용 예   | 전통적 entropy coding | 최신 비디오 코딩 표준           |

# Binary Arithmetic Coding

&ensp;이전 arithmetic coding은 가능한 심볼이 여러 개였다. <br/>
&ensp;예를 들어 -2, -1, 0, 1, 2<br/>

&ensp;이렇게 5개 심볼을 한 번에 다뤘다. 이런 걸 m-ary arithmetic coding이라고 생각하면 된다. 여기서 m은 심볼 종류 개수이다.<br/>

&ensp;그런데 Binary Arithmetic Coding은 이름 그대로 심볼을 0과 1 두 개만 다룬다.<br/>
&ensp;{0, 1}<br/>
&ensp;모든 심볼을 먼저 0과 1의 비트열로 바꾼 뒤, 그 비트열을 arithmetic coding으로 압축하는 방식이다.<br/>

&ensp;Binary Arithmetic Coding의 장점<br/>
&ensp;여러 개 심볼을 한 번에 처리하는 arithmetic coding보다, 0/1만 처리하는 binary arithmetic coding이 더 단순하고 실제 표준에서 쓰기 좋다.<br/>

&ensp;1. Less computational complexity<br/>
&ensp;m-ary arithmetic coding은 심볼 종류가 많으면 매번 여러 구간을 계산해야 한다.<br/>
&ensp;예를 들어 심볼이 5개면 -2, -1, 0, 1, 2<br/>

&ensp;각 심볼마다 누적확률 구간을 관리해야 한다.<br/>
&ensp;그런데 binary arithmetic coding은 항상 두 구간만 보면 된다.<br/>
&ensp;**0 구간, 1 구간** <br/>
&ensp;그래서 계산이 단순해진다.<br/>

&ensp;2. Higher order conditioning model 설계가 쉬움<br/>
> 주변 상황, 이전 심볼, 문맥을 고려해서 확률을 바꾸는 모델을 만들기 쉬워진다.

&ensp;예를 들어 이미지나 영상 압축에서는 현재 값이 주변 픽셀이나 이전 예측 결과에 영향을 받다.<br/>
&ensp;그런데 심볼 종류가 많으면 경우의 수가 너무 많아진다. 반대로 0/1만 다루면 확률 모델이 단순해진다.<br/>

&ensp;P(0), P(1) 만 잘 추정하면 되니까 context modeling이 쉬워진다.<br/>

&ensp;3. Context modeling on sub-symbol level<br/>
&ensp;이건 HEVC, VVC 같은 비디오 압축 표준에서 중요한 개념이다. 어떤 심볼 $S_i$ 를 바로 압축하지 않고 먼저 이진 코드로 바꾼다.<br/>

&ensp;예를 들어<br/>
<p align="center"><img src="/assets/img/Digital Image Processing/chap8-2/8-13.png" width="600"></p>

&ensp;여기서 S3 하나를 압축한다고 하면 S3 자체를 바로 arithmetic coding 하는 게 아니라 S3 -> 1011 으로 바꾼 뒤 1, 0, 1, 1 각각을 binary arithmetic coding으로 처리하는 것이다. 이걸 sub-symbol level 이라고 보면 된다.<br/>
&ensp;symbol 전체가 아니라 symbol을 구성하는 bit 단위에서 확률 모델링한다.<br/>

&ensp;4. Binarization is required<br/>
&ensp;Binary arithmetic coding은 0/1만 처리할 수 있다. 그래서 원래 심볼이 여러 종류라면 먼저 이진화해야 한다. 이 과정을 binarization이라고 한다.<br/>
&ensp;예: S3 → 1011, S7 → 10100<br/>

## Adaptive Binary Arithmetic Coding

&ensp;Binary Arithmetic Coding은 확률이 고정되어 있다.<br/>
&ensp;예를 들어 $P(0) = 0.6, P(1) = 0.4$ <br/>
&ensp;이렇게 확률을 미리 정해놓은 sequence를 인코딩했다. 그런데 Adaptive Binary Arithmetic Coding은 다르다.<br/>
> 데이터를 읽으면서 0과 1이 몇 번 나왔는지 세고, 그때그때 확률을 업데이트하면서 interval을 줄여나가는 방식이다.

&ensp;확률이 고정이 아니라 계속 바뀐다.<br/>

&ensp;Adaptive 예제<br/>
&ensp;주어진 binary sequence는: 01111<br/>
&ensp;초기 count는 C(0) = 1, C(1) = 1<br/>
&ensp;그래서 초기 확률은 $P(0) = \frac{1}{2}, P(1) = \frac{1}{2}$ <br/>

&ensp;여기서 왜 처음부터 0과 1의 count를 1로 두냐면, 처음에 아무 데이터도 안 봤을 때 확률이 0이 되는 걸 막기 위해서이다.<br/>
&ensp;만약 C(1) = 0인 상태에서 1이 나오면 P(1) = 0이 되어 구간이 사라져버린다. 그래서 보통 초기 count를 1씩 둬서 시작한다.<br/>

&ensp;Adaptive 방식의 핵심 규칙<br/>
&ensp;매 bit를 인코딩할 때마다<br/>
1. 현재 P(0),P(1)로 interval을 나눈다.
2. 현재 bit에 해당하는 interval을 선택한다.
3. 방금 나온 bit의 count를 1 증가시킨다.
4. 확률을 다시 계산한다.

$$P(0) = \frac{C(0)}{C(0) + C(1)}$$

$$P(1) = \frac{C(1)}{C(0) + C(1)}$$

&ensp;Sequence 01111 계산 흐름<br/>
<p align="center"><img src="/assets/img/Digital Image Processing/chap8-2/8-18.jpg" width="600"></p>

&ensp;왜 $0.46875_{10} = 0.01111_{2}$ 인가?<br/>
&ensp;최종 구간이 [0.4667, 0.5) 이니까 이 안에 들어가는 이진 소수 하나를 고르면 된다.<br/>

&ensp;$0.01111_{2} = 0 \times \frac{1}{2} + 1 \times \frac{1}{4} + 1 \times \frac{1}{8} + 1 \times \frac{1}{16} + 1 \times \frac{1}{32} = 0.25 + 0.125 + 0.0625 +0.03125 = 0.46875$

&ensp;0.4667 ≤ 0.46875 < 0.5 이므로 이 값은 최종 구간 안에 들어간다. 따라서 `01111` 이라는 binary sequence를 대표하는 코드로 쓸 수 있다.<br/>

&ensp;왜 renormalization이 필요할까?<br/>
&ensp;Without renormalization 방식은 계산은 직관적이다. 그런데 실제 컴퓨터에서는 문제가 있다. Arithmetic coding은 sequence가 길어질수록 interval이 계속 작아진다. <br/>
&ensp;예를 들어 [0, 1) 에서 시작해서 [0, 0.8) -> [0.64,0.8) -> [0.64,0.768) 이런 식으로 점점 좁아진다.<br/>
&ensp;sequence가 아주 길면 interval이 너무 작아져서 컴퓨터가 표현하기 어려워진다. 즉 정밀도 문제가 생긴다. 그래서 중간중간 interval을 다시 크게 늘려주는 작업이 필요하다. -> **Renormalization** <br/>

# Renormalization

&ensp;Renormalization의 핵심 아이디어<br/>
&ensp;현재 interval이 어느 절반에 완전히 들어가면, 그 정보를 bit로 출력하고 interval을 다시 [0,1) 크기로 확대하는 과정<br/>

&ensp;절반을 기준으로 보는 이유<br/>
&ensp;전체 구간 [0,1)을 binary 관점으로 보면:<br/>
* [0,0.5)에 있으면 첫 binary bit가 0
* [0.5,1)에 있으면 첫 binary bit가 1

&ensp;즉 interval 전체가 [0.5, 1) 안에 들어가면 그 구간 안의 어떤 숫자를 골라도 첫 bit는 무조건 1이다. 그러면 그 1은 이미 확정된 정보니까 출력해도 된다. 마찬가지로 interval 전체가 [0,0.5) 안에 있으면 첫 bit는 무조건 0이므로 0을 출력할 수 있다.<br/>

&ensp;마지막 출력<br/>
&ensp;최종 구간: [0.28,0.536)<br/>
&ensp;대표값으로 $0.5_{10} = 0.1_{2}$ 를 선택했다.<br/>
&ensp;그리고 최종 output으로 $Output2 = 1$ 을 붙인다.<br/>
&ensp;앞에서 이미 출력한 bit가 $Output1 = 1$
&ensp;마지막 대표값에서 나온 bit가 $Output2 = 1$ <br/>
&ensp;그래서 최종 출력은 `11`<br/>
&ensp;renormalization을 해도 최종 결과는 같고 단지 중간에 interval이 너무 작아지는 것을 막기 위해 출력을 미리 내보내고 구간을 다시 키우는 것이다.<br/>

&ensp;MPS: 가장 확률이 높은 심볼<br/>

&ensp;LP: 가장 확률이 낮은 심볼<br/>
&ensp;위 예시에서는 P(1) = 0.2 이므로 LPS = 1<br/>

# Lossless Block Coding

&ensp;픽셀 하나하나를 압축하는 게 아니라, 여러 픽셀로 이루어진 block 또는 pattern을 하나의 symbol처럼 보고 그 block을 codeword에 매핑하는 방식<br/>

&ensp;예를 들어 이미지에 이런 block이 자주 나온다고 하자<br/>
<p align="center"><img src="/assets/img/Digital Image Processing/chap8-2/8-24.png" width="600"></p>

&ensp;또는<br/>
<p align="center"><img src="/assets/img/Digital Image Processing/chap8-2/8-25.png" width="600"></p>

&ensp;이런 자주 나오는 패턴을 codebook에 등록해놓고 실제 데이터에서는 그 codeword 자체를 보내는 대신 index를 보내는 것이다.<br/>

&ensp;Codebook<br/>
&ensp;Codebook은 쉽게 말하면 패턴 사전이다.<br/>
&ensp;예를 들어<br/>
| Index | Pattern |
| ----- | ------- |
| 0     | 0000    |
| 1     | 1111    |
| 2     | 0011    |
| 3     | 1100    |

&ensp;이런 식으로 자주 나오는 block pattern을 저장해둔 표<br/>
&ensp;압축할 때는 실제 block 전체를 보내지 않고 Index = 2 이런 식으로 codeword index만 보낸다.<br/>
&ensp;복원할 때는 decoder가 codebook을 보고 Index = 2 -> 0011로 복원하는 것이다.<br/>

&ensp;왜 codebook size를 작게 유지해야 하나?<br/>
&ensp;Codebook이 너무 크면 문제가 생긴다.<br/>
* codebook 자체를 저장하거나 전송하는 비용이 커진다
* index 길이도 길어진다
* 검색도 복잡해진다

&ensp;너무 많은 패턴을 다 저장하지 않고 자주 나오는 중요한 패턴 위주로 유지해야 한다.<br/>

&ensp;LZ/LZW 계열의 핵심 아이디어<br/>
&ensp;처음에는 작은 codebook으로 시작한다. 예를 들어 처음에는 기본 문자나 기본 픽셀값만 들어있다고 하자. 그런데 데이터를 읽다가 새로운 패턴이 반복해서 보이면 그 패턴을 codebook에 추가한다. 즉 압축을 진행하면서 사전이 점점 확장되는 방식이다. -> **dictionary-based coding** <br/>

&ensp;Lossless block coding 압축률<br/>
&ensp;2:1 ∼ 3:1<br/>
&ensp;이 말은 원본 크기 대비 압축 후 크기가 대략<br/>
* 절반 정도
* 또는 1/3 정도

&ensp;예를 들어 원본이 300KB면<br/>
* 2:1 압축이면 150KB
* 3:1 압축이면 100KB

&ensp;정도로 줄어드는 느낌이다.<br/>

&ensp;LZ와 LZW<br/>
&ensp;이건 무손실 압축에서 유명한 사전 기반 압축 방식이다.<br/>

&ensp;LZ coding: Lempel-Ziv coding의 줄임말.<br/>

> 이미 앞에서 나온 문자열/패턴을 다시 저장하지 않고, 그 위치나 index로 참조해서 압축한다.

&ensp;LZW<br/>
&ensp;Lempel-Ziv-Welch의 줄임말<br/>
&ensp;대표적으로 GIF 같은 포맷에서 사용된 것으로 유명하다.<br/>

> LZW는 작은 초기 codebook에서 시작하여 입력 데이터를 읽으면서 새로운 패턴을 codebook에 추가하고, 실제 데이터 대신 codebook index를 전송하는 무손실 dictionary-based compression 방식이다.
