# 압축이 필요한 이유

&ensp;이미지는 데이터 양이 너무 크기 때문에 사람이 잘 못 느끼거나 반복되는 정보를 줄여서 저장, 전송 효율을 높이는 기술이 필요하다.<br/>

| 구분                   | 의미                       | 예시                                     |
| -------------------- | ------------------------ | -------------------------------------- |
| Lossless Compression | 원본을 완전히 복원 가능            | PNG, Huffman coding, Arithmetic coding |
| Lossy Compression    | 일부 정보 손실이 있지만 사람이 잘 못 느낌 | JPEG, DCT, Quantization, YCbCr 4:2:0   |

&ensp;압축에서 줄이는 대상<br/>

| 줄이는 대상                        | 의미                        | 관련 기법                                |
| ----------------------------- | ------------------------- | ------------------------------------ |
| Statistical Redundancy        | 자주 나오는 값은 짧게 표현           | VLC, Arithmetic coding               |
| Spatial / Temporal Redundancy | 주변 픽셀이나 이전 프레임과 비슷한 정보 제거 | DPCM, Motion Compensation            |
| Human Visual Redundancy       | 사람이 민감하지 않은 고주파·색상 정보 제거  | DCT, Quantization, YCbCr subsampling |

&ensp;Media vs. Information<br/>
&ensp;1. SDTV 데이터량<br/>
&ensp;1280×720×1.5×30Hz<br/>

| 항목         | 의미                            |
| ---------- | ----------------------------- |
| 1280 × 720 | 한 프레임의 해상도                    |
| 1.5        | YCbCr 4:2:0 포맷에서 픽셀당 평균 바이트 수 |
| 30Hz       | 초당 30프레임                      |

&ensp;한 초 데이터량=가로×세로×픽셀당 바이트×초당 프레임<br/>

&ensp;2. 왜 4:2:0이면 1.5 byte인가?<br/>
&ensp;RGB는 한 픽셀마다 R, G, B가 각각 1 byte씩 필요하다.<br/>
&ensp;RGB=3byte/pixel<br/>
&ensp;그런데 YCbCr 4:2:0은 밝기 Y는 모든 픽셀에 저장하지만 색차 Cb, Cr은 줄여서 저장한다.<br/>
&ensp;쉽게 보면 2×2 픽셀 블록을 기준으로:<br/>
&ensp;Y는 4개 모두 저장하고 Cb와 Cr은 각각 1개씩만 저장한다.<br/>
&ensp;총 2×2 픽셀 4개를 표현하는 데 필요한 샘플 수는 4 + 1 + 1 = 6개.<br/>
&ensp;4픽셀당 6 byte니까, 1픽셀당 평균은 $\frac{6}{4} = 1.5byte$ <br/>

&ensp;3. HDTV 데이터량 계산<br/>
&ensp;1920 x (1080/2) x 1.5 x 60Hz<br/>
&ensp;여기서 1080/2가 들어간 이유는 1080i이기 때문 -> i는 interlaced, 즉 한 번에 전체 프레임을 다 보내는 게 아니라 홀수 줄/짝수 줄을 번갈아 보내는 방식이다. 그래서 한 필드당 세로 줄 수를 절반으로 보는 것이다.<br/>
&ensp;계산해보면 1920 × 540 × 1.5 × 60 = 약 93Mbytes/sec<br/>

&ensp;4. Compression ratio 계산<br/>
&ensp;방송 대역폭이 10 Mbps라고 했을 때, 원본 HDTV 데이터량은 93 Mbytes/sec<br/>
&ensp;단위가 다르니까 byte를 bit로 바꿔야 한다. 1byte = 8bits<br/>
&ensp;따라서 $93Mbytes/sec = 93 × 8Mbits/sec = 744Mbps$ <br/>

&ensp;압축 후 전송 대역폭이 10 Mbps라면 압축률은<br/>
$$Compression Ratio = \frac{Original Data}{Compressed Data} = \frac{93  \times 8}{10} = 74.4$$

&ensp;원래 데이터를 약 74.4분의 1 수준으로 줄여야 방송 가능하다는 뜻이다.<br/>

&ensp;8K UHD, 4:4:4<br/>
&ensp;1. Full-HD @60Hz YCbCr 4:4:4<br/>
&ensp;1920 × 1080 × 60 × 3byte<br/>
&ensp;여기서 3byte가 붙는 이유는 4:4:4이기 때문이다.<br/>
&ensp;4:4:4는 색 정보를 줄이지 않는다. 즉 Y, Cb, Cr을 모두 픽셀마다 저장한다.<br/>
&ensp;Y = 1byte, Cb = 1byte, Cr = 1byte<br/>
&ensp;그래서 1pixel = 3byte 계산하면:<br/>
$$(1920 \times 1080 \times 60Hz) \times 3bytes = 0.36Gbyte/sec$$

&ensp;2. 8K @120Hz YCbCr 4:4:4<br/>
$$7680 \times 4320 \times 120 \times 3bytes ≈ 11.94Gbyte/sec$$

&ensp;즉, 8K 120Hz 4:4:4 영상은 압축하지 않으면 1초에 약 12GB 가까운 데이터가 생긴다.<br/>

| 요소     | 증가                 |
| ------ | ------------------ |
| 해상도    | Full-HD보다 8K가 훨씬 큼 |
| 프레임레이트 | 60Hz → 120Hz       |
| 색상 포맷  | 4:4:4라서 색 정보 손실 없음 |


&ensp;3. 그림 해석: Full-HD, 4K, 8K 크기 비교<br/>

<p align="center"><img src="/assets/img/Digital Image Processing/chap8/8-1.png" width="600"></p>

&ensp;Full-HD: 1920 × 1080<br/>
&ensp;4K UHD: 3840 × 2160<br/>
&ensp;8K UHD: 7680 × 4320<br/>

&ensp;4K는 Full-HD의 가로 2배, 세로 2배이다.<br/>
&ensp;4K는 Full-HD보다 픽셀 수가 4배(2 x 2 = 4) 많다.<br/>

&ensp;8K는 4K보다 가로 2배, 세로 2배이다.<br/>
&ensp;8K는 4K보다 4배 많고, Full-HD보다 보면 4 × 4=16배 많다.<br/>

| 해상도     | 픽셀 수 관계      |
| ------- | ------------ |
| Full-HD | 기준           |
| 4K UHD  | Full-HD의 4배  |
| 8K UHD  | Full-HD의 16배 |


&ensp;그래서 영상 압축이 없으면 저장도 전송도 거의 불가능해진다.<br/>

&ensp;그래서 압축이 필요한 이유는 영상 데이터가 너무 많이 생기기 때문이다.<br/>
&ensp;1. 통신미디어 이용 시<br/>
&ensp;압축을 하면 같은 통신망에서도 더 많은 데이터를 보낼 수 있다.<br/>
&ensp;2. 저장미디어 이용 시<br/>
&ensp;압축을 하면 적은 공간으로 멀티미디어 정보 기록 가능<br/>
&ensp;3. 방송미디어 이용 시<br/>
&ensp;압축하면 같은 방송 대역폭 안에서 더 많은 채널을 보낼 수 있다.<br/>

# In technical terms

&ensp;압축에서 실제로 어떤 정보를 활용하는지 정리<br/>
&ensp;A. **Statistical Coding Redundancy**<br/>
&ensp;통계적 중복성은 **자주 나오는 값과 덜 나오는 값을 똑같은 길이로 표현하는 낭비**를 말한다.<br/>
&ensp;예를 들어 어떤 이미지에서 픽셀 값이 다음처럼 나온다고 해보자<br/>

| 픽셀 값 | 등장 빈도 |
| ---- | ----- |
| 0    | 매우 자주 |
| 255  | 가끔    |
| 128  | 거의 없음 |

&ensp;그런데 모든 픽셀 값을 8비트로 표현하면, 자주 나오는 0도 8비트, 거의 안 나오는 128도 8비트를 쓴다. -> 비효율적<br/>
&ensp;그래서 자주 나오는 값에는 짧은 코드, 드물게 나오는 값에는 긴 코드를 주는 방식이 사용된다. -> **Variable Length Coding, VLC**<br/>

&ensp;예를 들어<br/>
| 값        | 기존 코드 | 압축 코드 |
| -------- | ----- | ----- |
| 자주 나오는 값 | 8비트   | 1비트   |
| 가끔 나오는 값 | 8비트   | 3비트   |
| 드문 값     | 8비트   | 6비트   |

&ensp;전체 평균 비트 수가 줄어드는 것이다.<br/>
&ensp;대표 기법: VLC, Arithmetic Coding<br/>
&ensp;이건 **lossless compression**에 해당<br/>

&ensp;B. **Spatial & Temporal Redundancy**<br/>
&ensp;1. Spatial Redundancy<br/>
&ensp;Spatial은 공간이라는 뜻이다. 이미지에서는 주변 픽셀까지 비슷하다는 뜻으로 이해하면 된다. 예를 들어 하늘 사진을 보면 주변 픽셀들이 거의 비슷한 파란색이다.<br/>
&ensp;120, 121, 121, 122, 120 -> 이런 식으로 조금씩만 바뀐다. 그러면 모든 픽셀 값을 각각 저장하는 대신 이전 픽셀과의 차이만 저장할 수 있다.<br/>
&ensp;예를 들어 원본이 100, 102, 103, 103, 104 이면 첫 값 100만 저장하고 차이를 저장하면 100, +2, +1, 0, +1 이렇게 된다.<br/>
&ensp;차이값은 원래 픽셀 값보다 작기 때문에 더 적은 비트로 표현할 수 있다.<br/>
&ensp;이 방식이 **DPCM=Differential PCM** 이다.<br/>
&ensp;핵심은 현재값 ≈ 이전값 이므로 차이값 = 현재값 - 예측값만 저장한다.<br/>

&ensp;2. Temporal Redundancy<br/>
&ensp;동영상에서는 연속된 프레임이 서로 비슷하다.<br/>
&ensp;예를 들어 사람이 화면에서 오른쪽으로 조금 움직였다고 해보자<br/>
&ensp;프레임 1: 사람이 왼쪽에 있음<br/>
&ensp;프레임 2: 사람이 조금 오른쪽으로 이동<br/>
&ensp;프레임 전체를 다시 저장하는 건 낭비이다. 대부분의 배경은 그대로고 물체 위치만 조금 바뀌었기 때문이다. 그래서 동영상 압축에서는 **이전 프레임에서 비슷한 블록을 찾고 얼마나 이동하는지만 저장**한다.<br/>
&ensp;-> **Motion Estimation / Motion Compensation(ME/MC)**<br/>

&ensp;C. **Human Visual System**<br/>
&ensp;이 부분은 손실 압축의 핵심<br/>
&ensp;사람의 눈은 모든 정보를 똑같이 민감하게 느끼지 않는다. 특히 사람 눈은 다음에 덜 민감하다.<br/>
| 덜 민감한 정보 | 의미                 |
| -------- | ------------------ |
| 고주파 성분   | 급격한 밝기 변화, 세밀한 디테일 |
| 색상 차이    | 밝기보다 색 변화에 둔감      |

&ensp;그래서 JPEG 같은 압축에서는 사람이 덜 민감한 정보를 더 많이 줄인다.<br/>

&ensp;1. DCT와 Quantization<br/>
&ensp;DCT는 이미지를 주파수 성분으로 바꾸는 변환이다.<br/>
&ensp;이미지 블록을 보면 대부분 중요한 정보는 저주파에 몰려 있다.<br/>

| 성분  | 의미               | 사람 눈 민감도 |
| --- | ---------------- | -------- |
| 저주파 | 전체적인 밝기, 부드러운 변화 | 민감       |
| 고주파 | 경계, 세부 무늬, 잡음    | 상대적으로 둔감 |


&ensp;그래서 DCT 후에 고주파 성분을 강하게 줄이거나 0으로 만들어도 사람이 크게 못 느낀다.<br/>
&ensp;이때 값을 줄이는 과정이 Quantization이다.<br/>
&ensp;압축 과정: Image → DCT → Quantization → Coding<br/>
&ensp;이 과정은 손실 압축이다. Quantization에서 값을 나누고 반올림하면서 원래 값을 완전히 복원할 수 없기 때문이다.<br/>

&ensp;2. Color space conversion + Subsampling<br/>
&ensp;RGB는 사람이 보는 색을 표현하기에는 직관적이지만, 압축에는 조금 불리하다. 그래ㅅ  보통 YCbCr로 바꾼다.<br/>

| 성분 | 의미           |
| -- | ------------ |
| Y  | 밝기 정보        |
| Cb | 파란색 계열 색차 정보 |
| Cr | 빨간색 계열 색차 정보 |

&ensp;사람 눈은 밝기 Y에는 민감하지만, 색차 Cb, Cr에는 상대적으로 둔감하다. 그래서 Cb, Cr 정보를 줄인다. 이게 색차 서브샘플링이다. 대표적으로 YCbCr 4:2:0<br/>
&ensp;이 방식은 밝기 정보는 많이 유지하고, 색 정보는 줄여서 저장한다. 그래서 화질 저하를 크게 못 느끼면서 데이터량을 줄일 수 있다.<br/>

| 항목                               | 설명              | 압축 종류                           |
| -------------------------------- | --------------- | ------------------------------- |
| A. Statistical redundancy        | 코드 길이를 효율화      | 무손실                             |
| B. Spatial & Temporal redundancy | 예측 후 차이만 저장     | 무손실 또는 손실 가능하지만 여기서는 무손실 쪽으로 분류 |
| C. Human Visual System           | 사람이 덜 느끼는 정보 제거 | 손실                              |


# Fundamentals — Data Redundancy

&ensp;1. $n_{1}, n_{2}$ 의 의미<br/>

| 표현 방식 | 필요한 비트 수 |
| ----- | -------- |
| 기존 표현 | $n_1$    |
| 압축 표현 | $n_2$    |

&ensp;보통 압축 전이 $n_1$, 압축 후가 $n_2$ 라고 보면 된다.<br/>

&ensp;2. Compression Ratio $C_R$
&ensp;공식: $C_{R} = \frac{n_1}{n_2}$ <br/>
&ensp;여기서 $C_{R}$ 은 compression ratio. 즉 압축률이다.<br/>
> 압축 전 데이터가 압축 후 데이터보다 몇 배 큰가?
	
&ensp;예를 들어 압축 전이 1000 bit, 압축 후가 250 bit라면: $C_R = 1000/250 = 4$ <br/>

&ensp;데이터가 원래의 1/4로 줄었다는 뜻이다.<br/>

&ensp;3. Relative Data Redundancy $R_D$ <br/>
&ensp;공식은 $R_{D} = 1 - \frac{1}{C_R}$ <br/>
&ensp;이 식은 compression ratio를 이용해서 얼마나 중복 데이터가 있었는지를 나타내는 식이다.<br/>

&ensp;여기에 $C_{R} = \frac{n_1}{n_2}$ 를 대입해보면 $R_{D} = 1 - \frac{1}{\frac{n_1}{n_2}} = 1 - \frac{n_2}{n_1}$ <br/>

&ensp;$R_{D} = \frac{n_1 - n_2}{n_1}$ <br/>
&ensp;= 원래 데이터 중에서 줄일 수 있었던 비율<br/>

&ensp;4. 세 가지 경우 해석<br/>
&ensp;경우 1. $n_1 = n_2$ <br/>
&ensp;압축 전후 비트 수가 같다.<br/>

$$C_R = \frac{n_1}{n_2} = 1$$

$$R_{D} = 1 - \frac{1}{1} = 0$$

&ensp;줄어든 게 없다.<br/>

&ensp;경우 2. $n_1 >> n_2$$ <br/>
&ensp;압축 전 데이터가 압축 후보다 훨씬 크다.<br/>
$$C_{R} = \frac{n_1}{n_2} -> \infty$$

$$R_{D} = 1 - \frac{1}{C_R}$$

&ensp;여기서 $C_{R}$ 이 매우 커지면 $\frac{1}{C_R} -> 0$ <br/>
&ensp;따라서 $R_{D} -> 1$ <br/>
&ensp;중복성이 매우 크다.<br/>

&ensp;경우 3. $n_{1} << n_{2}$ <br/>
&ensp;압축 후가 오히려 더 커진 경우이다.<br/>
$$C_{R} = \frac{n_1}{n_2} -> 0$$

$$R_{D} = 1 - \frac{1}{C_R}$$

&ensp;에서 $C_{R}$ 이 0에 가까우니까 $\frac{1}{C_R} -> \infty$ <br/>
&ensp;따라서 $R_{D} -> -\infty$ <br/>

## Statistical coding redundancy

&ensp;Statistical coding redundancy는 말 그대로 통계적으로 자주 나오는 값과 드물게 나오는 값이 있는데, 이들을 같은 길이의 코드로 표현해서 생기는 낭비이다.<br/>
&ensp;이미지에는 여러 gray level이 있다. 예를 들어 8비트 grayscale이면 가능한 밝기 값은 0,1, 2 , ⋯, 255  총 256개이다.<br/>
&ensp;그런데 실제 이미지에서는 모든 gray level이 똑같이 자주 나오지 않는다. 어떤 값은 자주 나오고 어떤 값은 거의 안 나온다. 그래서 자주 나오는 값은 짧은 비트로 표현하고 드물게 나오는 값은 긴 비트로 표현하면 평균 비트 수를 줄일 수 있다.<br/>

&ensp;1. Histogram probability 공식<br/>
$$p_{r}(r_k) = \frac{n_k}{n}$$

| 기호    | 의미                        |
| ----- | ------------------------- |
| $r_k$ | k번째 gray level            |
| $n_k$ | gray level (r_k)를 가진 픽셀 수 |
|  n    | 전체 픽셀 수                   |
|  L    | 가능한 gray level 개수         |

&ensp;$p_r(r_k)$ 는 이미지 안에서 gray level $r_k$ 가 등장할 확률이다. 예를 들어 전체 픽셀이 1000개인데 그 중 gray level 100인 픽셀이 250개라면 $p_r(100) = 250/1000 = 0.25$ 즉 gray level 100은 전체 이미지에서 25% 등장한다는 뜻이다.<br/>

&ensp;2. 왜 histogram probability가 압축에 중요할까?<br/>
&ensp;압축에서 중요한 건 **각 값이 얼마나 자주 등장하는가**이다.<br/>
&ensp;예를 들어 다음과 같은 이미지가 있다고 해보자<br/>
$$r_0, r_0, r_0, r_0, r_1, r_2$$

&ensp;여기서 $r_0$ 가 제일 많이 나온다. 그런데 모든 값에 3비트를 똑같이 주면 $r_0 = 000, r_1 = 001, r_2 = 010$ 자주 나오는 $r_0$ 에도 3비트를 써야 한다. 하지만 $r_0$ 에 짧은 코드를 주면 자주 나오는 값이 짧아져서 전제 평균 비트 수가 줄어든다.<br/>

&ensp;3. 평균 비트 수 공식<br/>

$$L_{avg} = \sum_{k = 0}^{L-1}l(r_k)p_r(r_k)$$

&ensp;하나의 픽셀을 표현하는 데 평균적으로 몇 비트가 필요한가?<br/>

| 기호         | 의미                          |
| ---------- | --------------------------- |
| $l(r_k)$   | gray level (r_k)에 배정된 코드 길이 |
| $p_r(r_k)$ | gray level (r_k)가 등장할 확률    |
| $L_{avg}$  | 평균 코드 길이                    |

&ensp;즉, 각 gray level에 대해 코드 길이×등장 확률을 모두 더하는 것이다.<br/>

&ensp;예시<br/>
<p align="center"><img src="/assets/img/Digital Image Processing/chap8/8-2.png" width="600"></p>

<p align="center"><img src="/assets/img/Digital Image Processing/chap8/8-3.png" width="600"></p>

&ensp;확률이 높은 gray level일수록 코드 길이가 짧고, 확률이 낮은 gray level일수록 코드 길이가 길다.<br/>
&ensp;Code 1의 평균 비트 수<br/>
&ensp;Code 1은 모든 값이 3비트<br/>

$$L_{avg, 1} = \sum_{k=0}^{7}3\cdot p_r(r_k) = 3 \times 1 = 3 bits$$

&ensp;즉 Code 1은 픽셀 하나당 평균 3비트가 필요하다.<br/>

&ensp;Code 2의 평균 비트 수<br/>
$$L_{avg} = \sum_{k=0}^{7}l_2(r_k)p_r(r_k) = 2(0.19) + 2(0.25) + 2(0.21) + 3(0.16) +4(0.08) + 5(0.06) + 6(0.03) + 6(0.02) = 2.70 bits$$

&ensp;Code 1은 평균 3비트였고, Code 2는 평균 2.7비트. 픽셀 하나당 평균적으로 0.3비트가 줄었다.<br/>

## Interpixel redundancy

&ensp;Interpixel redundancy는 말 그대로 픽셀들 사이에 존재하는 중복성이다. 이미지에서는 인접한 픽셀들이 완전히 랜덤하지 않다. 예를 들어 하늘, 벽, 피부, 도로 같은 영역은 주변 픽셀 값이 비슷하다. 즉 현재 픽셀은 주변 픽셀로 어느 정도 예측 가능하다. 그래서 현재 픽셀 값을 그대로 저장하지 말고, 주변 픽셀로 예측한 뒤 차이만 저장한다.<br/>

<p align="center"><img src="/assets/img/Digital Image Processing/chap8/8-4.png" width="600"></p>

&ensp;Histogram만으로는 이미지 구조를 알 수 없다<br/>
&ensp;두 이미지의 histogram이 비슷하다는 말은, 두 이미지에 사용된 밝기 값들의 비율이 비슷하다는 뜻이다. 하지만 이미지의 구조는 완전히 다르다.<br/>
&ensp;왼쪽 이미지는 성냥이 불규칙하게 놓여 있고, 오른쪽 이미지는 규칙적으로 정렬되어 있다. 그런데 histogram은 픽셀 값의 개수만 세기 때문에, 픽셀들이 어디에 배치되어 있는지는 모른다.<br/>
&ensp;histogram은 다음 정보는 알 수 없다<br/>
* 픽셀들의 위치 관계
* 구조적 관계
* 기하학적 패턴

&ensp;그래서 statistical coding redundancy만으로는 충분하지 않다. 이미지 압축에서는 픽셀 간 관계, interpixel redundancy를 봐야 한다.<br/>

&ensp;Correlation의 의미<br/>
&ensp;이미지 안 객체의 구조적 또는 기하학적 관계 때문에 픽셀들 사이에 상관성이 생긴다. 예를 들어 성냥 하나는 길쭉한 흰 막대와 검은 머리 부분으로 구성되어 있다. 성냥 막대 내부에서는 인접 픽셀들이 모두 밝은 값이다. 220, 221, 219, 222 이런 식으로 비슷하다. 그러면 한 픽셀을 알면 주변 픽셀도 어느 정도 예측할 수 있다. -> correlation<br/>

&ensp;Autocorrelation coefficient 공식<br/>
$$r(\bigtriangleup n) = \frac{A(\bigtriangleup n)}{A(0)}$$

&ensp;여기서 $A(\bigtriangleup n)$ 은 거리 $\bigtriangleup n$ 만큼 떨어진 픽셀들 사이의 평균 곱이다.<br/>

$$A(\bigtriangleup n) = \frac{1}{N - \bigtriangleup n}\sum_{y=0}^{N - 1 - \bigtriangleup n}f(x, y)f(x, y + \bigtriangleup n)$$

&ensp;이 식은 한 줄, 즉 같은 x 위치에서 y 방향으로 픽셀을 비교한다.<br/>

&ensp;Covariance<br/>
&ensp;Covariance는 왜 필요한가?<br/>
&ensp;A(Δn) 은 단순히 픽셀 값끼리 곱해서 평균을 냈다. 하지만 픽셀 값 자체에는 평균 밝기 성분이 포함되어 있다. 예를 들어 전체 이미지가 밝으면 픽셀 값들이 전반적으로 크고, 어두우면 전반적으로 작다. 그러면 실제 구조적 관계 때문이 아니라, 단순히 평균 밝기가 커서 값이 크게 나올 수 있다. 그래서 convariance에서는 평균을 빼고 비교한다.<br/>

&ensp;평균 밝기 공식<br/>
$$\mu \simeq \hat{\mu } = \frac{1}{MN}\sum_{m=1}^{M}\sum_{n=1}^{N}u(m, n)$$

&ensp;이건 M×N 이미지의 평균 밝기. 즉 전체 픽셀 값을 다 더해서 픽셀 개수 MN으로 나눈다.<br/>

&ensp;Covariance 공식<br/>
<p align="center"><img src="/assets/img/Digital Image Processing/chap8/8-5.png" width="600"></p>

&ensp;위치가 (m,n)만큼 떨어진 두 픽셀이 평균으로부터 얼마나 함께 변하는지 측정한다.<br/>

&ensp;첫 번째 픽셀: u(m', n')<br/>
&ensp;두 번째 픽셀: u(m+m', n+n')<br/>

&ensp;즉 두 번재 픽셀은 첫 번째 픽셀에서 m만큼 아래, n만큼 오른쪽으로 이동한 위치이다.<br/>

&ensp;각 픽셀에서 평균 밝기 $\hat{\mu }$ 를 뺀다.<br/>

$$u(m', n') - \hat{\mu }$$

$$u(m + m', n + n') - \hat{\mu }$$

&ensp;그리고 둘을 곱한다.<br/>

&ensp;평균을 빼는 이유<br/>
&ensp;평균을 빼면 각 픽셀이 전체 평균보다 밝은지 어두운지를 보게 된다.<br/>
&ensp;예를 들어 $u(m + m', n + n') - \hat{\mu } > 0$ 이면 평균보다 밝은 픽셀이고 $u(m + m', n + n') - \hat{\mu } < 0$ 이면 평균보다 어두운 픽셀이다.<br/>

&ensp;두 값을 곱했을 때 양수가 나오면 두 픽셀이 같은 방향으로 움직인다는 뜻이다.<br/>
| 첫 픽셀     | 두 번째 픽셀  | 곱 | 의미      |
| -------- | -------- | - | ------- |
| 평균보다 밝음  | 평균보다 밝음  | + | 같이 밝음   |
| 평균보다 어두움 | 평균보다 어두움 | + | 같이 어두움  |
| 평균보다 밝음  | 평균보다 어두움 | - | 반대로 움직임 |
| 평균보다 어두움 | 평균보다 밝음  | - | 반대로 움직임 |

# Subjective Fidelity Criteria

&ensp;압축 후 이미지 품질을 평가하는 방법이다. 압축을 하면 데이터는 데이터는 줄어들지만 특히 손실 압축에서는 원본과 복원 이미지가 완전히 같지 않을 수 있다. -> 이를 평가하는 기준이 fidelity criteria<br/>

&ensp;1. Fidelity의 의미<br/>
&ensp;Fidelity는 “충실도”라는 뜻<br/>
> 복원된 이미지가 원본 이미지와 얼마나 비슷한가?

&ensp;압축 전 원본 이미지를 u(m, n) 압축 후 복원 이미지를 u'(m, n)이라고 하면 두 이미지의 차이를 비교해서 품질을 평가할 수 있다.<br/>

| Value | Rating    | 의미               |
| ----: | --------- | ---------------- |
|     1 | Excellent | 매우 좋은 품질         |
|     2 | Fine      | 좋은 품질, 방해가 거의 없음 |
|     3 | Passable  | 받아들일 만한 품질       |
|     4 | Marginal  | 품질이 낮고 개선하고 싶음   |
|     5 | Inferior  | 매우 나쁘지만 볼 수는 있음  |
|     6 | Unusable  | 볼 수 없을 정도로 나쁨    |

# General image compression system

&ensp;입력 이미지는 f(x, y) 또는 동영상이면 시간까지 포함해서 f(x, y, t)로 표현<br/>

&ensp;압축기는 크게 세 단계로 구성: Mapper → Quantizer → Symbol coder<br/>
&ensp;복원기는 반대로 Symbol decoder → Inverse mapper<br/>
&ensp;를 거쳐 복원 이미지 $\hat{f}(x, y)$ 또는 $\hat{f}(x, y, t)$ 를 만든다.<br/>

&ensp;1. Mapper<br/>
&ensp;Mapper는 입력 이미지를 압축하기 좋은 형태로 바꾸는 단계(셀들 사이의 중복성을 줄이기 위한 단계)<br/>
&ensp;예를 들어 원본 픽셀을 그대로 저장하면 주변 픽셀들이 비슷해서 중복이 많다. 100, 101, 102, 102, 103 이걸 차이값으로 바꾸면 100, 1, 1, 0, 1<br/>
&ensp;이렇게 작은 값들이 많이 생긴다. 이런 변환이 mapper의 역할이다.<br/>

&ensp;Mapper는 reversible operation<br/>
&ensp;mapper 단계 자체는 보통 되돌릴 수 있다.<br/>
&ensp;예를 들어 원본이 100, 101, 102 이고 mapper가 차이값으로 바꾸면 100, 1, 1. 이걸 다시 원래대로 복원할 수 있다.<br/>
* 100
* 100 + 1 = 101
* 101 + 1 = 102

&ensp;mapper는 정보를 버리는 단계라기보다는 **표현 방식을 바꾸는 단계**<br/>
&ensp;대표 예시는 Run-length coding 또는 transform coefficients 로 표현하는 방식이다.<br/>

&ensp;Transform coefficients<br/>
&ensp;이미지를 공간 영역의 픽셀 값 그대로 보지 않고, 주파수 성분으로 바꾼 계수들<br/>
&ensp;예를 들어 JPEG에서는 이미지를 작은 블록으로 나눈 뒤 DCT를 적용한다. Image block→DCT coefficients<br/>
&ensp;이렇게 하면 이미지의 에너지가 주로 저주파 계수에 몰리고, 고주파 계수는 작아지는 경우가 많다. 그래서 이후 quantizer가 고주파 성분을 줄이기 쉬워진다.<br/>

&ensp;2. Quantizer<br/>
&ensp;Quantizer는 mapper의 출력값의 정확도를 줄이는 단계이다.<br/>
&ensp;Quantizer가 하는 일<br/>
&ensp;예를 들어 어떤 DCT 계수들이 있다고 해보자. 23, 17, 4, 2, 1. 이걸 양자화하면 대략적으로 표현한다.<br/>
&ensp;0 단위로 나누고 반올림하면 20, 20, 0, 0, 0 처럼 될 수 있다. 정확도는 떨어졌지만 작은 값들이 0이 되면서 압축하기 쉬워진다.<br/>
&ensp;하지만 원래 값 23, 17, 4, 2, 1을 원벽하게 되돌릴 수는 없다.<br/>
&ensp;그래서 lossy이다.<br/>

&ensp;Psychovisual redundancy<br/>
&ensp;Psychovisual redundancy는 사람이 시각적으로 잘 못 느끼는 정보이다. 대표적으로 사람은 밝기 변화에는 민감하지만 아주 세밀한 고주파 정보나 색차 변화에는 덜 민감하다. 그래서 quantizer는 사람이 덜 민감한 성분을 더 많이 줄인다. 예를 들어 JPEG에서는 고주파 DCT 계수를 더 강하게 양자화한다. 그 결과 데이터는 크게 줄고 사람 눈에는 큰 차이가 안 보이게 만드는 것이다.<br/>

&ensp;3. Symbol encoder<br/>
&ensp;Symbol encoder는 실제 비트열을 만드는 단계<br/>
&ensp;이건 앞에서 배운 statistical coding redundancy를 줄이는 방식<br/>

&emsp;Symbol encoder의 역할<br/>
&ensp;Mapper와 Quantizer를 거치면 출력값들이 나온다.<br/>
&ensp;예를 들어: 0, 0, 0, 0, 5, 0, 0, 1<br/>
&ensp;여기서 0이 많이 나오면 0에 짧은 코드를 주고, 드문 값에는 긴 코드를 준다.<br/>
&ensp;예를 들어 0→1, 1→010, 5→0001<br/>
&ensp;이렇게 하면 전체 평균 비트 수가 준다.<br/>
&ensp;대표 방식: Huffman coding, Arithmetic coding<br/>

&ensp;Mapper, Quantizer, Symbol encoder 차이<br/>

| 단계             | 역할       | 줄이는 중복성                 | 손실 여부  |
| -------------- | -------- | ----------------------- | ------ |
| Mapper         | 표현 형태 변환 | interpixel redundancy   | 보통 무손실 |
| Quantizer      | 정확도 감소   | psychovisual redundancy | 손실     |
| Symbol encoder | 짧은 코드 배정 | coding redundancy       | 무손실    |

&ensp;압축에서 손실이 생기는 대표 단계는 Quantizer다.<br/>
&ensp;Mapper나 Symbol encoder는 보통 원칙적으로 되돌릴 수 있지만, Quantizer는 값을 버리기 때문에 완전 복원이 어렵다.<br/>

# 압축 방식의 큰 분류 정리

&ensp;1. Compression Symmetry<br/>
&ensp;압축과 복원의 계산량이 비슷한지, 다른지를 알려준다.<br/>
&ensp;Symmetrical coding: 압축과 복원 난이도가 비슷한 방식<br/>
&ensp;Compression asymmetrical coding: 압축이 복원보다 훨씬 어려운 방식<br/>
&ensp;동영상 압축에서는 encoder가 엄청 많은 후보를 탐색한다. 예를 들어 현재 블록을 이전 프레임 어디에서 가져오면 가장 잘 맞는지 찾는 motion estimaiton을 한다. 이 과정은 매우 무겁다. 하지만 decoder는 이미 전달 motion vection와 잔차를 이용해서 복원만 하면 된다.<br/>
&ensp;그래서 Encoding 복잡도 > Decoding 복잡도 가 된다.<br/>
&ensp;YouTube 같은 서비스는 영상을 한 번 압축해두고 수많은 사용자가 반복 재생하니까, 인코딩이 오래 걸려도 괜찮진다. 대신 디코딩은 빠르고 가벼워야 한다.<br/>

&ensp;Decompression asymmetrical coding<br/>
&ensp;반대로 복원이 압축보다 더 어려운 구조도 있을 수 있다는 의미이다. 하지만 일반적인 영상 표준에서는 압축 쪽이 더 무거운 경우가 많다.<br/>

&ensp;2. Data explosion과 ESCAPE<br/>
&ensp;예를 들어 RLE는 반복이 많으면 좋지만, 반복이 거의 없으면 손해를 볼 수 있다.<br/>
* 원본: ABCDEF

&ensp;이런 식으로 전혀 반복이 없는데 매번 “몇 번 반복” 정보를 붙이면 오히려 길어진다. 그래서 압축 방식에서는 때때로 ESCAPE 코드를 사용한다.<br/>

&ensp;압축 데이터 오류의 위험<br/>
&ensp;압축 데이터는 구조가 촘촘하게 연결되어 있기 때문에 한 비트만 깨져도 그 뒤 해석이 전부 꼬일 수 있다. 예를 들어 가변 길이 코드에서 중간 비트 하나가 사라지면 어디서 코드가 끝나는지 모르게 된다. 그래서 영상 압축에서는 주기적으로 동기화 코드나 새 줄 시작 코드를 넣는다. 이걸 통해 오류가 생겨도 전체가 무너지지 않고 일정 구간 뒤부터 다시 복구할 수 있게 한다.<br/>

&ensp;3. Lossless vs Lossy<br/>
* Lossless (3:1)
* Lossy (>100:1)

&ensp;무손실 압축은 원본을 완전히 복원해야 해서 압축률이 제한적이다. 반면 손실 압축은 사람이 잘 못 느끼는 정보를 버리기 때문에 훨씬 높은 압축률이 가능하다.<br/>

&ensp;Lossless<br/>
&ensp;Decompressed data=original data<br/>
&ensp;복원 데이터와 원본 데이터가 완전히 같다.<br/>
* Run-Length Encoding
* Entropy Coding
* Huffman / Arithmetic Coding
* Lossless Predictive Coding

&ensp;Lossy<br/>
&ensp;Decompressed data ≠ original data<br/>
&ensp;즉 복원 데이터는 원본과 완전히 같지 않다.<br/>
&ensp;대표 방식<br/>
* Transform-domain Coding + Quantization
* MC-residual+Transform-domain Coding + Quantization

&ensp;MC는 Motion Compensation이다. 동영상 압축에서는 이전 프레임으로 예측하고 예측이 안 맞는 차이값인 residual을 transform coding과 quantization으로 압축된다.<br/>

&ensp;Hybrid<br/>
&ensp;MC + Transform Coding(DCT/DST) + Quantization<br/>
&ensp;이게 현대 비디오 압축의 핵심 구조이다.<br/>
&ensp;즉 동영상 압축은 보통 하나의 방법만 쓰는 게 아니라, Motion Compensation + Transform Coding + Quantization + Entropy Coding 을 섞어서 사용한다.<br/>

# RLE (Run-Length Encoding)

&ensp;1. RLE<br/>
&ensp;RLE는 Run-Length Encoding의 약자<br/>
> 같은 값이 연속해서 반복되면, 그 값을 여러 번 쓰지 않고 “값 + 반복 횟수”로 표현한다.

&ensp;예를 들어 AAAAABBBCC 를 그대로 저장하면 10개의 문자가 필요하다. 이걸 RLE로 A5B3C2 처럼 쓸 수 있다. 반복이 많을수록 효과가 좋다.<br/>

&ensp;예제<br/>
&ensp;원본 데이터: ABBBCCCCDEFGGGGHI<br/>
&ensp;반복되는 부분은:<br/>
* BBB
* CCCC
* GGGG

&ensp;RLE 결과는 AB!2C!4DEFG!3HI<br/>
* !: flag

&ensp;왜 B가 아니라 !2로 표현될까?<br/>
&ensp;반복 문자열을 special flag로 표시하는 방식<br/>
&ensp;원본에서 BBB 는 처음 B 하나는 그대로 두고, 나머지 반복을 !2로 표현한 것으로 볼 수 있다.<br/>
* BBB = B!2<br/>
* CCCC=C!4
* GGGG=G!3

&ensp;다만 RLE 표기 방식은 시스템마다 조금씩 다를 수 있다. 어떤 방식은 B3처럼 쓰고 어떤 방식은 B!2처럼 flag를 사용한다.<br/>

&ensp;2. Gray-scale RLE 예제<br/>
&ensp;슬라이드 예제: 76 76 76 76 76 78 79 79 79 79 80 80<br/>

&ensp;이걸 RLE로 표현하면 76∣5 78∣1 79∣4 80∣2<br/>
* 76이 5번
* 78이 1번
* 79가 4번
* 80이 2번

&ensp;바이트 수 계산<br/>
&ensp;원본은 숫자가 12개이다. -> 12 Bytes<br/>
&ensp;RLE 후에는 쌍이 4개 있다. -> 12 Bytes<br/>
* (76,5), (78,1), (79,4), (80,2)

&ensp;각 쌍이 값 1 byte + 길이 1 byte라고 보면 4 × 2=8 Bytes<br/>
&ensp;압축률은 $C_R = 12/8 = 1.5$ <br/>

&ensp;gray-scale RLE는 약 1.5:1<br/>

&ensp;3. Data explosion<br/>
&ensp;RLE는 반복이 많으면 좋지만, 반복이 없으면 오히려 커질 수 있다.<br/>
&ensp;예를 들어 76 78 80 81<br/>
&ensp;이걸 RLE로 쓰면 76∣1 78∣1 80∣1 81∣1<br/>
&ensp;원래는 4개였는데, 압축 후에는 값과 길이 쌍이 4개라서 총 8개 정보가 필요하다.<br/>
&ensp;즉 압축했는데 더 커진다. 이게 data explosion이다.<br/>

&ensp;4. Error와 resynchronization<br/>
&ensp;RLE 데이터는 중간에 하나가 깨지면 해석이 꼬일 수 있다.<br/>
&ensp;예를 들어 76∣5 78∣1 79∣4 에서 구분자나 숫자 하나가 깨지면 이후 값과 반복 횟수를 잘못 읽을 수 있다. 그래서 일정 구간마다 새 줄 시작 코드 같은 동기화 코드를 넣는다. 그러면 오류가 나도 한 줄 전체만 망가지고, 다음 줄부터 다시 정상 해석할 수 있다. -> resynchroniztion<br/>

&ensp;5. Binary image RLE<br/>
&ensp;Binary image는 픽셀 값이 0과 1만 있는 이미지이다. 팩스 문서처럼 흰색과 검은색만 있는 이미지가 대표적이다. 이런 이미지는 같은 값이 길게 반복되는 경우가 많다. 예를 들어 흰 배경은 0이 아주 길게 반복된다. 그래서 RLE가 매우 잘 먹힌다. -> 압축률: 4∼10:1<br/>

&ensp;6. Bit-plane RLE<br/>
&ensp;Gray-scale 이미지는 8비트라면 한 픽셀이 8개의 비트로 구성된다.<br/>
&ensp;예를 들어 픽셀 값 150을 이진수로 쓰면 10010110. 이미지 전체를 비트 위치별로 나누면 bit-plane이 된다. 예를 들어 최상위 비트들만 모은 이미지, 그 다음 비트들만 모은 이미지처럼 나누는 것이다.<br/> 
&ensp;Gray-scale image→bit-plane images<br/>
&ensp;각 bit-plane은 0과 1로만 된 binary image니까, 여기에 RLE를 적용할 수 있다. 다만 gray-scale 전체에서는 binary image만큼 반복성이 강하지 않아서 압축률은 최대 약 2:1.<br/>

&ensp;RLE 장점<br/>
* Simple to implement
    - 연속된 값의 개수만 세면 된다.
* Fast to execute
    - 계산량이 작다.
    - 복잡한 변환이나 확률 계산이 아니라 단순히 반복 횟수를 세는 방식
* Lossless compression
    - RLE는 무손실 압축

&ensp;RLE 단점<br/>
* Relatively low compression ratio
    - 일반적인 gray-scale 이미지에서는 반복되는 값이 생각보다 길지 않다.
* Susceptible to error
    - 값과 길이의 쌍으로 해석해야 하는데, 중간에 하나가 깨지면 뒤의 해석이 전부 밀릴 수 있기 때문이다.

&ensp;Error propagation problem<br/>
&ensp;전송된 데이터: 44∣2 53∣4 60∣3 89∣1 64∣2 77∣2<br/>
* 44가 2번
* 53이 4번
* 60이 3번
* 89가 1번

&ensp;그런데 깨진 데이터에서 60|3이 잘못되었다고 해보면 이후 해석이 꼬여서 decoded 결과가 3∣89 1∣64 2∣77 2∣... 처럼 밀려버린다. 즉 한 부분의 오류가 이후 전체 데이터 해석에 영향을 준다. -> error propagation<br/>

&ensp;해결 방법: special code 삽입<br/>
&ensp;일정 간격마다 새 줄 시작 코드 같은 동기화 코드를 넣는다.<br/>
&ensp;그러면 오류가 생겨도 다음 동기화 코드부터 다시 정상 해석할 수 있다. -> resynchronization<br/>
