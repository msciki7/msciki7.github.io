# Lempel-Ziv(LZ) coding — text compression

&ensp;1) 기본 아이디어<br/>
&ensp;텍스트를 보낼 때 원래는 글자 하나하나를 전송한다.<br/>
&ensp;예를 들어 ASCII를 사용하면 보통 한 글자당 7bit이다. `This` 라는 단어를 그냥 문자 단위로 보내면 총 4글자니까 `4 × 7bit = 28bit` 가 필요하다.<br/>
&ensp;그런데 사전에 "This"라는 단어가 이미 들어 있고, 그 단어의 번호가 128번이라면? `This → 128` <br/>
&ensp;이렇게 번호 하나만 보내면 된다. 즉 원래는 여러 글자를 보내야 했는데 압축 후에는 사전의 index만 전송한다.<br/>

&ensp;2) Dictionary-based compression이란<br/>
&ensp;`Dictionary-based compression = 단어 또는 문자열을 사전에 저장해두고, 실제 전송할 때는 문자열 자체가 아니라 사전 번호를 보내는 압축 방식` <br/>

&ensp;예를 들어 사전이 이렇게 있다고 해보자<br/>

| Index | Word   |
| ----: | ------ |
|   128 | This   |
|   129 | is     |
|   130 | simple |
|   131 | as     |
|   132 | it     |

&ensp;그러면 문장 `This is simple as it is` 를 전송할 때 문자 하나하나를 다 보내는 대신 `128 129 130 131 132 129` 처럼 보낼 수 있다.<br/>
&ensp;여기서 중요한 건 `"is"` 가 두 번 나오면 두 번 모두 `"is"` 를 문자로 보내는 게 아니라 **129라는 index만 반복해서 보낸다**는 점이다.<br/>

&ensp;압축률 계산<br/>
&ensp;문제: 평균 한 단어가 6글자이고, 사전에 4096개의 단어가 있다. 원래는 7-bit ASCII codeword를 사용한다. 평균 compression ratio를 구하라.<br/>

&ensp;(1) 원래 방식: ASCII 문자 단위 전송<br/>
&ensp;한 글자 = 7bit, 한 단어 평균 = 6글자<br/>
&ensp;따라서 한 단어를 원래 방식으로 보내면 `6 characters/word × 7 bits/character = 42 bits/word` <br/>
&ensp;단어 하나당 평균 42bit가 필요하다.<br/>

&ensp;(2) 압축 방식: 사전 index 전송<br/>
&ensp;사전에 단어가 4096개 있다.<br/>
&ensp;사전에 4096개의 단어가 있으면 각 단어를 구분하기 위해 index가 필요하다.<br/>
&ensp;`n비트 index로 표현 가능한 항목 수 = 2^n개` <br/>

&ensp;4096은 `4096 = 2^12` 이므로 4096개의 단어를 표현하려면 index가 12bit 필요하다.<br/>

&ensp;(3) 압축률<br/>
&ensp;`Compression ratio = Original bits / Compressed bits` <br/>

&ensp;Compression ratio = 42 / 12 = 3.5<br/>
&ensp;원래 42bit가 필요했던 정보를 압축하면 12bit로 보낼 수 있으니까, 약 3.5배 줄어든다.<br/>

&ensp;3) LZ 방식의 한계<br/>
&ensp;사전에 엄청 많은 단어를 미리 넣어놨는데, 실제 전송할 텍스트에서는 그중 아주 조금만 쓰면 비효율적이다.<br/>
&ensp;예를 들어 사전에 4096개 단어가 있으면 무조건 index가 12bit이다. 그런데 실제 문장에서는 단어가 20개 정도만 반복된다고 해보자.<br/>
&ensp;그러면 사실 20개만 구분하면 되니까 `20 < 32 = 2^5` 5bit 정도면 충분할 수 있다. 그런데 4096개 사전을 기준으로 12bit index를 계속 쓰면 낭비가 생긴다. 이걸 보완하기 위해 나온게 **LZW** 이다.<br/>

# Lempel-Ziv-Welsh(LZW) coding

&ensp;1) LZW는 LZ의 adaptive version<br/>
&ensp;LZW는 처음부터 거대한 사전을 다 가지고 시작하지 않는다. 대신 `텍스트를 읽으면서 자주 등장하는 문자열을 사전에 동적으로 추가한다.` <br/>

&ensp;2) LZW의 초기 사전<br/>
&ensp;초기 사전: `basic character set + empty locations`<br/>
&ensp;예를 들어 ASCII 문자 집합을 사용하면 초기 사전에는 ASCII 문자들이 들어 있다.<br/>
&ensp;8bit index를 기준<br/>
&ensp;8bit index로 표현 가능한 개수는 `2^8 = 256개` <br/>
* 0 ~ 127 : basic character set
* 128 ~ 255 : 새로 발견한 단어/문자열을 넣을 빈 공간

&ensp;3) LZW 기본 동작<br/>

&ensp;예시<br/>
&ensp;`This_is_simple_as_it_is` <br/>
&ensp;처음에는 사전에 기본 문자만 있다 그러다가 텍스트를 읽으면서 새 문자열을 사전에 추가한다.<br/>

| Index | Dictionary |
| ----: | ---------- |
| 0~127 | 기본 문자 집합   |
|   128 | This       |
|   129 | is         |
|   130 | simple     |
|   131 | as         |
|   132 | it         |

&ensp;그러면 "This" 라는 단어가 처음 나올 때는 아직 사전에 없을 수 있다. 그때는 문자 단위로 보내면서 "This" 를 새로 사전에 추가한다. 그 다음에 "is" 도 새로 등장하면 "is" 를 사전에 추가한다. 이후 문장 뒤쪽에서 "is" 가 다시 나오면 이미 "is" 는 index 129에 들어 있으니까 `is → 129` 로 보낼 수 있다.<br/>

<p align="center"><img src="/assets/img/Digital Image Processing/chap8-3/8-1.png" width="600"></p>

&ensp;LZW를 진짜 이해하는 핵심<br/>
&ensp;송신자와 수신자가 같은 규칙으로 사전을 동시에 만들어간다.<br/>
&ensp;송신자가 압축하면서 새 문자열을 사전에 추가한다. 수신자도 압축된 index를 해석하면서 똑같은 문자열을 사전에 추가한다.<br/>
* 송신자: 텍스트를 읽으며 사전 생성 + index 전송
* 수신자: index를 읽으며 같은 규칙으로 사전 복원

&ensp;그래서 따로 전체 사전을 보내지 않아도 된다.<br/>

&ensp;4) 사전 크기의 동적 확장<br/>
&ensp;index bit 수가 늘어나는 과정<br/>
&ensp;처음에는 index가 8bit이다. 8bit index로 표현 가능한 항목 수는 `2^8 = 256개` <br/>
&ensp;index는 0 ~ 255까지 가능하다. 그런데 LZW는 텍스트를 읽으면서 새 문자열을 계속 사전에 추가한다. 처음에는 128~255까지 빈 공간에 새 단어를 넣을 수 있다.<br/>

&ensp;예를 들어:<br/>
* 128 : This
* 129 : is
* ...
* 255 : fish

&ensp;여기까지는 8bit index로 표현 가능하다. 그런데 새로 "pond"라는 단어를 넣어야 하는데, index 256이 필요하다면?<br/>
&ensp;8bit로는 255까지만 표현 가능하니까 256을 표현할 수 없다. 그래서 index bit 수를 늘려야 한다.<br/>
&ensp;`8bit → 9bit` <br/>
&ensp;9bit index로 표현 가능한 항목 수는 2^9 = 512개. -> 0 ~ 511 까지 표현 가능하다.<br/>

<p align="center"><img src="/assets/img/Digital Image Processing/chap8-3/8-2.png" width="600"></p>

# Lossless Predictive Coding

&ensp;이미지에서는 주변 픽셀끼리 값이 비슷한 경우가 많다.<br/>
&ensp;예를 들어 어떤 한 줄의 픽셀 값이 이렇게 있다고 해보자<br/>
&ensp;`23 48 76 56 83` <br/>
&ensp;원래 방식이라면 이 픽셀 값을 그대로 전송한다. -> 각 픽셀이 8-bit라면 총 5개니까 5 × 8 = 40 bits가 필요하다.<br/>
&ensp;그런데 DPCM은 “현재 픽셀은 바로 이전 픽셀과 비슷할 가능성이 높다.” 라고 생각해 현재 픽셀을 그대로 보내는 대신 **이전 픽셀과의 차이**를 보낸다.<br/>

&ensp;DPCM의 기본 식<br/>
&ensp;`DPCM: Coded = f(x, y) - f(x-1, y)` <br/>

| 기호            | 의미               |
| ------------- | ---------------- |
| `f(x, y)`     | 현재 픽셀 값          |
| `f(x-1, y)`   | 바로 왼쪽 픽셀 값       |
| `coded value` | 현재 픽셀과 왼쪽 픽셀의 차이 |


&ensp;현재 픽셀을 예측할 때 왼쪽 픽셀을 predictor로 사용한다.<br/>
* 예측값 = 왼쪽 픽셀값
* 오차 = 현재 픽셀값 - 예측값

&ensp;그래서 DPCM의 핵심 식:<br/>

$$e = 실제값 - 예측값(= e_n = f_n - f̂_n)$$

| 기호     | 의미                      |
| ------ | ----------------------- |
| `f_n`  | 실제 현재 픽셀 값              |
| `f̂_n` | 예측한 현재 픽셀 값             |
| `e_n`  | prediction error, 예측 오차 |

&ensp;왜 차이값을 보내면 압축이 될까?<br/>
<p align="center"><img src="/assets/img/Digital Image Processing/chap8-3/8-3.png" width="600"></p>

&ensp;원본은 픽셀을 그대로 표현하려면 8bit가 필요하다. 그런데 인접한 픽셀은 값이 비슷한 경우가 많다. 예를 들어 `100, 102, 101, 103, 104` 이런 식이면 실제 필셀 값은 100 근처에 있지만 차이값은 작다. `100, +2, -1, +2, +1` . 원래 값은 0~255사이에 넓게 분포하지만 차이값은 대부분 0근처에 몰려있다. 그래서 DPCM histogram은 0 근처에 뾰족하게 모이게 된다.<br/>
* PCM samples histogram: 원본 픽셀 값 분포 → 넓게 퍼짐
* DPCM samples histogram: 차이값 분포 → 0 주변에 몰림

&ensp;Entropy가 작아지는 이유<br/>
&ensp;데이터가 얼마나 예측 불가능한가<br/>

&ensp;분포가 넓고 여러 값이 비슷한 확률로 나오면 예측하기 어렵다. 그러면 entropy가 커진다. 반대로 어떤 값이 매우 자주 나오고 나머지는 드물게 나오면 예측하기 쉽다. 그러면 entropy가 작아진다.<br/>

&ensp;DPCM에서는 차이값이 대부분 0 근처에 몰려있다. `e = 0, ±1, ±2, ±3 ...` <br/>
&ensp;같은 작은 값이 자주 나오고, 큰 차이값은 드물게 나온다. 그래서 entropy가 작아진다.<br/>

&ensp;원본 픽셀값:<br/>
* 0~255 범위에 비교적 넓게 분포
  - → 불확실성 큼
  - → entropy 큼
  - → 많은 bit 필요

&ensp;DPCM 예측 오차:<br/>
* 0 근처에 집중
  - → 불확실성 작음
  - → entropy 작음
  - → 적은 bit로 표현 가능

## 4-bit Two’s Complement

&ensp;4-bit two’s complement의 범위는: `-2^3 ~ 2^3 - 1` <br/>
&ensp;= -8 ~ 7 <br/>

&ensp;4-bit two’s complement에서는<br/>

```txt
0000 = 0
0001 = 1
0010 = 2
...
0111 = 7
1000 = -8
1001 = -7
...
1111 = -1
```

&ensp;n-bit two’s complement 범위<br/>
&ensp;n-bit two's complement range = `-2^(n-1) ~ 2^(n-1)-1` <br/>

&ensp;DPCM error는 음수가 나올 수 있으니까 unsigned가 아니라 signed representation이 필요하다.<br/>

## Lossless DPCM의 encoder/decoder 구조

&ensp;1) Encoder 구조<br/>
<p align="center"><img src="/assets/img/Digital Image Processing/chap8-3/8-6.jpg" width="600"></p>

&ensp;입력은 실제 픽셀값이다.( $f_n$ )<br/>
&ensp;Predictor는 이전 픽셀값들을 이용해서 현재 픽셀을 예측한다.( $f̂_n$ )<br/>
&ensp;그 다음 실제값에서 예측값을 뺀다.<br/>
$$e_n = f_n - f̂_n$$

&ensp;$e_{n}$ 만 부호화해서 보낸다.<br/>

&ensp;encoder는 이렇게 동작한다.<br/>
1. 현재 픽셀 f_n 입력
2. 이전 픽셀들을 이용해 예측값 f̂_n 계산
3. 예측 오차 e_n = f_n - f̂_n 계산
4. e_n을 Huffman coding 같은 방법으로 부호화해서 전송

&ensp;여기서 e_n은 0 근처에 몰려 있으니까 Huffman coding을 적용하면 더 잘 압축된다.<br/>

&ensp;2) Decoder 구조<br/>
<p align="center"><img src="/assets/img/Digital Image Processing/chap8-3/8-7.jpg" width="600"></p>

&ensp;Decoder는 전송받은 prediction error $e_n$ 을 복호화한다.<br/>
&ensp;그런 다음 decoder도 같은 predictor를 사용해서 예측값 `f̂_n` 을 만든다.<br/>
&ensp;그리고 원래 픽셀을 복원한다.<br/>
$$f_n = f̂_n + e_n$$

&ensp;복원값 = 예측값 + 예측 오차<br/>

&ensp;왜 encoder와 decoder가 같은 predictor를 알아야 할까?<br/>
&ensp;Encoder가 예측한 값과 decoder가 예측한 값이 다르면 복원이 틀어진다.<br/>

&ensp;예를 들어<br/>
* 실제값 $f_n = 80$
* encoder 예측값 f$̂_n = 75$
* error $e_n = 80 - 75 = 5$

&ensp;encoder는 5를 보냈다. 그런데 decoder가 다른 predictor를 써서 예측값을 70으로 만들면 `decoder 복원값 = 70 + 5 = 75` <br/>
&ensp;원래 값 80이 아니라 75가 되어버린다.<br/>
&ensp;즉, lossless가 깨진다.<br/>

&ensp;`무손실 DPCM에서는 encoder와 decoder가 같은 예측값 f̂_n을 만들어야 한다. 그래야 decoder가 f_n = f̂_n + e_n으로 원본 픽셀을 정확히 복원할 수 있다.` <br/>

&ensp;Predictor는 어떻게 만들까?<br/>

$$\hat{f}_{n} = round\{ \sum_{i=1}^{m} \alpha _{i} f_{n-i} \}$$

&ensp;현재 픽셀을 예측할 때 이전 픽셀들의 선형 결합을 사용한다.<br/>
&ensp;m = 예측에 사용하는 이전 sample 개수<br/>

# Lossless JPEG Coding

&ensp;무손실 JPEG가 DPCM 기반 예측 부호화를 사용한다<br/>

&ensp;1) 주변 픽셀 a, b, c의 위치<br/>
<p align="center"><img src="/assets/img/Digital Image Processing/chap8-3/8-8.png" width="600"></p>

| 기호  | 의미           |
| --- | ------------ |
| `x` | 현재 부호화하려는 픽셀 |
| `a` | 왼쪽 픽셀        |
| `b` | 위쪽 픽셀        |
| `c` | 왼쪽 위 대각선 픽셀  |


&ensp;이미지를 보통 왼쪽에서 오른쪽, 위에서 아래로 스캔한다고 생각하면, x를 처리하는 시점에서 a, b, c는 이미 처리된 픽셀이다. 그래서 이 값들을 이용해 현재 픽셀 x를 예측할 수 있다.<br/>

&ensp;2) 이전 픽셀만 사용하는 이유<br/>
&ensp;이미 부호화된 이웃 픽셀만 사용한다는 뜻 -> decoder도 똑같이 복원해야 해야 하기 때문<br/>
&ensp;decoder가 현재 픽셀 x를 복원하려면 predictor를 계산해야 한다. 그런데 아직 복원되지 않은 미래 픽셀을 predictor에 사용하면 decoder는 그 값을 알 수 없다. 그래서 현재 픽셀보다 먼저 처리된 픽셀만 사용해야 한다. <- causal system <br/>

&ensp;3) Lossless JPEG의 7가지 predictor<br/>
* P1 = a (현재 픽셀 x는 왼쪽 픽셀 a와 비슷할 것이다.)
* P2 = b (현재 픽셀 x는 위쪽 픽셀 b와 비슷할 것이다.)
* P3 = c (현재 픽셀 x는 왼쪽 위 픽셀 c와 비슷할 것이다.)
* P4 = a + b - c (왼쪽 방향 변화와 위쪽 방향 변화를 같이 반영하는 예측식)
* P5 = a + (b - c) / 2 (현재 픽셀은 왼쪽 픽셀 a와 비슷하지만, 위쪽과 왼쪽 위의 차이도 조금 반영하겠다.)
* P6 = b + (a - c) / 2 (현재 픽셀은 위쪽 픽셀 b와 비슷하지만, 왼쪽과 왼쪽 위의 차이도 조금 반영하겠다.)
* P7 = (a + b) / 2 (픽셀은 왼쪽과 위쪽 사이의 중간 정도 밝기)

&ensp;4) 첫 번째 행과 첫 번째 열은 예외<br/>
&ensp;현재 픽셀 x를 예측하려면 원래 a, b, c가 필요하다. 그런데 첫 번째 행에서는 위쪽 픽셀 b가 없다.<br/>
&ensp;그래서 사용할 수 있는 건 왼쪽 픽셀 a뿐<br/>
&ensp;반대로 첫 번째 열에서는 왼쪽 픽셀 a가 없다.<br/>

# Lossy Image Compression

&ensp;Lossy: 일부 정보를 버림 복원 후 원본과 완전히 같지는 않음<br/>

&ensp;1) 손실 압축의 두 가지 원리<br/>

&ensp;Redundancy reduction<br/>
&ensp;이미지에는 중복이 많다. 예를 들어 비슷한 파란색이 계속 반복되고, 벽이나 배경도 비슷한 픽셀이 반복된다. 이런 중복을 줄이는 게 redundancy reduction.<br/>

&ensp;Entropy reduction<br/>
&ensp;데이터의 불확실성 자체를 줄인다. 가장 대표적인 방법이 양자화, quantization이다.<br/>
&ensp;양자화는 여러 값을 하나의 대표값으로 바꾼다.<br/>
&ensp;예를 들어<br/>
* 50.341 → 55
* 51.200 → 55
* 54.900 → 55

&ensp;이런 식으러 서로 다른 값들이 같은 값으로 바꾼다. 그러면 원래 차이는 사라진다. 즉 정보가 실제로 버려진다.<br/>

* overload 발생 시 flag + original value 전송

## Truncation Coding

&ensp;압축을 위해 이미지 데이터 일부를 버린다.<br/>

&ensp;1) Spatial down-sampling<br/>
&ensp;Spatial은 공간 방향이다. 이미지에서 공간방향이라는 건 가로, 세로 위치를 의미한다. Spatial down-sampling은 픽셀 수를 줄이는 것이다.<br/>
&ensp;예를 들어 원본 이미지가 1000 × 1000이면 픽셀이 1,000,000개이다. 이걸 500 × 500으로 줄이면 픽셀이 250,000개가 된다. 데이터 양은 확 줄어든다. 하지만 픽셀을 줄였기 때문에 세부 정보가 사라진다. 그 결과 이미지가 흐릿해진다.<br/>
&ensp;`spatial down-sampling → image blurring` <br/>

&ensp;2) Temporal down-sampling<br/>
&ensp;Temporal은 시간 방향이다. 동영상에서 시간 방향은 frame을 의미한다. Temporal down-sampling은 프레임을 일부 버리는 것이다.<br/>
&ensp;예를 들어 60fps 영상을 30fps로 줄이면 1초에 60장이던 것이 30장이 된다. 데이터 양은 줄어든다. 데이터 양이 줄어든다. 하지만 움직임이 부드럽지 않고 끊겨 보일 수 있다.<br/>
&ensp;`temporal down-sampling → motion jerkiness` <br/>

&ensp;3) Quantization<br/>
&ensp;양자화는 밝기값의 정밀도를 줄인다. 예를 들어 원래 밝기값이 0부터 255까지 256단계였다면 이를 16단계만 사용하도록 줄일 수 있다. 그러면 비트 수는 줄어든다.<br/>
* 256 levels = 8 bits
* 16 levels = 4 bits

&ensp;하지만 밝기가 부드럽게 변해야 할 부분이 계단처럼 보일 수 있다.<- contouring effect<br/>

## Uniform Quantizer

&ensp;구간을 같은 크기로 나누는 양자화<br/>

&ensp;1) Decision level과 Quantization level<br/>

| 기호    | 의미                           |
| ----- | ---------------------------- |
| $t_k$ | decision level, 구간 경계값       |
| $r_k$ | quantization level, 대표값      |
| $Q$   | quantization step size, 구간 폭 |

&ensp;Decision level $t_k$ <br/>
&ensp;$t_k$ 는 구간을 나누는 경계이다. 입력이 어느 구간에 들어가는지 판단하는 기준값이다. 예를 들어 0부터 10까지를 256개 구간으로 나누면 경계는 257개가 필요하다.<br/>

<p align="center"><img src="/assets/img/Digital Image Processing/chap8-3/8-10.png" width="600"></p>

&ensp;Quantization step size Q<br/>
&ensp;구간 폭은 항상 일정하다.<br/>

$$Q = t_k - t_{k-1}$$

&ensp;Quantization level $r_k$ <br/>
&ensp;$r_k$ 는 각 구간을 대표하는 값이다. 보통 균일 양자화에서는 각 구간의 중앙값을 대표값으로 잡는다. <br/>

<p align="center"><img src="/assets/img/Digital Image Processing/chap8-3/8-11.png" width="600"></p>

&ensp;왜 5/256이냐면 구간 폭이 10/256이기 때문이다.<br/>

&ensp;Uniform quantization의 규칙<br/>
&ensp;입력값 f가 어떤 구간에 들어가면, 그 구간의 대표값으로 바뀐다.<br/>

$$t_k ≤ f < t_{k+1}  ⇒  r_k$$

&ensp;입력값 f가 $t_k$ 와 $t_{k+1}$ 사이에 있으면, 출력은 $r_k$ 로 한다.<br/>

<p align="center"><img src="/assets/img/Digital Image Processing/chap8-3/8-12.png" width="600"></p>

&ensp;예를 들어 어떤 구간이 40~50이고 대표값이 45라면 `40 ≤ f < 50  ⇒  45` <br/>
* 41도 45
* 44도 45
* 49도 45

&ensp;로 바뀐다.<br/>
&ensp;여기서 정보 손실이 발생한다. 왜냐하면 복원된 값 45만 보고는 원래 값이 41이었는지 44였는지 49였는지 알 수 없기 때문이다.<br/>

&ensp;Quantization은 왜 irreversible인가?<br/>
&ensp;양자화가 되돌릴 수 없는 이유는 여러 입력값이 하나의 대표값으로 합쳐지기 때문이다.<br/>
&ensp;예를 들어<br/>
* 50.341kg → 55kg
* 51.2kg   → 55kg
* 54.9kg   → 55kg

&ensp;이렇게 되면 양자화 결과는 모두 55kg 나중에 55kg만 보고 원래 값이 50.341kg인지 51.2kg인지 54.9kg인지 알 수 없다. 그래서 양자화는 손실 과정이다.<br/>

&ensp;Quantization error<br/>
&ensp;`error = 원래값 - 대표값` <br/>
&ensp;또는 부호를 반대로 잡아도 되지만, 핵심은 원래값과 대표값의 차이이다.<br/>

<p align="center"><img src="/assets/img/Digital Image Processing/chap8-3/8-13.png" width="600"></p>

&ensp;구간 안에서 가장 멀리 떨어진 지점은 왼쪽 끝이나 오른쪽 끝이다. 대표값 $r_k$ 가 구간 가운데에 있으면 왼쪽 끝까지의 거리와 오른쪽 끝까지의 거리가 같아진다.<br/>
&ensp;균일 양자화에서 대표값을 중앙에 놓는다면 최대 오차는 `Q / 2` 가 된다.<br/>

## De-quantization

&ensp;양자화 후에는 실제 값을 대표값으로 복원한다. <- de-quantization<br/>
&ensp;예를 들어 압축 과정에서 50.341kg을 50~60 구간의 코드로 저장했다고 해보자<br/>
&ensp;복원할 때는 그 구간의 대표값인 55kg으로 복원한다. `코드 → 대표값` <br/>
&ensp;`50.341kg → 양자화 코드 → 55kg` -> 원래 50.341kg으로 돌아가지 못한다. -> 손실<br/>

&ensp;코드 비트열<br/>
&ensp;`000 010 001 111` <br/>
&ensp;이건 각 구간을 나타내는 index이다.<br/>
&ensp;3bit를 사용하면 표현 가능한 구간 수는 $2^3 = 8개$ <br/>
&ensp;구간 8개를 각각 000부터 111까지의 코드로 표현할 수 있다.<br/>
&ensp;예를 들어 어떤 구간은 000, 어떤 구간은 010, 어떤 구간은 111 같은 식으로 매핑된다.<br/>

&ensp;**연속적인 실제값을 몇 개의 구간으로 나누고, 각 구간을 짧은 codeword로 표현한다.** <br/>
